Fəlakətdən Bərpa və Yüksək Əlçatanlıq

DPE-07 · Data Platform & Engineering Bootcamp

Data mərkəzi söndü, şəbəkə qırıldı, disk zədələndi — sual "olacaqmı" deyil, "nə vaxt olacaq" sualıdır. Fəlakətdən bərpa (Disaster Recovery, DR) həmin an biznesin dayanmaması üçün əvvəlcədən qurulmuş plandır. Bu fəsildə çox-region deploy, Route 53 ilə avtomatik failover, backup və replikasiya, həmçinin Kubernetes klasterləri üçün DR-i Terraform ilə necə avtomatlaşdıracağımıza baxırıq.

1 · Fəlakətdən bərpanın üç sütunu

DR nə deməkdir

DR data mərkəzi kəsintiləri, şəbəkə nasazlıqları, təbii fəlakətlər və kiber hücumlar zamanı biznesin davam etməsinə yönəlib. Yaxşı qurulmuş DR strategiyası iki şeyi minimuma endirir: dayanma müddəti və itirilən data.

  • Yüksək əlçatanlıq (HA) — xidmətləri bir neçə region və ya zona arasında paylayaraq həmişə əlçatan saxlamaq. HA gündəlik nasazlıqlara qarşıdır.
  • Backup və bərpa — verilənlər bazasının, fayl sistemlərinin və tətbiq datasının müntəzəm nüsxəsi. Data korlanması və ya səhvən silinmə hallarında yeganə çıxış yolu budur.
  • Failover və failback — sıradan çıxmış əsas sistemdən ehtiyat sistemə keçmək (failover), problem həll olunandan sonra geri qayıtmaq (failback).

Terraform bu işlərin böyük hissəsini avtomatlaşdıra bilir: infrastruktur kod şəklində olduğu üçün ikinci region-da eyni quruluşu təkrar yaratmaq bir apply məsafəsindədir.

AnlayışMənasıPraktiki sual

RPOİtirilməsinə dözülən maksimum data"Neçə dəqiqəlik datanı itirə bilərik?"

RTO və RPO texniki deyil, biznes qərarlarıdır. Sıfıra yaxın RPO tələb edən sistem çox-region sinxron replikasiya deməkdir və xərci bir neçə dəfə artırır. Rəqəmləri əvvəlcə biznes tərəfi ilə razılaşdırın, memarlığı sonra seçin.

2 · Terraform ilə DR-in açar anlayışları

a. Çox-region və çox-zona deploy

DR-in ən geniş yayılmış yanaşması resursları bir neçə region və ya availability zone arasında paylamaqdır. Bir region-da nasazlıq olanda trafik eyni infrastrukturun işlədiyi digər region-a yönləndirilir.

b. Backup və replikasiya

Müntəzəm backup DR-in özəyidir. Terraform bulud-nativ backup xidmətlərini — Amazon S3, Azure Backup, Google Cloud Storage — konfiqurasiya edərək datanın avtomatik olaraq təhlükəsiz yerə köçürülməsini təmin edir.

c. Avtomatik failover

Avtomatik failover əsas sistem sıradan çıxanda trafikin insan müdaxiləsi olmadan ehtiyat sistemə yönlənməsidir. Bunun üçün AWS Route 53, Azure Traffic Manager və ya Google Cloud Load Balancing kimi sağlamlıq yoxlamasına əsaslanan trafik yönləndiricilərindən istifadə olunur.

3 · Çox-region deploy nümunəsi

Addım 1 — Region-lar üçün provider alias-ları

Eyni infrastrukturu iki region-da qurmaq üçün aws provider-inin iki alias-lı nüsxəsini yaradırıq.

provider "aws" {
  region = "us-east-1"
  alias  = "us_east"
}

provider "aws" {
  region = "us-west-1"
  alias  = "us_west"
}

Addım 2 — Hər iki region-da EC2 instance

# US-East region-unda web server
resource "aws_instance" "web_us_east" {
  provider      = aws.us_east
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    Name = "WebServer-East"
  }
}

# US-West region-unda eyni web server
resource "aws_instance" "web_us_west" {
  provider      = aws.us_west
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    Name = "WebServer-West"
  }
}

Hər iki instance eyni tətbiqi xidmət edir — biri sıradan çıxsa, digəri yükü götürməyə hazırdır.

AMI ID-ləri region-a bağlıdır: us-east-1 üçün keçərli olan ID us-west-1-də mövcud olmaya bilər. Hər region üçün AMI-ni data "aws_ami" ilə dinamik tapın və ya region → AMI xəritəsini variable kimi saxlayın. Sabit ID-ni kopyalamaq çox-region konfiqurasiyalarında ən çox təkrarlanan səhvdir.

Addım 3 — Route 53 ilə DNS failover

resource "aws_route53_zone" "example" {
  name = "example.com"
}

# Əsas qeyd — sağlam olduqca bütün trafik buraya gedir
resource "aws_route53_record" "primary" {
  zone_id        = aws_route53_zone.example.zone_id
  name           = "www.example.com"
  type           = "A"
  set_identifier = "primary"

  alias {
    name                   = aws_lb.east.dns_name
    zone_id                = aws_lb.east.zone_id
    evaluate_target_health = true
  }

  failover_routing_policy {
    type = "PRIMARY"
  }
}

# Ehtiyat qeyd — əsas sağlamlıq yoxlamasından keçmədikdə işə düşür
resource "aws_route53_record" "secondary" {
  zone_id        = aws_route53_zone.example.zone_id
  name           = "www.example.com"
  type           = "A"
  set_identifier = "secondary"

  alias {
    name                   = aws_lb.west.dns_name
    zone_id                = aws_lb.west.zone_id
    evaluate_target_health = true
  }

  failover_routing_policy {
    type = "SECONDARY"
  }
}

Burada Route 53 failover routing rejimində qurulub: normal vəziyyətdə trafik US-East-dəki əsas nüsxəyə gedir; sağlamlıq yoxlaması uğursuz olanda isə DNS cavabı avtomatik olaraq US-West-dəki ehtiyat nüsxəyə keçir.

Alias qeydləri load balancer, CloudFront və ya S3 website endpoint kimi AWS resurslarına yönəlir — birbaşa EC2 IP ünvanına yox. EC2 instance-a yönləndirmək lazımdırsa, alias əvəzinə adi records = [aws_instance.web.public_ip] ilə A qeydi və ayrıca aws_route53_health_check resursu işlədin.
DNS failover ani deyil: TTL müddəti bitənə qədər köhnə cavab client-lərdə keşdə qalır. TTL-i 60 saniyəyə salmaq keçidi sürətləndirir, amma sıfır dayanma müddəti vəd etmir. RTO hesablayarkən TTL-i mütləq nəzərə alın.

4 · Backup və replikasiyanın avtomatlaşdırılması

a. RDS backup-ları

Bulud provider-lərinin öz backup vasitələri var: AWS RDS snapshot-ları, Azure Backup, Google Cloud Persistent Disk snapshot-ları. Terraform bunları konfiqurasiya səviyyəsində idarə edir.

resource "aws_db_instance" "mydb" {
  allocated_storage = 20
  engine            = "mysql"
  instance_class    = "db.t2.micro"
  db_name           = "mydb"
  username          = "admin"
  password          = var.db_password

  backup_retention_period = 7             # backup-ları 7 gün saxla
  backup_window           = "01:00-03:00"  # yükün az olduğu saatlar
}

resource "aws_db_snapshot" "mydb_snapshot" {
  db_instance_identifier = aws_db_instance.mydb.id
  db_snapshot_identifier = "mydb-snapshot-${formatdate("YYYY-MM-DD-hhmm", timestamp())}"
}

Bu konfiqurasiyada RDS instance-ı avtomatik backup ilə yaradılır və nüsxələr 7 gün saxlanılır; əlavə olaraq tələb üzrə vaxt möhürlü manual snapshot alınır.

timestamp() funksiyası hər plan-da yeni dəyər qaytarır, ona görə snapshot resursu hər dəfə yenidən yaradılmaq üçün planlanır. Müntəzəm snapshot-lar üçün Terraform-u zamanlayıcı kimi işlətməyin — backup_retention_period ilə avtomatik backup-a və ya AWS Backup plan-larına arxalanın.

b. S3 lifecycle qaydaları

Obyekt saxlanması üçün lifecycle qaydaları datanı avtomatik olaraq ucuz saxlama sinifinə köçürür və müddəti bitmişləri silir.

resource "aws_s3_bucket" "my_bucket" {
  bucket = "my-backup-bucket"
}

resource "aws_s3_bucket_lifecycle_configuration" "backup_lifecycle" {
  bucket = aws_s3_bucket.my_bucket.id

  rule {
    id     = "archive-and-expire"
    status = "Enabled"

    transition {
      days          = 30
      storage_class = "GLACIER"  # 30 gündən sonra Glacier-ə keçir
    }

    expiration {
      days = 365                  # 365 gündən sonra sil
    }
  }
}

Nəticədə data 30 gün sonra uzunmüddətli və ucuz Glacier saxlamasına keçir, 365 gündən sonra isə silinərək həm xərci azaldır, həm də datanın sonsuz saxlanmasının qarşısını alır.

Köhnə lifecycle_rule bloku birbaşa aws_s3_bucket daxilində yazılırdı; AWS provider 4.x-dən sonra o, ayrıca aws_s3_bucket_lifecycle_configuration resursuna ayrıldı. Köhnə nümunələri kopyalayarkən bu fərqə diqqət edin.

5 · Kubernetes üçün DR

Çox-AZ EKS klasteri

Konteynerləşdirilmiş tətbiqlər üçün Kubernetes klasterinin özü də DR planına daxil olmalıdır. Terraform ilə klasteri bir neçə availability zone arasında paylanmış şəkildə qurmaq mümkündür.

resource "aws_eks_cluster" "my_cluster" {
  name     = "my-eks-cluster"
  role_arn = aws_iam_role.eks_role.arn

  vpc_config {
    # subnet-lər müxtəlif AZ-lərdə yerləşir
    subnet_ids = aws_subnet.my_subnets[*].id
  }
}

resource "aws_eks_node_group" "my_node_group" {
  cluster_name    = aws_eks_cluster.my_cluster.name
  node_role_arn   = aws_iam_role.node_role.arn
  subnet_ids      = aws_subnet.my_subnets[*].id

  scaling_config {
    desired_size = 3
    max_size     = 5
    min_size     = 1
  }
}

Subnet-lər müxtəlif zonalarda olduğu üçün node group da zonalar arasında paylanır: bir zona sıradan çıxdıqda həm control plane, həm də qalan worker node-lar işləməyə davam edir.

Klasterin özünün ayaqda qalması hələ tətbiqin ayaqda qalması demək deyil. Pod-ların bir zonada toplanmaması üçün topologySpreadConstraints, kritik xidmətlər üçün isə PodDisruptionBudget təyin edin — bunlar Terraform-un yox, Kubernetes manifest-lərinin işidir.
Klaster resursları Terraform-dadır, amma klaster daxilindəki state (PersistentVolume, etcd-dəki obyektlər) yox. Namespace və manifest-lərin bərpası üçün Velero kimi ayrıca backup həlli lazımdır — terraform apply tək başına klasteri əvvəlki vəziyyətinə qaytarmır.

6 · Əməli qaydalar

a. DR planını müntəzəm sına

Sınanmamış DR planı plan deyil, ümiddir. Kəsintiləri süni şəkildə modelləşdirin: əsas region-u söndürün, failover-in işlədiyini, backup-dan bərpanın tamamlandığını və failback-in problemsiz olduğunu yoxlayın. Bərpa vaxtını ölçün və elan etdiyiniz RTO ilə müqayisə edin.

b. Backup prosesini avtomatlaşdır

Backup-ı əl ilə aparmaq insan səhvinə açıq qapıdır. Bulud-nativ vasitələr və Terraform ilə avtomatlaşdırılmış müntəzəm backup həm riski azaldır, həm də bərpa anında ən yeni datanın mövcudluğunu təmin edir.

c. Xərcə nəzarət et

Çox-region DR bahalıdır — ikinci region-da işləyən boş sərvətlər aylıq hesabı ikiqat edə bilər. AWS Budgets və ya Azure Cost Management ilə DR xərcini ayrıca izləyin.

DR modeliEhtiyat mühitRTONisbi xərc
Backup & restoreYalnız backup saxlanırSaatlarƏn aşağı
Pilot lightYalnız data qatı işləyirOnlarla dəqiqəAşağı
Warm standbyKiçik ölçüdə tam nüsxəDəqiqələrOrta
Active-activeHər iki region tam yükləSaniyələrƏn yüksək
Bu dörd model arasında seçim tamamilə RTO/RPO tələbindən asılıdır. Əksər dev və daxili sistemlər üçün "backup & restore" kifayətdir; "active-active" yalnız kəsintinin dəqiqəsi ciddi zərər gətirən sistemlərə lazımdır.
AI ilə iş: DR konfiqurasiyası soruşarkən RTO və RPO rəqəmlərinizi prompt-a daxil edin — "RPO 15 dəqiqə, RTO 1 saat olan iki region-lu AWS quruluşu". Rəqəmlər olmadan model adətən ən bahalı active-active variantı təklif edir. Yaradılan planı həmişə terraform plan ilə yoxlayın: DR resursları çox vaxt gözlənilməz xərc gətirir.

7 · Yadda saxla

  • DR üç sütun üzərində dayanır: yüksək əlçatanlıq, müntəzəm backup və işlək failover/failback mexanizmi.
  • Çox-region quruluş alias-lı provider blokları ilə qurulur; AMI kimi region-a bağlı dəyərləri sabit yazmaq yox, dinamik tapmaq lazımdır.
  • Route 53 failover routing sağlamlıq yoxlamasına əsaslanır, lakin DNS TTL keçidi ləngidir — RTO hesabında bunu nəzərə alın.
  • Backup-ı backup_retention_period və S3 lifecycle qaydaları ilə avtomatlaşdırın; Terraform-u snapshot zamanlayıcısı kimi işlətməyin.
  • Kubernetes-də çox-AZ klaster infrastrukturu qoruyur, klaster daxilindəki datanı yox — Velero kimi ayrıca backup həlli lazımdır.
  • Sınanmamış DR planı işləmir: kəsintini süni modelləşdirin, bərpa vaxtını ölçün, RTO/RPO ilə tutuşdurun.
