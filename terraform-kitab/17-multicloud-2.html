Multi-Cloud — Praktik Nümunələr

DPE-07 · Data Platform & Engineering Bootcamp

Multi-cloud sadəcə «iki bulud işlətmək» deyil — bir kod bazasından fərqli provider-ləri idarə etmək bacarığıdır. Bu fəsildə bir Terraform konfiqurasiyası ilə AWS-də EC2, Azure-da isə virtual maşın quracaq, provider alias-larını, state idarəetməsini, kredensial təhlükəsizliyini və iki bulud arasında şəbəkə bağlantısını nəzərdən keçirəcəyik.

1 · Niyə multi-cloud?

Qərarın arxasındakı səbəblər

Təşkilatlar bir neçə bulud provider-ini eyni anda işlətməyi adətən aşağıdakı səbəblərdən seçirlər:

  • Vendor asılılığından qaçmaq — tək bir provider-in ekosisteminə bağlanmamaq həm texniki çeviklik, həm də müqavilə danışıqlarında mövqe verir.
  • Dayanıqlıq və ehtiyat — iş yükünü buludlar arasında bölmək bir provider-in tam kəsintisi zamanı xidmətin dayanmaması deməkdir.
  • Xərc optimallaşdırması — provider-lərin qiymət modelləri fərqlidir; hər iş yükü üçün ən sərfəli platformanı seçmək mümkün olur.
  • Hər provider-in güclü tərəfi — AWS compute və ekosistem genişliyində, Azure korporativ inteqrasiya və Active Directory tərəfdə, Google Cloud isə data və maşın öyrənməsi xidmətlərində önə çıxır.
Multi-cloud pulsuz deyil. Hər əlavə provider yeni IAM modeli, yeni şəbəkə anlayışları, yeni monitorinq alətləri və komandanın öyrənməli olduğu yeni bilik deməkdir. Konkret səbəb yoxdursa (uyğunluq tələbi, müştəri tələbi, real DR ehtiyacı) — bir buludda qalmaq çox vaxt daha doğru mühəndis qərarıdır.

2 · Əsas anlayışlar

a · Provider arxitekturası

Terraform-un multi-cloud işləməsini mümkün edən şey onun provider arxitekturasıdır. Hər bulud platformasının öz provider plugin-i var və o, platformanın API-si ilə danışır. Eyni konfiqurasiyada bir neçə provider təyin edərək fərqli platformalarda resurs yarada bilərsən — Terraform hər resursu hansı provider-in idarə etdiyini bilir.

b · Provider alias-ları

Multi-cloud və ya multi-region ssenarilərində eyni provider-in bir neçə nüsxəsi lazım olur: məsələn, biri us-west-2, digəri eu-north-1 üçün. Terraform bunu alias mexanizmi ilə həll edir: hər nüsxəyə ad verirsən və resursda provider = aws.<alias> yazaraq hansı nüsxənin işlədiləcəyini göstərirsən.

3 · Nümunə: AWS və Azure birlikdə

Addım 1 · Hər iki provider-i təyin et

Bir konfiqurasiyada həm AWS, həm Azure resurslarını idarə edəcəyik. Əvvəlcə provider blokları:

provider "aws" {
  region = "us-west-2"
  alias  = "aws_us_west"
}

provider "azurerm" {
  features {}
  alias = "azure_west_us"
}

Burada AWS provider-i US-West regionuna, Azure provider-i isə Azure-un West US bölgəsindəki resurslar üçün qurulub. features {} bloku azurerm provider-i üçün məcburidir — boş olsa belə yazılmalıdır.

Alias təyin edəndə həmin provider artıq standart provider olmur. Yəni hər resurs blokunda provider = aws.aws_us_west yazmalısan. Əgər resursların çoxu bir konfiqurasiyadan istifadə edirsə, onu alias-sız (standart) saxla, yalnız istisnalar üçün alias yarat.

Addım 2 · AWS-də EC2 instance

resource "aws_instance" "web_server_aws" {
  provider      = aws.aws_us_west
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    Name = "WebServer-AWS"
  }
}

Bu blok AWS-in US-West regionunda sadə bir EC2 instance yaradır. Diqqət et: provider arqumenti resursu konkret provider nüsxəsinə bağlayır.

Addım 3 · Azure-da virtual maşın

Azure tərəfdə virtual maşın tək resurs deyil — əvvəlcə resource group, virtual şəbəkə və şəbəkə interfeysi lazımdır. Bu, Azure-un resurs modelinin AWS-dən fərqləndiyi yerlərdən biridir.

resource "azurerm_resource_group" "my_rg" {
  provider = azurerm.azure_west_us
  name     = "myResourceGroup"
  location = "West US"
}

resource "azurerm_virtual_network" "my_vnet" {
  provider            = azurerm.azure_west_us
  name                = "myVNet"
  address_space       = ["10.0.0.0/16"]
  location            = azurerm_resource_group.my_rg.location
  resource_group_name = azurerm_resource_group.my_rg.name
}

resource "azurerm_subnet" "my_subnet" {
  provider             = azurerm.azure_west_us
  name                 = "internal"
  resource_group_name  = azurerm_resource_group.my_rg.name
  virtual_network_name = azurerm_virtual_network.my_vnet.name
  address_prefixes     = ["10.0.1.0/24"]
}

resource "azurerm_network_interface" "my_nic" {
  provider            = azurerm.azure_west_us
  name                = "myNIC"
  location            = azurerm_resource_group.my_rg.location
  resource_group_name = azurerm_resource_group.my_rg.name

  ip_configuration {
    name                          = "myNICConfig"
    subnet_id                     = azurerm_subnet.my_subnet.id
    private_ip_address_allocation = "Dynamic"
  }
}

resource "azurerm_linux_virtual_machine" "my_vm" {
  provider              = azurerm.azure_west_us
  name                  = "myLinuxVM"
  location              = azurerm_resource_group.my_rg.location
  resource_group_name   = azurerm_resource_group.my_rg.name
  network_interface_ids = [azurerm_network_interface.my_nic.id]
  size                  = "Standard_DS1_v2"
  admin_username        = "adminuser"
  admin_password        = var.vm_admin_password

  os_disk {
    caching              = "ReadWrite"
    storage_account_type = "Standard_LRS"
  }
}

Nümunədə ardıcıllıqla resource group, virtual şəbəkə, subnet, şəbəkə interfeysi və nəhayət Linux virtual maşını yaradılır. Bu, Terraform-un AWS resursları ilə yanaşı Azure resurslarını da eyni iş axınında idarə edə bildiyini göstərir.

Mənbə nümunədə parol birbaşa kodda (admin_password = "P@ssw0rd123!") yazılmışdı — bunu heç vaxt etmə. Parol həm git tarixçəsinə, həm də state faylına düşür. Yuxarıdakı variantda o, dəyişənə köçürülüb; daha yaxşı yanaşma isə paroldan tamamilə imtina edib SSH açarı işlətməkdir (admin_ssh_key bloku) və disable_password_authentication = true qoymaqdır.
Mənbə mətnindəki azurerm_virtual_network.my_vnet.subnets[0].id ifadəsi işləmir — Azure provider-də subnet ayrıca resursdur. Yuxarıda ona görə azurerm_subnet resursu əlavə olunub və NIC ona istinad edir.

Addım 4 · Nəticələri output kimi vermək

İki buludda nə yaradıldığını görmək üçün hər iki maşının ünvanını output kimi çıxaraq:

output "aws_instance_public_ip" {
  value = aws_instance.web_server_aws.public_ip
}

output "azure_vm_public_ip" {
  value = azurerm_linux_virtual_machine.my_vm.public_ip_address
}

Addım 5 · Tətbiq et

terraform init   # provider-ləri yüklə
terraform plan   # icra planını nəzərdən keçir
terraform apply  # hər iki buludda resursları yarat

Tək bir apply əmri həm AWS, həm də Azure tərəfdə resursları yaradır. Terraform asılılıq qrafını qurarkən provider sərhədini nəzərə almır — resurslar arasındakı istinadlara baxır, ona görə də iki buludda paralel işləyə bilir.

4 · Multi-cloud resurslarının idarə olunması

a · State-in idarə edilməsi

Multi-cloud mühitdə state-in düzgün saxlanması daha da kritikdir. Remote backend (S3, Azure Blob Storage və ya Google Cloud Storage) state faylını mərkəzləşdirir, komanda işini mümkün edir və eyni anda iki nəfərin apply etməsinin qarşısını alır.

terraform {
  backend "azurerm" {
    storage_account_name = "mystorageaccount"
    container_name       = "tfstate"
    key                  = "terraform.tfstate"
  }
}

Bu konfiqurasiya state faylını Azure Blob Storage konteynerində saxlayır — yəni fayl lokal maşında deyil, hamının çata bildiyi mərkəzi yerdə olur.

Backend yalnız bir dənə ola bilər. Yəni AWS və Azure resursları eyni konfiqurasiyadadırsa, state hansısa birində saxlanacaq. Praktikada daha yaxşı yanaşma budur: hər bulud üçün ayrı state (ayrı qovluq və ya workspace), aralarındakı əlaqə isə terraform_remote_state data source-u ilə qurulur. Belədə bir buludda edilən dəyişiklik digərinin state-ini riskə atmır.

b · Kredensialların təhlükəsiz idarəsi

Bir neçə buludun açarını eyni anda saxlamaq təhlükəsizlik riskini artırır. Kredensialları heç vaxt konfiqurasiyaya yazma — mühit dəyişənlərindən və ya secret saxlama alətlərindən (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) istifadə et.

export AWS_ACCESS_KEY_ID="your-aws-access-key"
export AWS_SECRET_ACCESS_KEY="your-aws-secret-key"

export ARM_CLIENT_ID="your-azure-client-id"
export ARM_CLIENT_SECRET="your-azure-client-secret"
export ARM_SUBSCRIPTION_ID="your-azure-subscription-id"
export ARM_TENANT_ID="your-azure-tenant-id"

Terraform provider bloklarını icra edərkən bu dəyişənləri avtomatik oxuyur — konfiqurasiyada heç nə yazmaq lazım gəlmir.

CI/CD-də statik açar yerinə qısamüddətli identifikasiyaya keç: GitLab/GitHub OIDC ilə AWS-də AssumeRoleWithWebIdentity, Azure-da isə Workload Identity Federation işlədilir. Belədə pipeline-da saxlanacaq uzunömürlü secret ümumiyyətlə qalmır.

5 · Şəbəkə: buludlar necə danışır

İki bulud arasında site-to-site VPN

Fərqli buludlardakı resursların bir-biri ilə təhlükəsiz əlaqəsi multi-cloud-un ən çətin hissəsidir. Ən çox işlədilən həll AWS ilə Azure arasında site-to-site VPN tunelidir.

Addım 1 — AWS tərəfdə Virtual Private Gateway:

resource "aws_vpn_gateway" "my_vgw" {
  vpc_id = aws_vpc.my_vpc.id
}

Addım 2 — Azure tərəfdə VPN Gateway:

resource "azurerm_virtual_network_gateway" "azure_vpn_gw" {
  name                = "azure-vpn-gateway"
  location            = "West US"
  resource_group_name = azurerm_resource_group.my_rg.name
  type                = "Vpn"
  vpn_type            = "RouteBased"
  sku                 = "Standard"
}

Addım 3 — tuneli qur: hər iki tərəfdə gateway hazır olandan sonra AWS-də aws_customer_gateway və aws_vpn_connection resursları ilə bağlantı yaradılır. Azure gateway-in public IP-si AWS-də customer gateway kimi, AWS tərəfin IP-si isə Azure-da local network gateway kimi göstərilir — yəni hər bulud digərini «xarici sayt» kimi tanıyır.

Şəbəkə planlaşdırmasında ən çox təkrarlanan səhv CIDR üst-üstə düşməsidir. AWS VPC və Azure VNet fərqli diapazonlarda olmalıdır (məsələn, AWS 10.40.0.0/16, Azure 10.50.0.0/16). Üst-üstə düşən şəbəkələr arasında routing qurmaq mümkün deyil, düzəltmək üçün isə bütün şəbəkəni yenidən yaratmaq lazım gəlir.
VPN gateway-lər hər iki buludda saatlıq ödənişlidir və data transferi ayrıca hesablanır. Yüksək trafikli bağlantılar üçün VPN əvəzinə xüsusi xətt (AWS Direct Connect + Azure ExpressRoute) daha stabil və uzun perspektivdə daha sərfəli ola bilər.

6 · Best practice-lər

a · Ardıcıl tag siyasəti

Bütün provider-lərdə resurslar eyni məntiqlə tag-lanmalıdır. Bu, xərc təhlili, monitorinq və uyğunluq yoxlamalarını mümkün edir — əks halda hansı resursun hansı layihəyə aid olduğunu heç bir hesabatda görə bilməzsən.

resource "aws_instance" "web_server" {
  tags = {
    Environment = "production"
    Project     = "multi-cloud"
  }
}

resource "azurerm_linux_virtual_machine" "my_vm" {
  tags = {
    Environment = "production"
    Project     = "multi-cloud"
  }
}
Tag dəyərlərini locals blokunda bir yerdə saxla və hər resursda merge(local.common_tags, { ... }) ilə birləşdir. Belədə tag siyasəti dəyişəndə on beş yerdə deyil, bir yerdə düzəliş edirsən.

b · Modul strukturu

Böyük multi-cloud mühitlərdə kodu modullara böl. Hər bulud üçün ayrı modul (məsələn, modules/aws-network, modules/azure-network) təkrarçılığı azaldır və konfiqurasiyanı oxunaqlı saxlayır. Ortaq interfeys — eyni adlı dəyişən və output-lar — modulların bir-birini əvəz edə bilməsini asanlaşdırır.

AI köməkçisi ilə işləyəndə diqqətli ol: Copilot AWS sintaksisini Azure resursuna, Azure sintaksisini isə AWS resursuna qarışdırmağa meyillidir (məsələn, azurerm resursunda tags əvəzinə AWS üslubunda blok təklif etmək). Hər təklifi terraform validate və provider sənədləri ilə yoxla.

7 · Yadda saxla

  • Multi-cloud-un texniki açarı provider alias-larıdır: eyni konfiqurasiyada bir neçə bulud və region nüsxəsi paralel idarə olunur.
  • Alias təyin edilmiş provider standart olmaqdan çıxır — hər resursda provider = <ad>.<alias> göstərilməlidir.
  • Bir konfiqurasiyada yalnız bir backend ola bilər; praktikada hər bulud üçün ayrı state saxlayıb aralarında terraform_remote_state ilə əlaqə qurmaq daha təhlükəsizdir.
  • Kredensiallar kodda deyil, mühit dəyişənlərində və ya secret saxlama sistemində olmalıdır; CI/CD-də isə OIDC ilə qısamüddətli açarlara keç.
  • Şəbəkəni əvvəlcədən planlaşdır: üst-üstə düşən CIDR diapazonları buludlar arası bağlantını tamamilə mümkünsüz edir.
