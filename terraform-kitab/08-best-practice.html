Best Practice və Qabaqcıl Üsullar

DPE-07 · Data Platform & Engineering Bootcamp

İşləyən Terraform kodu yazmaq bir məsələdir, il yarımdan sonra da başa düşülən və təhlükəsiz qalan kod yazmaq isə tamam başqa. Bu fəsildə komanda şəraitində sınaqdan çıxmış qaydaları — modullaşdırma, remote backend, versiya nəzarəti — və gündəlik işi asanlaşdıran qabaqcıl üsulları: secret idarəçiliyi, Terraform Cloud, import, workspace və depends_on nəzərdən keçirəcəyik.

1 · Kodu modullaşdırın

Böyüyən infrastruktur, bölünən kod

İnfrastruktur böyüdükcə tək bir main.tf faylı idarəolunmaz hala gəlir. Modullar kodu təkrar istifadə edilə bilən, məsuliyyəti aydın hissələrə bölür.

Yaxşı modulun üç əlaməti

  • Tək məsuliyyət prinsipi: hər modul bir komponentə cavabdeh olsun — VPC, EC2, RDS ayrı-ayrı. Bu, modulu həm fokuslu, həm də başqa layihədə istifadəyə yararlı saxlayır.
  • Input və output işlədin: kənardan gələn dəyərlər üçün variable, modullar arasında məlumat ötürmək üçün output təyin edin. Modul öz daxilində sərt kodlanmış dəyər saxlamamalıdır.
  • Versiya nəzarətində saxlayın: modulları Git repository-də və ya Terraform Registry-də yerləşdirin ki, versiyalansın və komandalar arasında rahat paylaşılsın.

Nümunə quruluş

/modules
  /vpc
    main.tf
    variables.tf
    outputs.tf
  /ec2
    main.tf
    variables.tf
    outputs.tf

Bu quruluş modulun layihələr arasında təkrar istifadəsini asanlaşdırır, kod dublikasiyasını azaldır və mühitlər arasında ardıcıllığı təmin edir.

Modula istinad edərkən versiyanı sabitləyin. ref=v1.2.0 olmadan modul repository-sindəki hər dəyişiklik növbəti terraform init zamanı sizin infrastrukturunuza sızır: 
module "vpc" {
  source = "git::https://github.com/org/tf-modules.git//vpc?ref=v1.2.0"
  cidr   = "10.40.0.0/16"
}

2 · Remote state backend işlədin

State-i lokal saxlamayın

4-cü fəsildə gördüyümüz kimi, state faylını uzaq yaddaşda saxlamaq komanda işində vacibdir. Amazon S3, Azure Blob Storage və ya Terraform Cloud kimi backend state-in bütün komanda üzvləri üçün eyni olmasını təmin edir, üstəlik şifrələmə və kilidləmə (locking) əlavə edir.

Nümunə: S3 backend konfiqurasiyası

terraform {
  backend "s3" {
    bucket  = "my-terraform-state"
    key     = "global/s3/terraform.tfstate"
    region  = "us-west-1"
    encrypt = true
  }
}

Remote backend state korlanmasının qarşısını alır, eyni anda iki nəfərin apply işlətməsini əngəlləyir və əlavə təhlükəsizlik qatı verir.

State faylı açıq mətndir və orada verilənlər bazası parolları, private key-lər kimi həssas dəyərlər saxlanılır. Bucket-i mütləq şifrələyin (encrypt = true), public girişi bağlayın və versiyalamanı aktivləşdirin ki, səhvən silinən state-i bərpa edə biləsiniz.

3 · Versiya nəzarəti və teqləmə

Kodun tarixçəsi olmalıdır

Terraform konfiqurasiyalarınızı və modullarınızı həmişə versiya nəzarət sistemində (Git) saxlayın. Bu, dəyişiklikləri izləməyə, komanda ilə birgə işləməyə və nəsə səhv gedəndə əvvəlki versiyaya qayıtmağa imkan verir.

Əsas qaydalar

  • Tez-tez commit edin: kiçik, mənalı commit mesajları ilə addım-addım irəliləyin.
  • Branch işlədin: dev, staging və prod mühitlərini ayrı branch-larla və ya ayrı qovluqlarla bölün.
  • Versiyaları teqləyin: infrastruktur kodunun buraxılışlarını teqləyin — geri qayıtmaq lazım olanda hansı vəziyyətə qayıdacağınız aydın olsun.
git add .
git commit -m "VPC üçün Terraform konfiqurasiyası əlavə edildi"
git tag v1.0.0
git push --tags

Teqləmə sayəsində hansı infrastruktur versiyasının prod-da işlədiyini müəyyən etmək asanlaşır.

.gitignore faylına mütləq bunları əlavə edin: .terraform/, *.tfstate, *.tfstate.backup, *.tfvars (həssas dəyərlər olduqda), crash.log. .terraform.lock.hcl isə commit edilməlidir — o, provider versiyalarını bütün komanda üçün sabit saxlayır.

4 · .terraformignore faylı

Nəyin yüklənməyəcəyini müəyyən edin

.gitignore-a bənzər şəkildə, .terraformignore faylı Terraform Cloud kimi remote backend-lərə hansı faylların göndərilməyəcəyini təyin edir.

# .terraformignore
*.tfstate
*.log
.secret/*

Bu, həssas və ya lazımsız faylların backend-ə yüklənməsinin qarşısını alır — həm təhlükəsizlik, həm də yükləmə sürəti baxımından faydalıdır.

5 · Secret idarəçiliyi

Həssas məlumatı koda yazmayın

API açarları, parollar və SSH key-lər Terraform-da idarəsi ən çətin hissədir. Əsas qayda sadədir: bu dəyərlər heç vaxt konfiqurasiya faylında sərt kodlanmamalıdır. Bir neçə təhlükəsiz yol var.

1. Mühit dəyişənləri

Terraform TF_VAR_ prefiksi ilə başlayan mühit dəyişənlərini avtomatik olaraq eyniadlı variable-a bağlayır:

export TF_VAR_db_password="mysecretpassword"
terraform apply

2. Terraform Cloud / Enterprise

Terraform Cloud həssas dəyərləri workspace dəyişəni kimi saxlamağa imkan verir — onlar şifrələnir və log-da göstərilmir.

3. Secret idarəetmə alətləri

HashiCorp Vault, AWS Secrets Manager və ya Azure Key Vault ilə inteqrasiya edərək secret-ləri işləmə anında konfiqurasiyaya çəkmək olar.

# Parolu AWS Secrets Manager-dən oxuyuruq
data "aws_secretsmanager_secret_version" "db_password" {
  secret_id = "my-db-password"
}

resource "aws_db_instance" "my_db" {
  allocated_storage = 10
  engine            = "mysql"
  instance_class    = "db.t2.micro"
  name              = "mydb"
  username          = "admin"

  # Parol koda yazılmır, secret store-dan gəlir
  password = data.aws_secretsmanager_secret_version.db_password.secret_string
}

Burada verilənlər bazası parolu konfiqurasiyada sərt kodlanmaq əvəzinə AWS Secrets Manager-dən təhlükəsiz şəkildə oxunur.

Secret-i data source ilə oxumaq onun state faylına düşməsinin qarşısını almır — Terraform oxuduğu hər dəyəri state-də saxlayır. Ona görə remote state şifrələməsi və giriş məhdudiyyəti bu yanaşmanın ayrılmaz hissəsidir, alternativi deyil.

Yanaşmaların müqayisəsi

6 · Terraform Cloud ilə uzaq icra

Əmrləri lokal maşında işlətməmək

Terraform Cloud plan və apply əmrlərini sizin noutbukunuzda deyil, mərkəzi mühitdə icra etməyə imkan verir. Böyük komandalar üçün bu, infrastruktur idarəçiliyini bir yerdə toplayır.

Terraform Cloud-un verdikləri:

  • Uzaq state idarəçiliyi: state faylı avtomatik saxlanılır və kilidlənir.
  • Uzaq plan və apply: əmrlər eyni mühitdə işləyir — kimin hansı Terraform versiyası ilə işlətdiyi fərq etmir.
  • Birgə iş vasitələri: bir neçə komanda üzvü eyni infrastruktur üzərində nizamlı şəkildə işləyə bilir.

Nümunə: backend kimi Terraform Cloud

terraform {
  backend "remote" {
    organization = "my-org"

    workspaces {
      name = "my-workspace"
    }
  }
}

Bu quruluşla CI/CD pipeline-ları inteqrasiya etmək, plan-ların tətbiqini avtomatlaşdırmaq və təsdiq (approval) mərhələləri qurmaq da mümkün olur.

7 · terraform import — mövcud resursları idarəyə almaq

Əl ilə yaradılmış resurslar

Bulud konsolundan əl ilə yaradılmış resurslar var və siz onları bundan sonra Terraform ilə idarə etmək istəyirsinizsə, terraform import əmri bu resursu state-ə əlavə edir.

terraform import aws_instance.my_instance i-0abcd1234
  • Bu nümunədə i-0abcd1234 ID-li EC2 instansı Terraform state-inə import edilir.
  • Import-dan sonra həmin resursu konfiqurasiyada (məsələn main.tf-də) təsvir etməlisiniz — əks halda Terraform növbəti plan-da onu silmək istəyəcək.
Doğru ardıcıllıq: əvvəlcə boş resource bloku yazın, sonra import edin, sonra terraform plan işlədin və plan tamamilə boş olana qədər konfiqurasiyanı faktiki resursa uyğunlaşdırın. Terraform 1.5+ versiyasında bunu import bloku ilə deklarativ etmək və -generate-config-out ilə kodu avtomatik yaratmaq da olar.

8 · Workspace ilə çoxlu mühit

Bir konfiqurasiya, bir neçə mühit

Terraform workspace-ləri eyni konfiqurasiyadan bir neçə mühiti (dev, staging, prod) idarə etməyə imkan verir — 5-ci fəsildə baxdığımız kimi.

1. Workspace yaratmaq və keçid etmək

terraform workspace new dev
terraform workspace new prod
terraform workspace select dev

2. Resurs adlarını mühitə görə fərqləndirmək

resource "aws_instance" "my_instance" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    # Ad avtomatik olaraq aktiv workspace-in adını alır
    Name = "my-instance-${terraform.workspace}"
  }
}

Workspace sayəsində konfiqurasiya fayllarını təkrarlamadan fərqli mühitləri idarə etmək olur.

Workspace-lər eyni backend və eyni provider konfiqurasiyasını paylaşır. Mühitlər fərqli AWS account-larda yerləşirsə və ya tamamilə fərqli girişə malikdirsə, workspace əvəzinə ayrı qovluq və ayrı backend quruluşu daha təhlükəsizdir.

9 · depends_on ilə mürəkkəb asılılıqlar

Terraform-un görmədiyi əlaqələr

Terraform resurslar arasındakı asılılıqları istinadlara baxaraq özü müəyyən edir. Amma bəzi hallarda resurslar arasında birbaşa istinad olmur, halbuki sıra vacibdir. Belə vaxtlarda depends_on arqumenti ilə asılılığı açıq şəkildə bildirmək lazımdır.

resource "aws_instance" "my_instance" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  # Bucket bu instansdan əvvəl yaradılsın
  depends_on = [aws_s3_bucket.my_bucket]
}

resource "aws_s3_bucket" "my_bucket" {
  bucket = "my-bucket"
}

Bu nümunədə iki resurs arasında heç bir birbaşa əlaqə olmasa da, Terraform S3 bucket-i EC2 instansından əvvəl yaradacaq.

depends_on-u yalnız zərurət olanda işlədin. Hər yerə əlavə etmək asılılıq qrafını lazımsız yerə sıxlaşdırır, paralel icranı azaldır və plan-ı yavaşladır. Mümkün olduqca istinad (aws_s3_bucket.my_bucket.id) işlədin — Terraform asılılığı özü çıxarsın.

10 · Yadda saxla

  • Modul = tək məsuliyyət: hər modul bir komponentə cavabdeh olsun, input/output ilə ünsiyyət qursun və versiyalanmış mənbədən çağırılsın.
  • Remote backend şərtdir: komanda ilə işləyirsinizsə, lokal state ilk gündən problemdir. Şifrələmə, kilidləmə və versiyalama üçlüyünü aktivləşdirin.
  • Secret koda yazılmır: TF_VAR_, Terraform Cloud dəyişəni və ya Vault/Secrets Manager — üçündən biri, amma heç vaxt .tf faylında açıq mətn.
  • Import-dan sonra kod yazılır: resursu state-ə gətirmək yarım işdir; konfiqurasiyada təsvir etməsəniz, Terraform onu silməyə çalışacaq.
  • depends_on son çarədir: asılılığı istinadla ifadə etmək mümkündürsə, elə edin. Açıq depends_on yalnız gizli əlaqələr üçündür.
