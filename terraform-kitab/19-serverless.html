Serverless — Lambda və Azure Functions

DPE-07 · Data Platform & Engineering Bootcamp

Serverless yanaşmada sən yalnız kodu yazırsan — serveri ayırmaq, ölçüləndirmək və yamaqlamaq cloud provider-in işidir. Bu fəsildə Terraform ilə AWS Lambda funksiyasını yaradıb API Gateway-ə bağlayacağıq, sonra eyni işi Azure Functions üçün edəcəyik. Sonda serverless infrastrukturunu böyük miqyasda necə səliqəli saxlamağın qaydalarına baxacağıq.

1 · Serverless nədir

Server yoxdur demək deyil — sənin serverin yoxdur demək

Serverless — cloud modelidir ki, orada resursların ayrılmasını provider dinamik idarə edir. Sən EC2 instance seçmirsən, autoscaling group qurmursan, OS yeniləmirsən. Sən sadəcə bir function yazırsan və onun hansı hadisədə işə düşəcəyini deyirsən.

  • Avtomatik ölçüləndirmə — bir sorğu gəlsə bir nüsxə, min sorğu gəlsə min nüsxə işə düşür. Sən heç nə etmirsən.
  • Xərc səmərəliliyi — yalnız kodun işlədiyi millisaniyələrə görə ödəyirsən. Boş dayanan server üçün pul getmir.
  • Az əməliyyat yükü — provisioning, scaling və patching provider-in üzərindədir; komandan tətbiq məntiqinə fokuslanır.

Əsas platformalar

  • AWS Lambda
  • Azure Functions
  • Google Cloud Functions
Serverless hər iş üçün deyil. Uzun sürən (dəqiqələrlə) hesablamalar, davamlı açıq bağlantı tələb edən servislər və çox aşağı gecikmə istəyən yüklər üçün konteyner və ya VM daha uyğun ola bilər. Serverless-in güclü yeri — hadisəyə cavab verən, qısa ömürlü işlərdir.

2 · Serverless memarlığın anlayışları

a. Functions as a Service (FaaS)

Lambda, Azure Functions və Cloud Functions kimi platformalar sənə ayrı-ayrı funksiyaları deploy etməyə imkan verir. Hər function bir trigger-ə cavab olaraq icra olunur. Bu modelə Functions as a Service (FaaS) deyilir.

b. Hadisə yönümlü (event-driven) memarlıq

Serverless function-lar adətən bu hadisələrlə işə düşür:

Data platformasında ən çox rast gəlinən nümunə: S3-ə fayl düşür → Lambda işə düşür → faylı validasiya edib Glue/Redshift-ə ötürür. Bu zəncirin hər halqasını Terraform ilə kod kimi saxlamaq olar.

3 · Terraform ilə AWS Lambda deploy etmək

Addım 1 — AWS provider

Əvvəlcə provider-i və region-u təyin edirik. Function bu region-da yaradılacaq.

provider "aws" {
  region = "us-west-2"
}

Addım 2 — Lambda function

Lambda kodunu ZIP arxivinə yığıb ötürürük. handler — kodun giriş nöqtəsi, yəni fayl_adı.funksiya_adı.

resource "aws_lambda_function" "my_lambda" {
  function_name = "my-lambda-function"
  handler       = "lambda_function.lambda_handler"
  runtime       = "python3.8"
  role          = aws_iam_role.lambda_role.arn

  # Lambda kodunu saxlayan zip fayl
  filename         = "lambda_function.zip"
  # Zip dəyişəndə Terraform function-u yenidən deploy etsin
  source_code_hash = filebase64sha256("lambda_function.zip")
}

Bu nümunədə:

  • Function Python 3.8 ilə yazılıb və lambda_function.zip arxivinə yığılıb.
  • handler giriş nöqtəsini göstərir — lambda_function faylındakı lambda_handler funksiyası.
  • role — function-un icra üçün lazım olan icazələrini verən IAM role.
  • source_code_hash olmasa, sən zip-i dəyişsən də Terraform «dəyişiklik yoxdur» deyəcək. Bu sətri unutma.
Runtime versiyaları köhnəlir. python3.8 nümunə üçün yazılıb; canlı işdə AWS-in hazırda dəstəklədiyi versiyanı seç, çünki dəstəkdən çıxan runtime-da function-u yeniləmək mümkün olmur.

Addım 3 — Lambda üçün IAM role

Function-un öz kimliyi olmalıdır. assume_role_policy bu role-u kimin götürə biləcəyini deyir — burada Lambda servisi.

resource "aws_iam_role" "lambda_role" {
  name = "lambda-execution-role"

  assume_role_policy = <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Action": "sts:AssumeRole",
      "Effect": "Allow",
      "Principal": {
        "Service": "lambda.amazonaws.com"
      }
    }
  ]
}
EOF
}

İndi role-a icazə əlavə edirik — function loqlarını CloudWatch Logs-a yaza bilsin:

resource "aws_iam_role_policy" "lambda_policy" {
  role = aws_iam_role.lambda_role.id

  policy = <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "logs:CreateLogGroup",
      "Resource": "arn:aws:logs:*:*:*"
    },
    {
      "Effect": "Allow",
      "Action": "logs:CreateLogStream",
      "Resource": "arn:aws:logs:*:*:*"
    },
    {
      "Effect": "Allow",
      "Action": "logs:PutLogEvents",
      "Resource": "arn:aws:logs:*:*:*"
    }
  ]
}
EOF
}
Bu üç icazə — CreateLogGroup, CreateLogStream, PutLogEvents — Lambda-nın minimum dəsti sayılır. Onlarsız function işləyər, amma loq görməzsən və xətanı tapmaq mümkün olmaz. Function başqa servisə (S3, DynamoDB) müraciət edirsə, o icazələri də ayrıca əlavə et.

4 · Lambda-nı API Gateway ilə birləşdirmək

Function-u HTTP üzərindən əlçatan etmək

Lambda özü URL ilə açıq deyil. Ona HTTP qapısı lazımdır — API Gateway. Ardıcıllıq belədir: REST API → resource (yol) → method (HTTP fel) → invoke icazəsi.

# 1) REST API özü
resource "aws_api_gateway_rest_api" "my_api" {
  name        = "My API"
  description = "Lambda function üçün API Gateway"
}

# 2) Yol: /lambda
resource "aws_api_gateway_resource" "lambda_resource" {
  rest_api_id = aws_api_gateway_rest_api.my_api.id
  parent_id   = aws_api_gateway_rest_api.my_api.root_resource_id
  path_part   = "lambda"
}

# 3) Bu yolda GET metodu
resource "aws_api_gateway_method" "get_lambda" {
  rest_api_id   = aws_api_gateway_rest_api.my_api.id
  resource_id   = aws_api_gateway_resource.lambda_resource.id
  http_method   = "GET"
  authorization = "NONE"
}

# 4) API Gateway-ə function-u çağırmaq icazəsi
resource "aws_lambda_permission" "api_gateway_invoke" {
  statement_id  = "AllowAPIGatewayInvoke"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.my_lambda.arn
  principal     = "apigateway.amazonaws.com"
}

Bu konfiqurasiyada:

  • API Gateway-də GET metodu qurulub və o, Lambda function-u işə salır.
  • aws_lambda_permission resource-u olmadan API Gateway function-u çağıra bilməz — 403 alarsan. Bu, ən çox unudulan hissədir.
authorization = "NONE" API-ni internetə tam açıq qoyur. Öyrənmək üçün olar, amma prod-da mütləq IAM, Cognito authorizer və ya API key qoy.

Konfiqurasiyanı tətbiq etmək

terraform init
terraform plan
terraform apply

Nəticədə Lambda function yaranacaq, IAM role-u qoşulacaq və function API Gateway üzərindən əlçatan olacaq.

5 · Terraform ilə Azure Functions deploy etmək

Addım 1 — Azure provider

provider "azurerm" {
  features {}
}
features {} boş olsa da mütləqdir — azurerm provider-i onsuz işə düşmür.

Addım 2 — Function App və onun asılılıqları

Azure-da function tək başına yaşamır. Ona resource group, storage account və app service plan lazımdır.

# Bütün resursların yerləşdiyi qrup
resource "azurerm_resource_group" "example_rg" {
  name     = "example-resources"
  location = "West US"
}

# Function kodunu və vəziyyətini saxlayan storage
resource "azurerm_storage_account" "example_storage" {
  name                     = "examplestorageacct"
  resource_group_name      = azurerm_resource_group.example_rg.name
  location                 = azurerm_resource_group.example_rg.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
}

# Dynamic (Y1) plan = istifadəyə görə ödəniş, serverless rejim
resource "azurerm_app_service_plan" "example_plan" {
  name                = "example-appserviceplan"
  location            = azurerm_resource_group.example_rg.location
  resource_group_name = azurerm_resource_group.example_rg.name
  kind                = "FunctionApp"

  sku {
    tier = "Dynamic"
    size = "Y1"
  }
}

# Function App-ın özü
resource "azurerm_function_app" "example_function" {
  name                       = "examplefunction"
  location                   = azurerm_resource_group.example_rg.location
  resource_group_name        = azurerm_resource_group.example_rg.name
  app_service_plan_id        = azurerm_app_service_plan.example_plan.id
  storage_account_name       = azurerm_storage_account.example_storage.name
  storage_account_access_key = azurerm_storage_account.example_storage.primary_access_key
  os_type                    = "Linux"
  version                    = "~3"
}

Bu nümunədə:

  • Function App bir resource group, storage account və app service plan içində yaradılır.
  • Plan Dynamic/Y1 seçilib — bu, Azure-un «consumption» yəni serverless rejimidir: istifadə olunmayanda pul getmir.
  • Function App Linux üzərində işləyir və Azure Functions runtime-ın 3.x versiyasını istifadə edir.
storage_account_access_key state faylına açıq şəkildə düşür. Bu, remote state-i şifrələmək və girişi məhdudlaşdırmaq üçün ayrıca bir səbəbdir — 4-cü fəsildəki backend qaydalarını xatırla.

Deploy

terraform init
terraform plan
terraform apply

7 · Serverless infrastrukturu idarə etmək qaydaları

a. Function-lar üçün modul yaz

Bir-iki function-la problem yoxdur. Amma otuz function və üç mühit (dev, staging, prod) olanda kod təkrarı idarəolunmaz olur. Terraform modulu yaz: function adı, handler, runtime, environment dəyişənləri parametr olsun, IAM role və log group modulun içində yaransın.

module "ingest_function" {
  source        = "./modules/lambda"
  function_name = "ingest-events"
  handler       = "app.handler"
  runtime       = "python3.12"
  environment   = var.environment
}

b. Sirləri təhlükəsiz saxla

API açarları, baza parolları kimi həssas məlumatı heç vaxt Terraform koduna və ya environment variable-a açıq yazma. Cloud-un öz sirr idarəetmə vasitələrindən istifadə et — AWS Secrets Manager və ya Azure Key Vault. Function işə düşəndə sirri oradan oxusun; Terraform yalnız sirrin adını (ARN-i) bilsin.

Terraform koduna yazılan sirr iki yerdə qalır: git tarixçəsində və state faylında. İkisi də silinməsi çətin izdir. Kod yazılan anda düzgün etmək daha ucuzdur.

c. Loq saxlanma müddətini özün təyin et

AWS Lambda özü avtomatik log group yaradır və onun saxlanma müddəti sonsuzdur — yəni loq üçün əbədi ödəyirsən. Log group-u Terraform ilə əvvəlcədən yarat və retention_in_days qoy. Bunu növbəti fəsildə ətraflı görəcəyik.

d. Versiya və alias istifadə et

Function-un yeni versiyasını dərhal bütün trafikə vermək əvəzinə alias ilə mərhələli keçid et. Beləliklə problem çıxsa, geri qayıtmaq bir konfiqurasiya dəyişikliyi qədər asan olur.

8 · Yadda saxla

  • Serverless = kod + trigger + kimlik. Terraform-da hər function üçün bu üç hissəni birlikdə təsvir et; biri əskik olsa, function ya işə düşmür, ya da səssizcə xəta verir.
  • source_code_hash olmadan deploy işləmir — zip dəyişsə də Terraform fərqi görməz və köhnə kod işləməyə davam edər.
  • API Gateway → Lambda üçün aws_lambda_permission məcburidir. Ən çox rast gəlinən «403 Forbidden» səbəbi budur.
  • Azure-da serverless rejim plan seçimi ilə gəlir — Dynamic/Y1 olmasa, boş dayanan Function App üçün də ödəyirsən.
  • Sirlər Secrets Manager və ya Key Vault-da, kodda yox. Modul quruluşu isə function sayı artdıqca səni xilas edən yeganə şeydir.
