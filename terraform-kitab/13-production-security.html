Prod Mühitində Terraform və Təhlükəsizlik

DPE-07 · Data Platform & Engineering Bootcamp

Sınaq mühitində işləyən Terraform konfiqurasiyası prod mühitə çıxanda tamam başqa tələblərlə üzləşir: state faylı həssas məlumat daşıyır, bir neçə adam eyni infrastruktura toxunur, hər dəyişikliyin izi qalmalıdır. Bu fəsildə state-in təhlükəsiz saxlanmasından tutmuş RBAC, secret idarəetməsi, CI/CD avtomatlaşdırması və monitorinqə qədər prod mühit üçün lazım olan bütün təbəqələri nəzərdən keçiririk.

1 · Prod mühitin əsas çətinlikləri

Nə dəyişir?

Lokal maşında terraform apply yazmaqla prod mühitdə eyni əmri işə salmaq arasında böyük fərq var. Aşağıdakı beş sahə prod mühitdə mütləq həll olunmalıdır:

SahəProblemHəll istiqaməti
State idarəetməsiState faylı parol, IP, ARN kimi həssas dəyərləri açıq saxlayırŞifrələnmiş remote backend, məhdud giriş
TəhlükəsizlikKim nəyi dəyişə bilər — nəzarətsizdirRBAC, IAM policy, secret manager
Komanda işiİki nəfər eyni anda apply edir, state korlanırState locking + Git axını
AvtomatlaşdırmaƏl ilə apply — insan səhvi qaçılmazdırCI/CD pipeline, plan/apply ayrılması
Monitorinq və logNə dəyişdi, kim dəyişdi — bilinmirCloudWatch, CloudTrail, audit log
Yadda saxla: bu beş sahə bir-birindən asılıdır. Yalnız state-i şifrələyib RBAC qurmasan, şifrələmə çox az şey qazandırır — çünki state-ə girişi olan hər kəs həmin açarları oxuya bilər.

2 · Prod mühitdə state idarəetməsi

a. Remote state saxlanması

Terraform state faylı infrastrukturun mövcud vəziyyətini izləyir və hansı dəyişikliklərin tətbiq olunacağını məhz bu fayla əsasən hesablayır. Prod mühitdə state heç vaxt lokal fayl kimi qalmamalıdır — Amazon S3, Azure Blob Storage və ya Terraform Cloud kimi remote backend işlədilir. Remote backend komanda işi, versiyalama, locking və şifrələmə imkanı verir.

Nümunə: state-in S3-də saxlanması

terraform {
  backend "s3" {
    bucket         = "my-terraform-state-prod"
    key            = "global/s3/terraform.tfstate"
    region         = "us-west-1"
    encrypt        = true              # server-side şifrələmə
    dynamodb_table = "terraform-lock"  # state locking cədvəli
  }
}

Bu konfiqurasiyada:

  • State şifrələmə aktiv olan S3 bucket-də saxlanır.
  • DynamoDB cədvəli state locking üçün işlədilir — eyni anda bir neçə istifadəçinin state-i dəyişməsinin qarşısını alır.

b. Locking və versiyalama

State locking eyni vaxtda iki əməliyyatın state faylına toxunmasının qarşısını alır: istənilən anda yalnız bir Terraform icrası infrastrukturu dəyişə bilər. Prod mühitdə bu, race condition və konflikt riskini aradan qaldırır.

Versiyalama isə lazım gələndə əvvəlki state-ə qayıtmaq imkanı verir — səhv apply-dan və ya gözlənilməz nəticədən sonra bərpa yolu açıq qalır. Yuxarıdakı nümunədə DynamoDB locking-i, S3 bucket versiyalanması isə tarixçəni təmin edir.

Diqqət: S3 bucket-də versiyalamanı bucket səviyyəsində ayrıca aktivləşdirməlisən — encrypt = true avtomatik versiyalama gətirmir. Həmçinin bucket-i mütləq public access block ilə bağla; açıq state bucket-i infrastrukturun tam xəritəsini kənar adamlara verir.

3 · Təhlükəsizlik: RBAC və secret idarəetməsi

a. Rol əsaslı giriş nəzarəti (RBAC)

Prod mühitdə infrastruktura dəyişiklik tətbiq edə bilən adamların dairəsi məhdud olmalıdır. Bunu bulud provayderinin IAM policy-ləri ilə və ya Terraform Enterprise-ın daxili RBAC imkanları ilə qururuq.

Nümunə: Terraform istifadəçiləri üçün AWS IAM policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::my-terraform-state-prod/*"
    },
    {
      "Effect": "Allow",
      "Action": "dynamodb:*",
      "Resource": "arn:aws:dynamodb:us-west-1:123456789012:table/terraform-lock"
    }
  ]
}

Bu policy Terraform istifadəçisinə yalnız state saxlanan S3 bucket-i və locking üçün işlədilən DynamoDB cədvəli ilə işləmək icazəsi verir — nə artıq, nə əskik.

Təklif: plan və apply üçün ayrı rollar qur. Plan rolu yalnız oxuma (Describe*, Get*, List*) icazələri ilə işləsin, apply rolunu isə yalnız CI/CD-nin main branch job-u öz üzərinə götürə bilsin. Beləliklə pull request mərhələsində heç kim təsadüfən infrastrukturu dəyişə bilməz.

b. Secret idarəetməsi

API açarları, parollar və digər kredensiallar heç vaxt Terraform konfiqurasiyasına birbaşa yazılmamalıdır. Bunun əvəzinə AWS Secrets Manager, Azure Key Vault və ya HashiCorp Vault kimi secret idarəetmə sistemlərindən istifadə edilir.

Nümunə: AWS Secrets Manager-dən secret oxumaq

data "aws_secretsmanager_secret_version" "db_password" {
  secret_id = "my-database-password"
}

resource "aws_db_instance" "example" {
  allocated_storage = 20
  engine            = "mysql"
  instance_class    = "db.t2.micro"
  name              = "exampledb"
  username          = "admin"
  # parol kodda deyil — icra anında Secrets Manager-dən gəlir
  password = data.aws_secretsmanager_secret_version.db_password.secret_string
}

Burada baza parolu dinamik olaraq Secrets Manager-dən oxunur, yəni həssas məlumat Terraform kodunda və Git tarixçəsində qalmır.

Vacib incəlik: secret kodda görünmür, amma state faylına düşür. Terraform data source-un nəticəsini state-də saxlayır. Buna görə secret idarəetməsi remote state şifrələməsini əvəz etmir — ikisi birlikdə işləməlidir.

4 · Komanda işi və versiya nəzarəti

Terraform üçün Git axını

Prod mühitdə adətən bir neçə komanda eyni infrastruktur üzərində işləyir. Konfliktin qarşısını almaq və məsuliyyəti izləmək üçün Git remote backend və locking ilə birlikdə işlədilir. Tipik axın belədir:

  1. Feature branch yarat — hər infrastruktur dəyişikliyi üçün ayrı branch: 
    git checkout -b add-new-ec2-instance
  2. Konfiqurasiyanı dəyiş — yeni resource əlavə et və ya mövcudunu redaktə et.
  3. terraform plan işlət — hansı dəyişikliklərin tətbiq olunacağını gör.
  4. Pull request aç — dəyişiklik baxışdan keçsin; plan çıxışını PR şərhinə əlavə et.
  5. Merge və apply — təsdiqdən sonra main branch-a merge et, apply pipeline-dan keçsin.
Plan çıxışını PR-a avtomatik yapışdırmaq ən dəyərli vərdişlərdən biridir: rəyçi kodun nə yazdığını deyil, infrastrukturun faktiki nə edəcəyini görür. -2 to destroy sətri heç bir kod baxışının tuta bilməyəcəyi səhvi üzə çıxarır.

5 · Terraform üçün CI/CD pipeline

GitHub Actions nümunəsi

Terraform axınının avtomatlaşdırılması infrastrukturun ardıcıl və minimal insan müdaxiləsi ilə yerləşdirilməsini təmin edir. Jenkins, GitHub Actions və ya GitLab CI — hansını seçməyindən asılı olmayaraq məntiq eynidir: PR-da plan, main-də apply.

name: Terraform

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  terraform:
    runs-on: ubuntu-latest
    steps:
      - name: "Repo-nu yüklə"
        uses: actions/checkout@v2

      - name: "Terraform quraşdır"
        uses: hashicorp/setup-terraform@v1

      - name: "Terraform init"
        run: terraform init

      - name: "Terraform plan"
        run: terraform plan

      # apply yalnız main branch-a push olanda işə düşür
      - name: "Terraform apply"
        if: github.ref == 'refs/heads/main'
        run: terraform apply -auto-approve

Bu axında:

  • Hər pull request üçün terraform plan işə düşür və dəyişikliyi yoxlayır.
  • terraform apply yalnız main branch-a push olduqda tətbiq edilir.
Bir addım irəli: plan nəticəsini fayla yaz (terraform plan -out=tfplan) və apply mərhələsində məhz həmin faylı tətbiq et (terraform apply tfplan). Belədə baxışdan keçən plan ilə tətbiq edilən dəyişiklik eyni olur — aralıqda infrastruktur dəyişsə belə, gözlənilməz nəticə çıxmır.

6 · Prod mühitdə monitorinq və loglama

CloudWatch ilə monitorinq

Monitorinq və loglama infrastrukturun vəziyyətini izləmək və problemləri erkən görmək üçün vacibdir. Bulud provayderlərinin öz monitorinq alətləri Terraform ilə birbaşa idarə oluna bilər.

Nümunə: EC2 üçün CloudWatch alarm

resource "aws_cloudwatch_metric_alarm" "cpu_alarm" {
  alarm_name          = "high-cpu-usage"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 2
  metric_name         = "CPUUtilization"
  namespace           = "AWS/EC2"
  period              = 60
  statistic           = "Average"
  threshold           = 80
  alarm_description   = "EC2 instance-də yüksək CPU istifadəsini izləyir."

  dimensions = {
    InstanceId = aws_instance.my_instance.id
  }

  # alarm işə düşəndə SNS topic-ə bildiriş gedir
  alarm_actions = [aws_sns_topic.my_topic.arn]
}

Burada EC2 instance-in CPU istifadəsini izləyən alarm yaradılır: göstərici ardıcıl iki dövr ərzində 80%-i keçərsə, SNS topic-ə xəbərdarlıq göndərilir.

Copilot ilə iş: alarm bloklarını əl ilə yazmaq yerinə Copilot-a “bu resource üçün CPU, disk və status-check alarm-larını yarat, hamısı eyni SNS topic-ə göndərsin” tipli göstəriş ver. Sonra threshold və evaluation_periods dəyərlərini özün yoxla — model adətən nümunə dəyərləri təkrarlayır, sənin yükünə uyğun rəqəmi bilmir.

7 · Prod mühit üçün ən yaxşı praktikalar

a. IaC prinsipləri

  • İdempotentlik: eyni Terraform kodunu bir neçə dəfə işə salmaq eyni nəticəni verməlidir. İkinci apply “No changes” deməlidir.
  • Versiyalama: kod dəyişikliklərini Git-də izlə — geri qayıtmaq imkanı bundan gəlir.
  • Modulluq: konfiqurasiyanı təkrar istifadə olunan modullara böl; belədə mühitlər arasında ardıcıllıq təbii şəkildə yaranır.

b. Avtomatlaşdırılmış test

Terratest kimi alətlərlə infrastruktur kodunu prod mühitə çıxmazdan əvvəl yoxla: modul həqiqətən gözlənilən resource-ları yaradırmı, output-lar düzgündürmü, təhlükəsizlik qrupları gözlədiyindən artıq port açmırmı.

8 · Yadda saxla

  • Prod state mütləq remote, şifrələnmiş və locking-li olmalıdır — S3 + DynamoDB ən çox işlədilən cütlükdür.
  • Terraform istifadəçisinə minimal IAM icazəsi ver; plan və apply üçün ayrı rol işlət ki, PR mərhələsində heç nə dəyişməsin.
  • Secret-lər kodda deyil, Secrets Manager / Key Vault / Vault-da saxlanır — lakin state faylına düşdüyünü unutma, state-i də qoru.
  • Hər dəyişiklik Git branch → plan → PR baxışı → merge → apply yolundan keçsin; əl ilə apply istisna hal olmalıdır.
  • Monitorinq və audit log-u infrastrukturun bir hissəsi kimi Terraform ilə qur — sonradan əlavə edilən monitorinq həmişə natamam qalır.
