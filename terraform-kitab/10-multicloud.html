Multi-Cloud Deploy

DPE-07 · Data Platform & Engineering Bootcamp

Bir şirkət nadir hallarda yalnız bir cloud provider ilə qalır — bəzən qiymət, bəzən xüsusiyyət, bəzən də sadəcə şirkət birləşməsi sizi ikinci buluda aparır. Terraform-un provider arxitekturası AWS, Azure və Google Cloud resurslarını eyni konfiqurasiyada, eyni dillə idarə etməyə imkan verir. Bu fəsildə çoxlu provider blokları, alias-lar, credential idarəçiliyi və multi-cloud üçün əməli qaydaları öyrənəcəyik.

1 · Multi-cloud nə üçün lazımdır

Üç əsas motiv

  • Vendor lock-in-dən qaçmaq — bütün infrastrukturunuz tək provider-də olanda qiymət artımı və ya uzunmüddətli kəsinti sizə alternativ qoymur. İki provider ilə danışıqlar masasında da, texniki planda da əliniz güclü olur.
  • Hər provider-in ən güclü tərəfini götürmək — AWS compute və genişlik baxımından, Azure korporativ inteqrasiya (Active Directory, lisenziyalar) baxımından, Google Cloud isə maşın öyrənməsi və data analitikası baxımından fərqlənir. Multi-cloud sizə hər işin üçün ən uyğun servisi seçmək imkanı verir.
  • Dayanıqlıq — infrastrukturu müxtəlif cloud mühitlərinə yaymaq fəlakətdən bərpa və yüksək əlçatanlıq üçün əlavə qat yaradır. Bir provider-də region səviyyəli kəsinti olanda xidmət tam dayanmır.

Əvəzində isə mürəkkəblik ödəyirsiniz: iki fərqli IAM modeli, iki fərqli şəbəkə anlayışı, iki fərqli hesab. Məhz burada Terraform işə düşür — konfiqurasiya dili, plan/apply axını və state modeli hər iki tərəf üçün eynidir.

Multi-cloud "hər şeyi hər yerdə işlət" demək deyil. Praktikada uğurlu quruluşlar iş yükünü bölür: məsələn əsas tətbiq AWS-də, data anbarı GCP-də, korporativ identity Azure-da. Eyni tətbiqi iki buludda paralel saxlamaq isə xərci və əməliyyat yükünü ikiqat artırır.

2 · Terraform-da açar anlayışlar

a. Bir konfiqurasiyada çoxlu provider

Terraform-un çoxlu bulud ilə eyni anda işləyə bilməsinin arxasında provider plugin modeli dayanır. Hər cloud provider-in öz plugin-i var və o plugin həmin provider-in API-si ilə danışır. Konfiqurasiyada neçə provider bloku yazsanız, Terraform o qədər plugin yükləyir və hər resursu öz provider-inə yönləndirir.

b. Provider alias-ları

Eyni provider-in birdən çox nüsxəsi lazım olanda — məsələn iki AWS region-u, iki Azure subscription-u — alias arqumentindən istifadə edirsiniz. Alias eyni plugin-in fərqli konfiqurasiyalı ikinci nüsxəsini yaradır, resurs isə provider = aws.us_west yazaraq hansı nüsxəni istədiyini bildirir.

VəziyyətYanaşma
AWS + Azure eyni konfiqurasiyadaİki ayrı provider bloku, alias lazım deyil
İki AWS region-uEyni provider, fərqli alias dəyərləri
İki Azure subscription-uazurerm provider-i alias ilə təkrarlanır
On-prem vSphere + AWSvsphere və aws provider-ləri yan-yana
Modul daxilində fərqli providerproviders = { aws = aws.us_west } ötürülür

3 · Nümunə: AWS və Azure-da eyni anda deploy

Qovluq quruluşu

/multi-cloud
  ├── main.tf
  ├── variables.tf
  └── outputs.tf

Addım 1 — Provider-ləri konfiqurasiya et

# AWS provider konfiqurasiyası
provider "aws" {
  region     = var.aws_region
  access_key = var.aws_access_key
  secret_key = var.aws_secret_key
}

# Azure provider konfiqurasiyası
provider "azurerm" {
  features {}
  subscription_id = var.azure_subscription_id
  client_id       = var.azure_client_id
  client_secret   = var.azure_client_secret
  tenant_id       = var.azure_tenant_id
}

Burada iki provider paralel təyin olunur: aws bloku resursları göstərilən AWS region-una, azurerm bloku isə verilmiş Azure subscription-una yerləşdirir. features {} bloku azurerm provider-i üçün məcburidir — boş qalsa belə yazılmalıdır.

Addım 2 — AWS-də EC2 instance

resource "aws_instance" "my_aws_instance" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    Name = "AWS-Instance"
  }
}

Addım 3 — Azure-da virtual maşın

Azure tərəfdə VM tək resurs deyil: əvvəlcə resource group, sonra virtual network, sonra network interface, ən sonda isə maşının özü yaradılır. Bu, AWS-dən fərqli düşüncə modelidir və multi-cloud yazarkən ilk qarşılaşacağınız fərqlərdəndir.

resource "azurerm_resource_group" "my_rg" {
  name     = "myResourceGroup"
  location = "East US"
}

resource "azurerm_virtual_network" "my_vnet" {
  name                = "myVNet"
  address_space       = ["10.0.0.0/16"]
  location            = azurerm_resource_group.my_rg.location
  resource_group_name = azurerm_resource_group.my_rg.name
}

resource "azurerm_network_interface" "my_nic" {
  name                = "myNIC"
  location            = azurerm_resource_group.my_rg.location
  resource_group_name = azurerm_resource_group.my_rg.name

  ip_configuration {
    name                          = "myNICConfig"
    subnet_id                     = azurerm_subnet.my_subnet.id
    private_ip_address_allocation = "Dynamic"
  }
}

resource "azurerm_windows_virtual_machine" "my_vm" {
  name                  = "myWindowsVM"
  resource_group_name   = azurerm_resource_group.my_rg.name
  location              = azurerm_resource_group.my_rg.location
  size                  = "Standard_DS1_v2"
  admin_username        = "adminuser"
  admin_password        = var.vm_admin_password  # parolu koda yazma!
  network_interface_ids = [azurerm_network_interface.my_nic.id]

  os_disk {
    caching              = "ReadWrite"
    storage_account_type = "Standard_LRS"
  }
}
Mənbə nümunələrində admin_password = "P@ssw0rd123!" kimi sabit parollara tez-tez rast gəlinir. Belə yazılmış parol state faylına və git tarixçəsinə düşür. Həmişə variable + sensitive = true, daha yaxşısı isə Key Vault / Secrets Manager istifadə edin.

Addım 4 — Nəticələri output kimi qaytar

output "aws_instance_public_ip" {
  value = aws_instance.my_aws_instance.public_ip
}

output "azure_vm_public_ip" {
  value = azurerm_windows_virtual_machine.my_vm.public_ip_address
}

Addım 5 — Tətbiq et

terraform init    # hər iki provider plugin-ini yükləyir
terraform plan    # planı nəzərdən keçir
terraform apply   # hər iki buludda eyni anda yaradır

Bir apply əmri həm AWS-də EC2 instance-ı, həm də Azure-da virtual maşını qurur. Aralarında birbaşa asılılıq olmadığı üçün Terraform onları paralel işlədir.

terraform init multi-cloud layihələrdə həmişə daha uzun çəkir, çünki hər provider plugin-i onlarla meqabayt ola bilir. CI-da .terraform qovluğunu cache-ə salmaq pipeline vaxtını gözlə görünəcək qədər azaldır.

4 · Multi-cloud credential idarəçiliyi

a. Environment dəyişənləri

Həssas açarları konfiqurasiya faylına yazmaq multi-cloud-da ikiqat təhlükəlidir — bir sızma iki buludu birdən açır. Ən sadə düzgün yol credential-ları environment dəyişənləri ilə ötürməkdir; Terraform onları avtomatik oxuyur və provider blokunda heç nə yazmağa ehtiyac qalmır.

# AWS credential-ları
export AWS_ACCESS_KEY_ID="your-aws-access-key"
export AWS_SECRET_ACCESS_KEY="your-aws-secret-key"

# Azure credential-ları
export ARM_CLIENT_ID="your-azure-client-id"
export ARM_CLIENT_SECRET="your-azure-client-secret"
export ARM_TENANT_ID="your-azure-tenant-id"
export ARM_SUBSCRIPTION_ID="your-azure-subscription-id"

b. Secrets management servisləri

Daha yetkin yanaşma sirləri mərkəzi saxlama xidmətindən dinamik oxumaqdır: AWS Secrets Manager, Azure Key Vault, Google Secret Manager və ya HashiCorp Vault. Bu halda sirr heç vaxt repository-də olmur, rotasiya isə Terraform-dan asılı olmadan aparılır.

data "aws_secretsmanager_secret_version" "db_password" {
  secret_id = "db_password"
}

resource "aws_db_instance" "my_db" {
  allocated_storage = 20
  engine            = "mysql"
  instance_class    = "db.t2.micro"
  password          = data.aws_secretsmanager_secret_version.db_password.secret_string
}
Secrets Manager-dən oxunan dəyər yenə də state faylına düz mətnlə yazılır. Bu, Terraform-un işləmə prinsipidir və qaçılmazdır. Buna görə state mütləq şifrələnmiş remote backend-də (S3 + KMS, Azure Storage + encryption) saxlanmalı və ona giriş məhdud olmalıdır.
ÜsulNə vaxtZəif tərəf

Secrets Manager / Key VaultKomanda, prodDəyər yenə state-ə düşür

Ən yaxşı seçim uzunömürlü açarı ümumiyyətlə yaratmamaqdır: GitLab CI və GitHub Actions hər ikisi OIDC ilə AWS və Azure-a qısamüddətli token alaraq giriş edə bilir. Belə halda sızacaq bir sirr yoxdur.

5 · Multi-cloud üçün əməli qaydalar

a. Provider-lər arasında ardıcıllıq

Adlandırma, teq və konfiqurasiya nümunələri hər iki buludda eyni olmalıdır. Bu, resursların izlənməsini, xərc hesabatını və avtomatlaşdırmanı sadələşdirir — eyni Project teqi ilə iki fərqli buludun hesabını yan-yana qoya bilirsiniz.

resource "aws_instance" "my_instance" {
  tags = {
    Environment = "prod"
    Project     = "multi-cloud-demo"
  }
}

resource "azurerm_virtual_machine" "my_vm" {
  tags = {
    Environment = "prod"
    Project     = "multi-cloud-demo"
  }
}
Teq açarlarında böyük-kiçik hərf fərqinə diqqət yetirin: AWS teq açarlarını hərfə həssas saxlayır, Azure isə bəzi hallarda normallaşdırır. Komanda daxilində bir konvensiya seçin (məsələn həmişə PascalCase) və default_tags ilə mərkəzləşdirin.

b. Monitorinq və müşahidə

Hər buludun öz monitorinq paneli var, lakin siz vahid mənzərəyə ehtiyac duyursunuz. Prometheus, Grafana və Datadog kimi vasitələr multi-cloud metrikaları bir yerdə toplaya bilir — beləliklə "hansı buludda problem var" sualına bir ekrandan cavab verirsiniz.

c. Mərkəzləşdirilmiş loglama

ELK Stack (Elasticsearch, Logstash, Kibana), Azure Monitor və ya AWS CloudWatch vasitəsilə müxtəlif provider-lərin loglarını tək yerə toplayın. Multi-cloud mühitdə problemi araşdırarkən iki fərqli konsol arasında gedib-gəlmək ən çox vaxt itirən işdir.

AI ilə iş: Copilot və ya Claude-dan multi-cloud konfiqurasiya istəyəndə provider-i açıq yazın — "AWS və Azure üçün, azurerm 3.x sintaksisi ilə". Əks halda model çox vaxt köhnəlmiş azurerm_virtual_machine resursunu təklif edir; halbuki müasir sintaksis azurerm_windows_virtual_machine / azurerm_linux_virtual_machine-dir. Yaradılan kodu həmişə terraform validate və provider sənədi ilə yoxlayın.

6 · Yadda saxla

  • Multi-cloud üç şey verir — vendor lock-in-dən azadlıq, hər provider-in güclü tərəfi və dayanıqlıq; əvəzində əməliyyat mürəkkəbliyi gətirir.
  • Bir konfiqurasiyada istənilən sayda provider bloku ola bilər; eyni provider-in təkrar nüsxəsi üçün alias işlədilir və resurs provider = aws.us_west ilə seçim edir.
  • Credential-ları heç vaxt konfiqurasiyaya yazmayın — environment dəyişənləri, Secrets Manager / Key Vault, ən yaxşısı isə OIDC ilə qısamüddətli token.
  • Sirlər state faylına düz mətnlə düşür: state mütləq şifrələnmiş remote backend-də saxlanmalı, girişi məhdudlaşdırılmalıdır.
  • Ardıcıl teq və adlandırma, vahid monitorinq və mərkəzləşdirilmiş loglama multi-cloud-u idarə oluna bilən saxlayan üç sütundur.
