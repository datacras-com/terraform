Xərc İdarəetməsi

DPE-07 · Data Platform & Engineering Bootcamp

Bulud infrastrukturunda ən çox təkrarlanan səhv budur: resurs yaradılır, işini görür, sonra unudulur — amma hesab hər ay gəlməyə davam edir. Bu fəsildə Terraform ilə xərci necə görünən, ölçülən və idarə olunan hala gətirməyi öyrənəcəyik: right-sizing, Reserved Instances, avtomatik söndürmə, budget alert-ləri, S3 lifecycle policy və autoscaling.

1 · Niyə xərc idarəetməsi kritikdir

Buludda xərc bir dəfəlik qərar deyil, davamlı proses

Ənənəvi data mərkəzində serveri bir dəfə alırsan və beş il işlədirsən. Buludda isə hər saat pul yanır. Ona görə xərc idarəetməsi infrastrukturun ayrılmaz hissəsi olmalıdır:

  • Büdcə nəzarəti — gözlənilməz hesab artımının qarşısını alır.
  • Resurs optimallaşdırması — resurslar iş yükünə uyğun ölçüdə və səmərəli istifadə olunur.
  • Miqyaslanma çevikliyi — infrastruktur böyüyəndə xərc mütləq eyni sürətlə böyüməməlidir.
  • FinOps — infrastruktur qərarlarını maliyyə hədəfləri ilə uzlaşdırır; həm performans, həm xərc birlikdə optimallaşdırılır.

Xərc strategiyalarını Terraform iş axınına daxil edəndə optimallaşdırma kiminsə yadına düşəndə edilən əməliyyat olmaqdan çıxır, kodun bir hissəsinə çevrilir — yəni review olunur, versiyalanır və təkrarlanır.

2 · Right-sizing — resursu iş yükünə uyğunlaşdırmaq

Ən sadə və ən çox unudulan optimallaşdırma

Right-sizing resursun ölçüsünü faktiki istifadəyə uyğunlaşdırmaq deməkdir. Compute, yaddaş və disk üzrə həddindən artıq resurs ayırmaq (overprovisioning) heç bir fayda vermədən xərc yaradır. CPU-su ayda orta hesabla 4% yüklənən t3.large instance-ın yerinə t3.micro tam kifayət edə bilər.

resource "aws_instance" "example" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"  # istifadə statistikasına görə kiçildildi

  tags = {
    Name = "example-instance"
  }
}

Burada instance tipi t3.large-dan t3.micro-ya endirilib. Dəyişiklik bir sətirdir, amma aylıq hesabda fərq təxminən səkkiz dəfədir.

Right-sizing təxminlə edilmir. Əvvəlcə CloudWatch (və ya Azure Monitor) metrikalarına bax: son 14–30 günün CPU, yaddaş və şəbəkə istifadəsi. AWS Compute Optimizer və Trusted Advisor bu təhlili hazır şəkildə verir — Terraform-da isə sadəcə nəticəni tətbiq edirsən.
Instance tipini dəyişmək instance-ın restart olunmasına səbəb olur. Prod mühitdə bunu iş saatlarından kənarda və ya autoscaling group vasitəsilə tədricən (rolling) et. instance_type dəyişikliyi bəzi hallarda resursun tam yenidən yaradılmasına gətirib çıxarır — mütləq əvvəlcə terraform plan nəticəsini oxu.

Dəyişəni parametrləşdirmək mühitlər arasında fərqi idarə etməyi asanlaşdırır:

variable "instance_type" {
  type        = string
  default     = "t3.micro"
  description = "Mühitə görə instance ölçüsü"
}

# dev.tfvars   → instance_type = "t3.micro"
# prod.tfvars  → instance_type = "m6i.large"

3 · Reserved Instances və Savings Plans

Öhdəlik müqabilində endirim

AWS, Azure və Google Cloud müəyyən müddət ərzində (adətən 1 və ya 3 il) müəyyən həcmdə compute istifadə etmək öhdəliyi qarşılığında ciddi endirim təklif edir. AWS-də bunlar Reserved Instances (RI) və Savings Plans, Azure-da Reservations adlanır. Endirim on-demand qiymətə nisbətən 75%-ə qədər ola bilər.

resource "aws_instance" "example" {
  ami                = "ami-0c55b159cbfafe1f0"
  instance_type      = "t3.micro"
  instance_lifecycle = "reserved"  # instance-ı reserved kimi işarələyir
}
Bu nümunə anlayışı izah etmək üçündür — AWS provider-də aws_instance resursunun belə bir arqumenti yoxdur və RI instance-ın öz üzərində qeyd olunmur. Praktikada RI/Savings Plan ayrıca alınan maliyyə öhdəliyidir: uyğun instance-lar işə düşəndə endirim hesaba avtomatik tətbiq olunur. Terraform tərəfdə buna ən yaxın resurs aws_ec2_capacity_reservation-dır; Savings Plan isə Billing konsolu və ya API üzərindən alınır.

Praktik qayda: RI-ni yalnız yükü proqnozlaşdırıla bilən sistemlər üçün al. Bir ilə bağlandığın instance ailəsi altı ay sonra artıq lazım olmasa, endirim qənaətə yox, itkiyə çevrilir.

ModelNə vaxtÇeviklikEndirim
On-DemandQısamüddətli, sınaq yükləriTam—
Savings PlanSabit ümumi compute xərciYüksək (instance ailəsi dəyişə bilər)~30–70%
Reserved InstanceKonkret tip, sabit yükAşağı~40–75%
SpotKəsilməyə dözümlü batch, CI runnerOrta (istənilən an geri alına bilər)~70–90%
Dev mühitləri üçün Spot instance-lar çox vaxt RI-dən daha yaxşı seçimdir: öhdəlik yaratmır və EKS node group-larında capacity_type = "SPOT" ilə bir sətirlik dəyişiklikdir.

4 · Boş resursların avtomatik söndürülməsi

Gecə işləməyən mühit üçün niyə pul verək?

Dev və test mühitləri günün 24 saatı işləyir, amma komanda onlardan gündə 8–9 saat istifadə edir. Yəni vaxtın təxminən 65%-i boşa gedir. EventBridge (CloudWatch Events) və Lambda kombinasiyası ilə instance-ları axşam söndürüb səhər yandırmaq mümkündür — və bu qurğunun özü də Terraform ilə yazılır.

resource "aws_cloudwatch_event_rule" "shutdown_rule" {
  name                = "shutdown-instances"
  schedule_expression = "cron(0 18 * * ? *)"  # hər gün 18:00-da
}

resource "aws_lambda_function" "shutdown_ec2" {
  filename      = "lambda_shutdown.zip"
  function_name = "shutdownEC2Instances"
  handler       = "lambda_function.lambda_handler"
  runtime       = "python3.12"
  role          = aws_iam_role.lambda_exec.arn
}

resource "aws_cloudwatch_event_target" "shutdown_target" {
  rule      = aws_cloudwatch_event_rule.shutdown_rule.name
  target_id = "EC2Shutdown"
  arn       = aws_lambda_function.shutdown_ec2.arn
}

Bu konfiqurasiyada Lambda funksiyası hər axşam saat 18:00-da işə düşür və müəyyən tag-a malik EC2 instance-ları dayandırır. Səhər üçün eyni məntiqlə ikinci bir rule (cron(0 8 ? * MON-FRI *)) əlavə edilir.

Lambda-nı bütün instance-lar üzərində deyil, tag üzərində işlət: yalnız AutoShutdown = "true" tag-ı olanları dayandır. Belədə yeni resurs əlavə edəndə kodu deyil, sadəcə tag-ı dəyişirsən — və səhvən prod verilənlər bazasını söndürmək riski aradan qalxır.
Söndürülmüş EC2 instance üçün compute haqqı alınmır, amma qoşulmuş EBS disk və Elastic IP üçün ödəniş davam edir. Yəni real qənaət 100% deyil, təxminən 60–70%-dir.

5 · Xərc monitorinqi və alert-lər

a · AWS Budgets ilə hədd təyin etmək

Xərci ay sonunda hesabda görmək gecdir. AWS Budgets müəyyən hədd təyin etməyə və bu həddin faizi keçiləndə bildiriş almağa imkan verir. Terraform bu qurğunu da avtomatlaşdırır.

resource "aws_budgets_budget" "monthly_budget" {
  budget_type  = "COST"
  limit_amount = "500"
  limit_unit   = "USD"
  time_unit    = "MONTHLY"

  cost_filters = {
    Service = "AmazonEC2"
  }

  notification {
    comparison_operator        = "GREATER_THAN"
    threshold                  = 80
    threshold_type             = "PERCENTAGE"
    notification_type          = "ACTUAL"
    subscriber_email_addresses = ["admin@example.com"]
  }
}

Nümunədə:

  • EC2 xidməti üçün aylıq $500 büdcəsi təyin olunur.
  • Büdcənin 80%-i istifadə olunanda e-poçta bildiriş gedir — yəni ay bitməmiş reaksiya vermək imkanı qalır.
notification_type üçün iki dəyər var: ACTUAL artıq xərclənmiş məbləği, FORECASTED isə cari templə ay sonunda gözlənilən məbləği izləyir. Ən faydalı qurğu ikisini birlikdə işlətməkdir — forecast alert-i problemi bir neçə gün əvvəl xəbər verir.

b · Azure Cost Management

Azure tərəfdə eyni məntiq azurerm_cost_management_budget ilə qurulur: subscription və ya resource group səviyyəsində məbləğ təyin edilir, hədd keçiləndə bildiriş göndərilir.

resource "azurerm_cost_management_budget" "example" {
  name              = "monthly-budget"
  scope             = azurerm_subscription.primary.id
  amount            = 500
  time_grain        = "Monthly"
  time_period_start = "2024-01-01"
  time_period_end   = "2024-12-31"

  notification {
    threshold      = 0.8  # 80% həddi
    contact_emails = ["admin@example.com"]
  }
}

Burada 2024-cü il üçün $500 limitli büdcə qurulur və 80% həddə çatanda bildiriş göndərilir.

Büdcə alert-i xərci dayandırmır — sadəcə xəbər verir. Əgər avtomatik reaksiya lazımdırsa, bildirişi SNS topic-ə yönləndirib oradan Lambda işə salmaq lazımdır (məsələn: qeyri-prod resursları dayandırmaq). Alert-in getdiyi e-poçt ünvanı da mütləq komanda siyahısı olsun — bir nəfərin şəxsi poçtu məzuniyyətə çıxanda alert də çıxır.

6 · S3 lifecycle policy ilə storage optimallaşdırması

Nadir oxunan datanı ucuz tier-ə köçür

Uzunmüddətli saxlanan data — loglar, backup-lar, arxiv — çox vaxt yazıldıqdan bir neçə həftə sonra praktik olaraq heç vaxt oxunmur. Lifecycle policy bu datanı avtomatik olaraq daha ucuz storage sinfinə keçirir (S3 Glacier, Azure Blob Archive) və müəyyən müddətdən sonra silir.

resource "aws_s3_bucket" "my_bucket" {
  bucket = "my-data-bucket"

  lifecycle_rule {
    enabled = true

    transition {
      days          = 30
      storage_class = "GLACIER"  # 30 gündən sonra Glacier-ə köçür
    }

    expiration {
      days = 365  # 365 gündən sonra sil
    }
  }
}

Nəticədə data 30 gün sonra ucuz arxiv qatına keçir, 365 gün sonra isə tamamilə silinir — beləcə heç kimin lazım bilmədiyi obyektlər illərlə pul yandırmır.

AWS provider-in 4-cü versiyasından etibarən bucket daxilindəki lifecycle_rule bloku köhnəlmiş sayılır. Yeni kodda ayrıca resurs işlədilir: 
resource "aws_s3_bucket_lifecycle_configuration" "my_bucket" {
  bucket = aws_s3_bucket.my_bucket.id

  rule {
    id     = "archive-and-expire"
    status = "Enabled"

    transition {
      days          = 30
      storage_class = "GLACIER"
    }

    expiration {
      days = 365
    }
  }
}
S3 storage sinfiUyğun ssenariBərpa müddətiNisbi qiymət
StandardAktiv oxunan dataDərhal1×
Standard-IAAyda bir-iki dəfə oxunanDərhal~0.5×
Glacier Instant RetrievalArxiv, amma tez lazım ola bilərDərhal~0.25×
Glacier Flexible RetrievalBackup, audit arxiviDəqiqələr–saatlar~0.1×
Glacier Deep ArchiveUyğunluq tələbi ilə 7–10 il saxlanan12 saata qədər~0.04×
Glacier-dən data çıxarmaq pulludur. Əgər arxivi ayda bir neçə dəfə oxumaq ehtimalı varsa, retrieval haqqı qənaəti üstələyə bilər. Qaydanı yazmadan əvvəl datanın oxunma tezliyinə bax.

7 · Autoscaling ilə xərci tələbata bağlamaq

Yalnız istifadə etdiyin qədər ödə

Autoscaling resurs sayını yükə görə avtomatik artırıb-azaldır. Pik saatlarda performans qorunur, gecə isə instance sayı minimuma düşür. Terraform autoscaling group-un konfiqurasiyasını tam avtomatlaşdırır.

resource "aws_autoscaling_group" "example" {
  desired_capacity = 1
  max_size         = 5
  min_size         = 1

  launch_configuration = aws_launch_configuration.example.id

  tag {
    key                 = "Name"
    value               = "autoscaled-instance"
    propagate_at_launch = true
  }
}

resource "aws_launch_configuration" "example" {
  image_id        = "ami-0c55b159cbfafe1f0"
  instance_type   = "t3.micro"
  security_groups = [aws_security_group.instance.id]

  lifecycle {
    create_before_destroy = true
  }
}

Burada iki mühüm detal var. Birincisi, autoscaling group instance sayını 1 ilə 5 arasında tələbata görə tənzimləyir. İkincisi, create_before_destroy = true lifecycle qaydası yeni launch konfiqurasiyasını köhnəni silmədən əvvəl yaradır — belədə dəyişiklik zamanı xidmət kəsilməsi olmur.

aws_launch_configuration AWS tərəfindən köhnəlmiş elan olunub və yeni account-larda dəstəklənmir. Yeni kodda aws_launch_template işlədin — o həm Spot qarışıq siyasətlərini, həm də daha yeni instance tiplərini dəstəkləyir.
Scale-in siyasəti scale-out qədər vacibdir. Çox komanda instance əlavə etməyi konfiqurasiya edir, azaltmağı isə unudur — nəticədə pikdən sonra qrup böyük qalır. target_tracking siyasəti (məsələn, orta CPU 50%) hər iki istiqaməti bir konfiqurasiya ilə idarə edir.

8 · Best practice-lər

Xərc idarəetməsini vərdişə çevir

  • Müntəzəm baxış. Terraform konfiqurasiyalarını dövri olaraq (məsələn, rüblük) nəzərdən keçir: resurslar hələ də düzgün ölçüdədirmi, RI və Savings Plan imkanları istifadə olunurmu, artıq lazım olmayan resurs qalıbmı.
  • Alert-ləri avtomatlaşdır. Büdcə və hədd bildirişləri kod ilə qurulmalıdır ki, yeni account və ya mühit yaradılanda avtomatik gəlsin.
  • Autoscaling tətbiq et. Statik instance sayı əvəzinə yükə bağlı miqyaslanma — həm performans, həm xərc üçün.
  • Ardıcıl tag siyasəti. Environment, Project, Owner, CostCenter tag-ları olmadan hesabı bölmək mümkün deyil. Tag-ları default_tags ilə provider səviyyəsində tətbiq et.
  • Xərci plan mərhələsində gör. infracost kimi alətlər terraform plan nəticəsinə baxıb aylıq xərc fərqini hesablayır və CI/CD-də merge request-ə şərh kimi yazır.
provider "aws" {
  region = "eu-north-1"

  default_tags {
    tags = {
      Environment = "dev"
      Project     = "dpe-07"
      ManagedBy   = "terraform"
      CostCenter  = "platform"
    }
  }
}
AI köməkçisindən istifadə: terraform plan nəticəsini və ya mövcud konfiqurasiyanı Copilot-a verib «bu konfiqurasiyada hansı resurslar lazımsız xərc yaradır?» sualını verə bilərsən. Model NAT Gateway sayı, boş Elastic IP, gp2 əvəzinə gp3 disk kimi tez-tez qaçırılan detalları yaxşı tapır. Amma qiymət rəqəmlərini modeldən deyil, provider-in rəsmi qiymət cədvəlindən yoxla.

9 · Yadda saxla

  • Xərc idarəetməsi ayrıca əməliyyat deyil — right-sizing, lifecycle policy və budget kod içində, review olunan hissə kimi yaşamalıdır.
  • Ən böyük qənaət adətən ən sadə yerlərdən gəlir: düzgün instance ölçüsü, gecə söndürülən dev mühit və köhnə datanın arxivə köçürülməsi.
  • Reserved Instance və Savings Plan yalnız proqnozlaşdırıla bilən yük üçün mənalıdır; dəyişkən yük üçün autoscaling və Spot daha uyğundur.
  • Budget alert xərci dayandırmır, sadəcə xəbərdarlıq edir — ACTUAL və FORECASTED alert-lərini birlikdə qur.
  • Tag olmadan xərc təhlili mümkün deyil: default_tags ilə hər resursa mühit, layihə və sahib məlumatı yaz.
