CI/CD İnteqrasiyası

DPE-07 · Data Platform & Engineering Bootcamp

Terraform-un gücü onu əl ilə deyil, avtomat pipeline vasitəsilə işlətdikdə tam açılır. Bu fəsildə Terraform-u GitHub Actions, Jenkins və GitLab CI ilə birləşdirməyi, plan və apply mərhələlərini ayırmağı, secret-ləri təhlükəsiz saxlamağı və prod üçün təsdiq mərhələsi qurmağı öyrənəcəyik.

1 · CI/CD inteqrasiyasının faydaları

Niyə pipeline?

Terraform-u CI/CD ilə birləşdirmək bir neçə konkret üstünlük verir:

  • Avtomatlaşdırma: infrastruktur kod dəyişikliyinə əsasən avtomatik qurulur, əl işi minimuma enir.
  • Ardıcıllıq: hər deploy eyni addımlarla, eyni mühitdə keçir — "mənim maşınımda işləyirdi" problemi aradan qalxır.
  • Birgə iş: bütün dəyişikliklər Git üzərindən keçir, izlənilir və nəzərdən keçirilir.
  • Test və yoxlama: pipeline dəyişikliyi tətbiq etməzdən əvvəl terraform validate və terraform plan ilə yoxlaya bilir, səhv konfiqurasiya riski azalır.
  • Geri qayıtma: nəsə səhv gedərsə, əvvəlki commit-ə qayıdıb pipeline-ı yenidən işə salmaqla infrastrukturu bərpa etmək olur.
CI/CD Terraform-un məsuliyyətini azaltmır — əksinə artırır. Avtomat pipeline səhv konfiqurasiyanı da eyni sürətlə tətbiq edəcək. Ona görə plan-ın nəzərdən keçirilməsi və prod üçün təsdiq mərhələsi pipeline-ın ayrılmaz hissəsidir.

2 · Terraform və GitHub Actions

Workflow qurmaq

GitHub Actions workflow-ları repository-nin .github/workflows/ qovluğunda saxlanılır. İnfrastruktur kodunda dəyişiklik olanda (məsələn, pull request merge ediləndən sonra) Terraform-u işə salmaq üçün belə bir fayl yazılır.

Fayl: .github/workflows/terraform.yml

name: Terraform

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

jobs:
  terraform:
    runs-on: ubuntu-latest
    steps:
      # Repository kodunu runner-ə çək
      - name: Checkout repository
        uses: actions/checkout@v2

      # Terraform CLI-ı quraşdır
      - name: Set up Terraform
        uses: hashicorp/setup-terraform@v1

      - name: Initialize Terraform
        run: terraform init

      - name: Terraform Plan
        run: terraform plan

      # apply yalnız main-ə push olanda işləyir
      - name: Terraform Apply
        if: github.event_name == 'push'
        run: terraform apply -auto-approve

Bu nümunədə:

  • Workflow main branch-ına push və ya pull request zamanı işə düşür.
  • Kod çəkilir, Terraform quraşdırılır, sonra init və plan icra olunur.
  • main-ə push olduqda apply avtomatik işləyərək dəyişiklikləri tətbiq edir.

Secret-lərin saxlanması

Giriş açarları və API token-ləri kimi həssas məlumatlar GitHub Secrets vasitəsilə saxlanılmalıdır. Repository-də Settings → Secrets and variables → Actions bölməsindən əlavə edin, sonra workflow-da mühit dəyişəni kimi istifadə edin:

env:
  AWS_ACCESS_KEY_ID:     ${{ secrets.AWS_ACCESS_KEY_ID }}
  AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
Uzunmüddətli açar əvəzinə OIDC ilə müvəqqəti giriş qurmaq daha təhlükəsizdir: GitHub Actions AWS-ə birbaşa IAM rolu ilə qoşulur və repository-də heç bir daimi açar saxlanmır.

Plan və apply-ın ayrılması

Tipik iş axınında terraform plan hər pull request üçün işləyərək dəyişikliyi göstərir, amma tətbiq etmir. terraform apply isə yalnız dəyişiklik main-ə merge olunandan sonra işləyir.

- name: Terraform Plan
  run: terraform plan
  if: github.event_name == 'pull_request'

- name: Terraform Apply
  run: terraform apply -auto-approve
  if: github.event_name == 'push'

Bu quruluş infrastruktur dəyişikliklərinin yalnız kod nəzərdən keçirildikdən və merge edildikdən sonra tətbiq olunmasını təmin edir.

-auto-approve təsdiq soruşmadan tətbiq edir. Bu, avtomat pipeline üçün lazımdır, amma o deməkdir ki, pipeline-a çatan hər plan tətbiq olunacaq. Prod üçün mütləq təsdiq mərhələsi və ya -out=tfplan ilə yazılmış planın yenidən istifadəsi qurulmalıdır.

3 · Terraform və Jenkins

Jenkins pipeline qurmaq

Jenkins də Terraform iş axınını avtomatlaşdırmaq üçün geniş işlədilən vasitədir. Pipeline vasitəsilə konfiqurasiyanı yoxlamaq, plan qurmaq və tətbiq etmək olur.

1. Terraform plugin-i quraşdırın

Jenkins-in Terraform plugin-i inteqrasiyanı asanlaşdırır: Manage Jenkins → Manage Plugins → Available bölməsində "Terraform" axtarıb quraşdırın.

2. Pipeline yaradın

Jenkins-də yeni pipeline job yaradın və addımları Jenkinsfile-da təsvir edin.

pipeline {
  agent any

  stages {
    stage('Checkout') {
      steps {
        checkout scm
      }
    }
    stage('Terraform Init') {
      steps {
        sh 'terraform init'
      }
    }
    stage('Terraform Plan') {
      steps {
        sh 'terraform plan'
      }
    }
    stage('Terraform Apply') {
      // yalnız main branch-da işləyir
      when {
        branch 'main'
      }
      steps {
        sh 'terraform apply -auto-approve'
      }
    }
  }
}

Bu nümunədə pipeline kodu repository-dən çəkir, terraform init ilə hazırlıq görür, terraform plan ilə dəyişiklikləri yoxlayır və apply-ı yalnız main branch-ında icra edir.

3. Credentials saxlamaq

Bulud provider-inin giriş açarlarını Jenkins Credentials-da saxlayın: Manage Jenkins → Manage Credentials. Sonra pipeline-da bu credential-lara mühit dəyişəni vasitəsilə istinad edin:

environment {
  AWS_ACCESS_KEY_ID     = credentials('aws-access-key-id')
  AWS_SECRET_ACCESS_KEY = credentials('aws-secret-access-key')
}

4 · Terraform və GitLab CI

.gitlab-ci.yml faylı

GitLab CI GitLab-a daxil olan CI/CD vasitəsidir və konfiqurasiya repository-nin kök qovluğundakı .gitlab-ci.yml faylında təsvir edilir.

image: hashicorp/terraform:latest

stages:
  - validate
  - plan
  - apply

# Hər job-dan əvvəl init işləyir
before_script:
  - terraform init

validate:
  stage: validate
  script:
    - terraform validate

plan:
  stage: plan
  script:
    - terraform plan
  # plan yalnız merge request üçün
  only:
    - merge_requests

apply:
  stage: apply
  script:
    - terraform apply -auto-approve
  # apply yalnız əsas branch-da
  only:
    - master

Bu nümunədə:

  • Pipeline üç mərhələdən ibarətdir: validate, plan, apply.
  • terraform validate ilk mərhələdə işləyərək sintaksisi yoxlayır.
  • terraform plan yalnız merge request-lər üçün işləyir və dəyişikliyi əvvəlcədən göstərir.
  • terraform apply yalnız əsas branch-da işləyir — yəni dəyişiklik merge olunandan sonra.

Secret idarəçiliyi

Həssas dəyərləri GitLab CI dəyişənləri kimi saxlayın: Settings → CI/CD → Variables. Dəyişəni Masked və Protected kimi işarələyin ki, log-da görünməsin və yalnız qorunan branch-larda əlçatan olsun.

GitLab həm də daxili Terraform state backend təklif edir — ayrıca S3 bucket qurmadan state-i GitLab-da saxlamaq və kilidləmək olur. Kiçik komandalar üçün bu, quraşdırmanı əhəmiyyətli dərəcədə sadələşdirir.

6 · Pipeline üçün best practice

a. Mühitləri ayırın

CI/CD ilə deploy edərkən dev, staging və prod üçün ayrı pipeline və ya ayrı workspace işlədin. Bu, dəyişikliyin prod-a çıxmazdan əvvəl staging-də sınaqdan keçməsini təmin edir.

- name: Terraform Apply (Staging)
  run: terraform workspace select staging && terraform apply -auto-approve

- name: Terraform Apply (Prod)
  run: terraform workspace select production && terraform apply -auto-approve

b. Təsdiq mərhələsi qurun

Prod mühiti üçün terraform apply-dan əvvəl təsdiq (approval gate) əlavə edin. Beləliklə, infrastruktur dəyişikliyi tətbiq olunmazdan əvvəl komanda üzvü tərəfindən nəzərdən keçirilir.

jobs:
  terraform:
    runs-on: ubuntu-latest
    steps:
      - name: Terraform Apply
        # yalnız əl ilə başladılanda tətbiq olunur
        if: github.event_name == 'workflow_dispatch'
        run: terraform apply -auto-approve

Bu konfiqurasiya tətbiqin əl ilə işə salınmasını tələb edir — prod dəyişiklikləri avtomatik keçmir.

GitHub Actions-da bunun daha güclü variantı Environment protection rules-dır: prod adlı environment yaradıb ona təsdiq verəcək məsul şəxs (reviewer) təyin edirsiniz. Job həmin environment-ə istinad edəndə pipeline dayanır və təsdiq gözləyir.

c. Avtomat test işlədin

Dəyişikliyi tətbiq etməzdən əvvəl konfiqurasiyanı avtomat testlərlə yoxlayın. 7-ci fəsildə baxdığımız Terratest və ya InSpec kimi vasitələr infrastrukturun gözlənilən kimi işlədiyini təsdiqləyir.

7 · Yadda saxla

  • Plan və apply ayrılmalıdır: plan pull request-də, apply merge-dən sonra. Bu bölgü infrastruktur dəyişikliyini nəzərdən keçirilmiş kodla məhdudlaşdırır.
  • Secret pipeline konfiqurasiyasında yazılmır: GitHub Secrets, Jenkins Credentials və ya GitLab CI Variables işlədin — mümkünsə OIDC ilə müvəqqəti giriş qurun.
  • Prod təsdiq tələb edir: -auto-approve prod-a birbaşa yol açır; təsdiq mərhələsi və ya əl ilə tetikləmə mütləqdir.
  • Mühitlər ayrı olsun: ayrı workspace və ya ayrı pipeline — dev-də sınanmamış heç nə prod-a getməsin.
  • Ardıcıllıq vacibdir: fmt → validate → lint → plan → test → apply. Ucuz yoxlamalar əvvəldə, bahalı olanlar sonda.
