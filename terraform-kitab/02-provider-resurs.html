Provider-lər və Resurslar

DPE-07 · Data Platform & Engineering Bootcamp

Provider Terraform-u xarici dünyaya bağlayan körpüdür, resource isə Terraform-un idarə etdiyi ən kiçik tikinti bloku. Bu fəsildə provider-lərin necə konfiqurasiya olunduğunu, versiyalandığını və alias-larla necə çoxaldıldığını, resource bloklarının quruluşunu, atributları, asılılıqları, lifecycle qaydalarını və provisioner-ləri öyrənəcəksən.

1 · Provider anlayışı

Provider nədir

Terraform-da provider resursların həyat dövrünü idarə etməyə cavabdehdir. Terraform provider-lər vasitəsilə müxtəlif API-larla və bulud platformaları ilə — AWS, Azure, Google Cloud və bir çox başqası ilə — əlaqə qurur. Provider-lər Terraform ilə onun idarə etdiyi infrastruktur arasında körpü rolunu oynayır.

Texniki baxımdan provider-lər Terraform-un xarici sistemlərlə danışmasına imkan verən plugin-lərdir. Bu sistemlər bulud platformaları (AWS, Azure, Google Cloud), SaaS platformaları (GitHub, PagerDuty) və ya infrastruktur xidmətləri (Kubernetes, OpenStack) ola bilər.

Provider-lər Terraform-un idarə edə biləcəyi resource və data source dəstini müəyyən edir. Məsələn, AWS provider-i EC2 instance, S3 bucket, RDS verilənlər bazası kimi AWS resurslarını idarə etməyə imkan verir.

ProviderTəqdim etdiyi resurslardan bəziləri
AWSaws_instance, aws_s3_bucket, aws_vpc
Azureazurerm_virtual_machine, azurerm_storage_account, azurerm_app_service
Google Cloudgoogle_compute_instance, google_storage_bucket

Resurs yaratmazdan əvvəl provider mütləq konfiqurasiya olunmalıdır. Provider konfiqurasiyası adətən autentifikasiya məlumatlarını (giriş açarları və ya token-lər) və region parametrlərini əhatə edir.

2 · Provider-in konfiqurasiyası

provider bloku

Provider-i konfiqurasiya etmək üçün konfiqurasiyada provider bloku yazılır. AWS ilə işləyirsənsə, belə görünür:

provider "aws" {
  region     = "us-west-1"
  access_key = "your-access-key"
  secret_key = "your-secret-key"
}

Bu nümunədə:

  • region — Terraform-un resursları yaradacağı AWS regionunu göstərir (məsələn us-west-1).
  • access_key və secret_key — Terraform-un API sorğularını autentifikasiya etmək üçün işlətdiyi AWS credential-larıdır. Onları ya birbaşa koda yaza bilərsən (təhlükəsizlik baxımından təklif olunmur), ya da AWS_ACCESS_KEY_ID və AWS_SECRET_ACCESS_KEY mühit dəyişənlərindən istifadə edə bilərsən.
Xəbərdarlıq. Credential-ları konfiqurasiya faylına yazma. Kod Git-ə düşən an açarlar açıq şəkildə tarixçəyə yazılır və sonradan tam təmizləmək çətindir. Mühit dəyişəni, AWS profil faylı və ya (EC2/EKS üzərində işləyirsənsə) IAM rolu ən düzgün yoldur.

3 · Bir neçə provider-in idarəsi

Eyni konfiqurasiyada müxtəlif buludlar

Terraform eyni konfiqurasiya daxilində bir neçə provider üzərindən infrastruktur idarə etməyi dəstəkləyir. Məsələn, bir layihədə həm AWS, həm də Google Cloud resurslarını idarə edə bilərsən.

# AWS provider
provider "aws" {
  region = "us-west-1"
}

# Google Cloud provider
provider "google" {
  project = "my-gcp-project"
  region  = "us-central1"
}

# AWS-də EC2 instance
resource "aws_instance" "my_aws_instance" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
}

# Google Cloud-da storage bucket
resource "google_storage_bucket" "my_bucket" {
  name     = "my-storage-bucket"
  location = "US"
}

Burada AWS provider-i EC2 instance yaratmaq üçün, Google Cloud provider-i isə storage bucket yaratmaq üçün işlədilir. Terraform hər resursun adının önündəki prefiksə (aws_, google_) baxaraq hansı provider-in cavabdeh olduğunu özü müəyyən edir.

4 · Provider versiyalandırması

Versiyanı sabitləmək niyə vacibdir

Terraform işlədəcəyin provider versiyasını təyin etməyə imkan verir. Bu vacibdir, çünki bütün mühitlərdə eyni provider versiyasının işlədilməsi provider yeniləmələrindən doğan uyğunsuzluqların (breaking change) qarşısını alır.

provider "aws" {
  version = "~> 2.0" # provider-in 2.x seriyasını işlət
  region  = "us-west-1"
}

version arqumenti Terraform-un AWS provider-inin 2.x versiyasını işlətməsini təmin edir. Dəqiq versiyanı sabitləmək (pin) və ya versiya aralığı göstərmək də mümkündür.

YazılışMənası
= 2.70.0Yalnız bu dəqiq versiya
~> 2.02.x seriyası daxilində ən yeni versiya (3.0-a keçmir)
>= 2.0, < 3.0Aralıq şəklində göstərilmiş məhdudiyyət
Qeyd. Müasir Terraform versiyalarında provider versiyası terraform { required_providers { ... } } bloku daxilində göstərilir; provider blokundakı version arqumenti köhnə üsuldur. Məntiq isə eynidir: versiyanı sərbəst buraxma, sabitlə.

5 · Provider alias-ları

Eyni provider-in bir neçə nüsxəsi

Eyni provider daxilində bir neçə hesab və ya region ilə işləmək lazım gələrsə, provider alias-larından istifadə edirsən. Məsələn, resursları bir neçə AWS regionunda idarə etmək istəyə bilərsən.

# Standart AWS provider (us-west-1)
provider "aws" {
  region = "us-west-1"
}

# Əlavə AWS provider (us-east-1) — alias ilə
provider "aws" {
  alias  = "us_east"
  region = "us-east-1"
}

# Standart regionda resurs (us-west-1)
resource "aws_instance" "west_instance" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
}

# Əlavə regionda resurs (us-east-1)
resource "aws_instance" "east_instance" {
  provider      = aws.us_east
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
}

Bu nümunədə alias = "us_east" olan provider bloku us-east-1 regionu üçün ikinci AWS provider-i qurur, standart provider isə us-west-1 ilə işləyir. east_instance adlı EC2 instance provider = aws.us_east sətri sayəsində us-east-1 regionunda yaradılır.

Məsləhət. Alias-lar çox-regionlu disaster recovery, ACM sertifikatlarının us-east-1-də yaradılması (CloudFront tələbi) və çox-hesablı (multi-account) quruluşlarda əvəzsizdir. Alias adını region və ya hesabın rolu ilə uyğunlaşdır: us_east, prod_account.

6 · Resource anlayışı

Resource nədir

Resource Terraform-un təməl tikinti blokudur. O, Terraform-un idarə etdiyi infrastruktur komponentini təmsil edir. Resurslara nümunə: virtual maşınlar, verilənlər bazaları, storage bucket-lər, load balancer-lər.

Resurslar konfiqurasiya fayllarında resource blokları ilə təyin olunur. Hər resource bloku idarə olunacaq resursun tipini, onu idarə edəcək provider-i və həmin resursun konfiqurasiyasını göstərir.

Blokun quruluşu

resource "<PROVIDER>_<RESOURCE_TYPE>" "<RESOURCE_NAME>" {
  <KONFIQURASIYA>
}
  • <PROVIDER> — resursu idarə edən bulud provayderi (aws, azurerm, google).
  • <RESOURCE_TYPE> — idarə olunan resursun tipi (instance, bucket, vpc).
  • <RESOURCE_NAME> — resursun Terraform daxilindəki adı; bunu sən özün seçirsən.
  • <KONFIQURASIYA> — resursun necə qurulacağını göstərən arqumentlər dəsti.

Nümunə: AWS EC2 instance

resource "aws_instance" "my_instance" {
  ami           = "ami-0c55b159cbfafe1f0" # Amazon Linux AMI
  instance_type = "t2.micro"
}
  • Resurs tipi aws_instance-dır — AWS-də EC2 instance idarə edir.
  • Resurs adı my_instance-dır — Terraform resursu öz daxili state-ində bu adla tanıyır.
  • ami və instance_type EC2 instance-ı konfiqurasiya edən arqumentlərdir.
Qeyd. Resursun Terraform daxilindəki adı (my_instance) buludda görünən ad deyil — o, yalnız konfiqurasiya və state daxilində istinad üçündür. Bu adı sonradan dəyişsən, Terraform resursu silib yenidən yaratmaq istəyəcək.

7 · Resurs atributları

Atributlara müraciət

Terraform-da hər resurs bir sıra atribut təqdim edir. Bu atributlar həm resursu konfiqurasiya etmək, həm də ondan məlumat çıxarmaq üçün işlədilir.

Məsələn, EC2 instance aşağıdakı atributları təqdim edir:

AtributTəyinatı
amiİşlədiləcək Amazon Machine Image-i göstərir
instance_typeInstance-ın ölçüsünü müəyyən edir (məsələn t2.micro)
public_ipInstance-a təyin olunmuş public IP ünvanı — yalnız oxunan (output-only) atribut

Resurs atributlarına konfiqurasiyanın başqa yerlərindən müraciət edə bilərsən:

output "instance_ip" {
  value = aws_instance.my_instance.public_ip
}
Məsləhət. Yalnız oxunan atributlar (məsələn public_ip, id, arn) resurs yaradılana qədər məlum olmur. Elə buna görə terraform plan nəticəsində belə dəyərlər (known after apply) kimi görünür — bu, səhv deyil.

8 · Asılılıqların idarəsi

Terraform ardıcıllığı özü müəyyən edir

Terraform resurslar arasındakı asılılıqları avtomatik idarə edir. O, hansı resursun başqasından asılı olduğunu başa düşür və resursların düzgün ardıcıllıqla yaradılmasını təmin edir.

Məsələn, VPC-dən asılı olan EC2 instance yaradırsansa, Terraform əvvəlcə VPC-nin qurulmalı olduğunu biləcək.

resource "aws_vpc" "my_vpc" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_instance" "my_instance" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
  subnet_id     = aws_vpc.my_vpc.id # EC2 instance VPC-dən asılıdır
}

Bu nümunədə EC2 instance VPC uğurla qurulmayınca yaradılmayacaq. Asılılıq aws_vpc.my_vpc.id istinadı ilə gizli (implicit) şəkildə yaranır — əlavə heç nə yazmağa ehtiyac yoxdur.

Qeyd. Asılılıq konfiqurasiyada birbaşa istinadla görünmürsə (məsələn IAM siyasətinin instance-dan əvvəl hazır olması tələbi), depends_on arqumenti ilə asılılığı açıq şəkildə göstərmək olar.

9 · Resursun həyat dövrü — lifecycle

lifecycle bloku

Terraform lifecycle bloku vasitəsilə resursların həyat dövrünü idarə etməyə imkan verir. Bu, Terraform-un resursun yaradılmasını, yenilənməsini və ya silinməsini necə həyata keçirdiyini fərdiləşdirmək üçün faydalıdır.

ArqumentNə edir
create_before_destroyKöhnə resurs silinməzdən əvvəl yenisinin yaradılmasını təmin edir
prevent_destroyTerraform-un resursu silməsinin qarşısını alır
ignore_changesResursun müəyyən atributlarındakı dəyişikliklərə məhəl qoymamağı bildirir

Nümunə: köhnə EC2 instance silinməzdən əvvəl yenisinin yaradılması:

resource "aws_instance" "my_instance" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  lifecycle {
    create_before_destroy = true
  }
}

Bu halda Terraform köhnə instance-ı silməzdən əvvəl yenisini yaradacaq və beləliklə xidmətin dayanma müddəti minimuma enəcək.

Məsləhət. prevent_destroy = true verilənlər bazası və state saxlayan bucket kimi kritik resurslar üçün ucuz, lakin çox effektiv qorunma vasitəsidir. ignore_changes isə xarici sistemin (məsələn autoscaling və ya operator) dəyişdirdiyi sahələr üçün faydalıdır — Terraform hər plan-da həmin sahəni geri qaytarmağa çalışmaz.

10 · Provisioner-lər

Resurs yarandıqdan sonra əmr işlətmək

Provisioner-lər resurs yaradıldıqdan sonra onun üzərində skript və ya əmr icra etməyə imkan verir. Onlar resursların ilkin hazırlanması (bootstrap) və ya konfiqurasiya işləri üçün faydalıdır.

Nümunə: EC2 instance yaradıldıqdan sonra onun üzərində shell əmrləri işlətmək:

resource "aws_instance" "my_instance" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  provisioner "remote-exec" {
    inline = [
      "sudo apt-get update",
      "sudo apt-get install -y nginx"
    ]
  }

  connection {
    type        = "ssh"
    user        = "ubuntu"
    private_key = file("~/.ssh/id_rsa")
    host        = self.public_ip
  }
}

Burada remote-exec provisioner-i instance yaradıldıqdan sonra onun üzərində əmrləri icra edir. connection bloku isə Terraform-un instance-a necə qoşulacağını göstərir: SSH protokolu, istifadəçi adı, xüsusi açar və hədəf host (self.public_ip — yaradılan instance-ın öz public IP-si).

Xəbərdarlıq. Provisioner-lər son çarə hesab olunur. Onlar deklarativ modeli pozur: Terraform icra olunan əmrlərin nəticəsini state-də izləmir, uğursuzluq halında resurs "yararsız" (tainted) işarələnir. Mümkün olduqda əvəzinə user_data, əvvəlcədən hazırlanmış AMI (Packer) və ya Ansible kimi konfiqurasiya idarəsi aləti işlət.

11 · Yekun

Bu fəsildə Terraform provider-lərini və resurslarını ətraflı nəzərdən keçirdik. Provider-lər xarici sistemlərlə əlaqə üçün vacibdir, resurslar isə Terraform-un idarə etdiyi infrastrukturun təməl vahidləridir. Provider-lərin necə konfiqurasiya olunduğunu, resursların necə təyin edildiyini, asılılıqların necə idarə olunduğunu və resursun həyat dövrünə necə nəzarət edildiyini gördük.

Növbəti fəsildə dəyişənlər, output-lar və data source-lar mövzusuna keçirik — bunlar Terraform konfiqurasiyalarını dinamik və təkrar istifadəyə yararlı etməyin əsas vasitələridir.

12 · Yadda saxla

  • Provider Terraform ilə xarici API arasındakı plugin-dir; resurs yaratmazdan əvvəl mütləq konfiqurasiya olunmalıdır.
  • Provider versiyasını hər zaman sabitlə — versiyasız konfiqurasiya bir gün gözlənilmədən sınacaq.
  • alias eyni provider-in bir neçə region və ya hesab üçün nüsxəsini yaratmağa imkan verir; resursda provider = aws.<alias> ilə seçilir.
  • Resurs adı Terraform daxilində istinad üçündür; dəyişdirsən, resurs silinib yenidən yaradılır.
  • Asılılıqlar atribut istinadı ilə avtomatik qurulur; görünməyən asılılıqlar üçün depends_on var.
  • lifecycle ilə silinməni qadağan et, sıfır dayanma müddəti üçün əvvəl yarat, xarici dəyişikliklərə isə göz yum.
  • Provisioner-lərdən mümkün qədər çəkin — user_data və ya hazır image daha etibarlıdır.
