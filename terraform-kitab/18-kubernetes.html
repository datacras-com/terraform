Kubernetes və EKS

DPE-07 · Data Platform & Engineering Bootcamp

Terraform yalnız virtual maşın və şəbəkə yaratmır — Kubernetes cluster-inin özünü də, onun içindəki iş yüklərini də idarə edə bilir. Bu fəsildə AWS EKS cluster-ini modul ilə qurmağı, Kubernetes provider-ini konfiqurasiya etməyi, Deployment və Service yaratmağı, ConfigMap, Namespace və Horizontal Pod Autoscaler ilə işləməyi öyrənəcəyik.

1 · Niyə Kubernetes üçün Terraform?

Cluster də infrastrukturdur

Kubernetes cluster-ini konsoldan «bir dəfə» qurmaq asandır — problem ikinci dəfə eynisini qurmaq lazım olanda başlayır. Terraform bu prosesi təkrarlana bilən hala gətirir:

  • Avtomatlaşdırma — cluster yaradılması fərqli bulud provider-lərində (AWS EKS, Azure AKS, Google GKE) eyni alətlə avtomatlaşdırılır.
  • Infrastructure as Code — cluster və iş yükləri deklarativ təsvir olunur; dəyişikliklər git tarixçəsində izlənir və mühitlər arasında fərq yaranmır.
  • Multi-cloud dəstəyi — fərqli buludlardakı cluster-lər tək alət dəsti ilə idarə olunur.
  • Miqyaslanma çevikliyi — həm cluster node-larının, həm də iş yüklərinin miqyaslanması konfiqurasiyanın bir hissəsi olur.
Praktik bölgü belədir: cluster və node group üçün Terraform ideal seçimdir; tətbiq deployment-ləri üçün isə çox komanda Helm və ya GitOps (Argo CD, Flux) işlədir. Səbəb sadədir — tətbiq gündə on dəfə deploy olunur, cluster isə ayda bir dəfə dəyişir və bu iki ritmi eyni state faylında saxlamaq gərginlik yaradır.

2 · Əsas anlayışlar

a · Kubernetes üçün provider-lər

Burada iki fərqli provider iştirak edir və onları qarışdırmamaq vacibdir. Bulud provider-i (aws, azurerm, google) cluster-in özünü — control plane, node group, şəbəkə — yaradır. Kubernetes provider-i isə artıq mövcud cluster-in API-si ilə danışır və onun içindəki obyektləri (Deployment, Service, Namespace) idarə edir.

b · Cluster idarəetməsi

Terraform Kubernetes cluster-ini müxtəlif platformalarda yarada bilər: AWS-də EKS, Azure-da AKS, Google Cloud-da GKE. Hər biri üçün öz resursları və hazır modulları var.

c · Resurs idarəetməsi

Cluster hazır olandan sonra Terraform onun daxilindəki obyektləri də idarə edə bilər: Deployment, Service, Namespace, ConfigMap, Ingress. Bu, infrastruktur və iş yükünün vahid iş axınında idarə olunması deməkdir.

3 · Nümunə: AWS EKS cluster-in qurulması

Addım 1 · Provider və EKS modulu

EKS cluster-ini sıfırdan resurs-resurs yazmaq əvəzinə icma tərəfindən dəstəklənən terraform-aws-modules/eks/aws modulundan istifadə edirik. Modul IAM role-ları, security group-ları və node group-ları arxa planda düzgün qurur.

provider "aws" {
  region = "us-west-2"
}

module "eks" {
  source          = "terraform-aws-modules/eks/aws"
  cluster_name    = "my-eks-cluster"
  cluster_version = "1.21"
  subnets         = ["subnet-123456", "subnet-789012"]
  vpc_id          = "vpc-12345678"

  node_groups = {
    eks_nodes = {
      desired_capacity = 2
      max_capacity     = 3
      min_capacity     = 1
      instance_type    = "t3.medium"
    }
  }
}

Bu konfiqurasiyada:

  • AWS provider-i us-west-2 regionu üçün təyin olunur.
  • EKS modulu cluster-i yaradır və onun hansı VPC və subnet-lərdə yerləşəcəyini göstərir.
  • Node group worker node-ları idarə edir: minimum 1, maksimum 3, başlanğıcda 2 node.
Modulun 18-ci versiyasından etibarən arqument adları dəyişib: subnets → subnet_ids, node_groups → eks_managed_node_groups, instance_type → instance_types (siyahı). Həmçinin cluster_version = "1.21" artıq dəstəklənmir — aktual versiyanı seç. Modulu işlədəndə mütləq version = "~> 20.0" kimi versiya kilidi qoy, əks halda modul yenilənəndə konfiqurasiyan gözlənilmədən sınır.
Subnet ID-lərini kodda sabit yazmaq əvəzinə şəbəkəni də Terraform ilə yarat və modula module.vpc.private_subnets kimi istinad et. EKS üçün node-lar private subnet-lərdə, load balancer-lər isə public subnet-lərdə olmalıdır — subnet-lərə uyğun kubernetes.io/role/elb tag-larını qoymağı unutma.

Addım 2 · Kubernetes provider-inin konfiqurasiyası

Cluster hazır olandan sonra onun içinə obyekt yaratmaq üçün Kubernetes provider-i cluster endpoint-inə və sertifikatına bağlanmalıdır.

provider "kubernetes" {
  host                   = module.eks.cluster_endpoint
  cluster_ca_certificate = base64decode(module.eks.cluster_certificate_authority_data)

  exec {
    api_version = "client.authentication.k8s.io/v1beta1"
    command     = "aws"
    args        = ["eks", "get-token", "--cluster-name", module.eks.cluster_name]
  }
}

Burada provider EKS-in endpoint-i və CA sertifikatı ilə cluster-ə qoşulur. exec bloku isə hər dəfə aws eks get-token əmrini çağıraraq qısamüddətli token alır — yəni kodda heç bir sabit kredensial saxlanmır.

Mənbə nümunədə api_version v1alpha1 idi və command sətri ümumiyyətlə yox idi. v1alpha1 artıq işləmir — v1beta1 (və ya yeni versiyalarda v1) işlət və command = "aws" sətrini mütləq əlavə et, yoxsa provider autentifikasiya edə bilməyəcək.
Ən çox rast gəlinən problem: cluster hələ mövcud deyilkən Kubernetes provider-inin konfiqurasiyası hesablanmağa çalışır və plan mərhələsində xəta verir. Ona görə cluster-i və cluster daxilindəki obyektləri ayrı konfiqurasiyalarda (ayrı state) saxlamaq praktikada ən sağlam yanaşmadır: əvvəlcə cluster apply olunur, sonra iş yükləri.

Addım 3 · İş yükünün deploy edilməsi

İndi cluster-ə sadə bir Nginx tətbiqi yerləşdirək — iki replika Deployment və onu xaricə açan LoadBalancer tipli Service.

resource "kubernetes_deployment" "nginx" {
  metadata {
    name      = "nginx-deployment"
    namespace = "default"
  }

  spec {
    replicas = 2

    selector {
      match_labels = {
        app = "nginx"
      }
    }

    template {
      metadata {
        labels = {
          app = "nginx"
        }
      }

      spec {
        container {
          name  = "nginx"
          image = "nginx:1.27"

          ports {
            container_port = 80
          }
        }
      }
    }
  }
}

resource "kubernetes_service" "nginx_service" {
  metadata {
    name      = "nginx-service"
    namespace = "default"
  }

  spec {
    selector = {
      app = "nginx"
    }

    port {
      port        = 80
      target_port = 80
    }

    type = "LoadBalancer"
  }
}

Nəticədə iki replikalı Nginx deployment-i və onu xaricə açan LoadBalancer tipli service yaranır. AWS-də LoadBalancer tipi avtomatik olaraq Elastic Load Balancer yaradır.

image = "nginx:latest" yazmaqdan çəkin. latest tag-ı zamanla fərqli image-a işarə edir — yəni eyni Terraform kodu bu gün və üç ay sonra fərqli nəticə verir və problemi təkrarlamaq mümkün olmur. Konkret versiya (nginx:1.27) və ya digest işlət.

Addım 4 · Tətbiq

terraform init   # provider və modulları yüklə
terraform plan   # planı nəzərdən keçir
terraform apply  # cluster və iş yükünü yarat

Bu ardıcıllıq EKS cluster-ini yaradır, worker node-ları konfiqurasiya edir və Nginx iş yükünü cluster-ə yerləşdirir. EKS cluster-inin tam qalxması adətən 10–15 dəqiqə çəkir — bu normaldır.

4 · Digər Kubernetes resursları

a · Namespace

Namespace resursları məntiqi olaraq ayırır: fərqli komandalar və ya mühitlər eyni cluster-də bir-birinə qarışmadan yaşayır.

resource "kubernetes_namespace" "my_namespace" {
  metadata {
    name = "my-app-namespace"
  }
}

Bu blok my-app-namespace adlı yeni namespace yaradır.

b · ConfigMap

ConfigMap tətbiqin konfiqurasiya məlumatını açar-dəyər cütləri şəklində saxlayır və onu image-dan ayırır — yəni eyni image fərqli mühitlərdə fərqli parametrlərlə işləyə bilər.

resource "kubernetes_config_map" "my_config_map" {
  metadata {
    name      = "app-config"
    namespace = "default"
  }

  data = {
    app_environment = "production"
    app_version     = "v1.0.0"
  }
}

Bu ConfigMap-a deployment içindən istinad edərək mühitə uyğun konfiqurasiya ötürmək olar.

Parol, API açarı və sertifikat ConfigMap-də saxlanmır — onlar üçün Secret var. Amma nəzərə al ki, kubernetes_secret resursunun dəyəri Terraform state faylına açıq mətnlə düşür. Ona görə secret-ləri External Secrets Operator və ya AWS Secrets Manager üzərindən idarə etmək daha təhlükəsizdir.

5 · Autoscaling — HPA

Pod sayını yükə görə tənzimləmək

Kubernetes-in ən güclü xüsusiyyətlərindən biri iş yükünü tələbata görə avtomatik miqyaslamasıdır. Horizontal Pod Autoscaler (HPA) pod sayını metrikaya — adətən CPU istifadəsinə — görə artırıb-azaldır.

resource "kubernetes_horizontal_pod_autoscaler" "nginx_autoscaler" {
  metadata {
    name      = "nginx-hpa"
    namespace = "default"
  }

  spec {
    scale_target_ref {
      kind = "Deployment"
      name = kubernetes_deployment.nginx.metadata[0].name
    }

    min_replicas                      = 2
    max_replicas                      = 10
    target_cpu_utilization_percentage = 50
  }
}

Nümunədə:

  • HPA Nginx deployment-ini 2 ilə 10 replika arasında miqyaslayır.
  • Hədəf CPU istifadəsi 50%-dir — autoscaler bu səviyyəni saxlamaq üçün replika əlavə edir və ya azaldır.
HPA-nın işləməsi üçün cluster-də metrics-server quraşdırılmış olmalıdır və pod-larda resources.requests.cpu təyin edilməlidir. Request yoxdursa, autoscaler faizi nəyə görə hesablayacağını bilmir və miqyaslanma baş vermir. Yeni layihələrdə kubernetes_horizontal_pod_autoscaler_v2 resursunu işlət — o, yaddaş və xüsusi metrikaları da dəstəkləyir.
Autoscaling növüNəyi miqyaslayırNə vaxt lazımdır
HPAPod sayınıTrafik dalğalanmalarında
VPAPod-un CPU/yaddaş limitləriniResurs tələbi bilinməyəndə
Cluster Autoscaler / KarpenterNode sayınıPod-lar yer tapmayanda
HPA və Cluster Autoscaler birlikdə işləyir: HPA pod əlavə edir, pod-a yer çatmayanda Cluster Autoscaler (və ya daha yeni alət olan Karpenter) node əlavə edir. Yalnız HPA qursan, pod-lar Pending vəziyyətində qalacaq.

6 · Best practice-lər

Cluster-i idarə oluna bilən saxlamaq

  • Modul strukturu. Böyük Kubernetes mühitlərində konfiqurasiyanı təkrar işlədilə bilən modullara böl — cluster, node group, addon-lar, iş yükləri ayrı-ayrı.
  • Miqyaslanmanı avtomatlaşdır. İş yükü səviyyəsində HPA, node səviyyəsində Cluster Autoscaler və ya Karpenter.
  • Təhlükəsizlik. Secret, Ingress və RBAC siyasətlərini diqqətlə idarə et. Terraform RBAC role və binding-lərini də kod ilə tətbiq etməyə imkan verir — yəni «kimin nəyə icazəsi var» sualının cavabı review olunan fayl olur.
  • State-i ayır. Cluster infrastrukturu və tətbiq iş yükləri üçün ayrı state faylı saxla — biri sınanda digərinə toxunmasın.
  • Versiyaları kilidlə. Modul, provider və Kubernetes versiyalarını konkret göstər; avtomatik yeniləmə prod cluster-də ən arzuolunmaz yerdir.
AI köməkçisi Kubernetes provider-inin blok sintaksisini (HCL) YAML manifest sintaksisi ilə qarışdıra bilər — məsələn spec.containers siyahısı əvəzinə container bloku lazımdır. Bir Deployment yazdıranda nəticəni terraform validate ilə yoxla; xüsusilə metadata[0].name kimi indeksli istinadlarda modelin təklifi tez-tez səhv olur.

7 · Yadda saxla

  • İki fərqli provider iştirak edir: bulud provider-i cluster-i yaradır, Kubernetes provider-i isə onun içindəki obyektləri idarə edir.
  • Cluster və iş yüklərini ayrı state-də saxla — əks halda cluster mövcud olmayanda plan mərhələsində xəta alacaqsan.
  • EKS modulunun arqument adları versiyalar arasında dəyişir; modulu mütləq versiya kilidi ilə işlət.
  • HPA yalnız metrics-server və resources.requests təyin olunanda işləyir; node səviyyəsində miqyaslanma üçün ona Cluster Autoscaler əlavə et.
  • latest image tag-ından və state-də açıq qalan Secret-lərdən çəkin — hər ikisi prod-da problemin gec üzə çıxan mənbəyidir.
