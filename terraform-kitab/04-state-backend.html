State İdarəsi və Backend-lər

DPE-07 · Data Platform & Engineering Bootcamp

Terraform-ın idarə etdiyi hər resurs barədə məlumat state faylında saxlanılır — bu fayl olmasa Terraform nəyi yaratdığını, nəyi dəyişməli olduğunu bilməz. Bu fəsildə state-in necə işlədiyini, içində nə saxlandığını, niyə onu qorumaq lazım gəldiyini öyrənəcəyik. Sonra remote state və backend anlayışlarına keçib komanda ilə işləyəndə state-i S3, Azure Blob Storage və ya Terraform Cloud-da necə saxlamağı, locking və şifrələməni necə qurmağı görəcəyik.

1 · Terraform state nədir

State — infrastrukturun anlıq şəkli

Terraform idarə etdiyi resursları izləmək üçün terraform.tfstate adlı state faylından istifadə edir. Bu fayl infrastrukturun mövcud konfiqurasiyasının anlıq şəklidir (snapshot): Terraform hansı resursları yaratdığını, yenilədiyini və ya sildiyini məhz oradan bilir.

State olmasaydı, Terraform hər dəfə bulud provider-in API-sinə müraciət edib bütün resursların cari vəziyyətini soruşmalı olardı. State faylı sayəsində isə Terraform mövcud vəziyyəti (state faylında yazılan) arzu olunan vəziyyətlə (.tf fayllarında təsvir edilən) müqayisə edir və yalnız fərqi tətbiq edir.

terraform apply işləyəndə state nəyə cavab verir

  • Hansı resurslar artıq mövcuddur?
  • Hansılar yaradılmalı, hansılar dəyişdirilməli, hansılar silinməlidir?
State faylı Terraform üçün həqiqət mənbəyidir (source of truth). Onu əl ilə redaktə etmək demək olar ki, həmişə səhv addımdır — bunun üçün terraform state alt əmrləri var.

2 · State necə işləyir

Əməliyyat mərhələləri

Terraform resurs yaradanda və ya dəyişəndə state faylını yeniləyir. Məsələn, AWS-də EC2 instance yaradanda instance ID və public IP kimi məlumatlar state-ə yazılır.

MərhələƏmrState ilə nə baş verir
State-in başlanğıcıterraform initBoş state hazırlanır, yaxud remote backend-də mövcud state götürülür
Refreshterraform plan / applyProvider API-si sorğulanır, state-in gerçəkliyə uyğunluğu yoxlanılır
Planterraform planState ilə konfiqurasiya müqayisə olunur, dəyişiklik siyahısı hazırlanır
Applyterraform applyİnfrastruktur dəyişdirilir və state faylı yenilənir
Destroyterraform destroyState oxunur, orada qeyd olunan resurslar tapılıb silinir
Plan mərhələsində gördüyünüz fərqlərin bir hissəsi əslində drift-dir: kimsə konsoldan əl ilə dəyişiklik edib, refresh isə bunu aşkarlayıb. Belə hallarda əvvəl drift-in səbəbini araşdırın, sonra apply edin.

3 · State faylı harada saxlanılır və nə saxlayır

Yerləşmə

Susmaya görə Terraform state faylını Terraform işə salınan qovluqda — yerli olaraq — terraform.tfstate adı ilə saxlayır. Ancaq komanda ilə işlənən layihələrdə bu yanaşma münaqişəyə gətirib çıxarır: eyni infrastrukturu iki nəfər eyni vaxtda dəyişəndə state faylı korlanır. Buna görə də state-i remote backend-də (Amazon S3, Azure Blob Storage və s.) saxlamaq daha düzgündür.

State faylının içindəkilər

  • Resource ID-lər: yaradılmış resursların unikal identifikatorları — EC2 instance ID, S3 bucket adı və s.
  • Resource atributları: IP ünvanları, security group qaydaları, subnet ID-ləri kimi əlavə məlumatlar.
  • Output-lar: output bloklarında təyin etdiyiniz dəyərlər — public IP, verilənlər bazasının endpoint-i və s.
Diqqət: parollar, access key-lər və digər həssas məlumatlar da state faylına açıq mətn şəklində düşə bilər. Buna görə state faylı heç vaxt git repozitoriyasına yüklənməməli, giriş hüququ məhdudlaşdırılmalı və şifrələnməlidir. .gitignore-a *.tfstate və *.tfstate.backup əlavə etmək ilk addımdır.

State niyə bu qədər vacibdir

Dəyişikliyin izlənməsi

State Terraform üçün həqiqət mənbəyidir; apply zamanı hansı dəyişikliyin lazım olduğu ondan çıxarılır.

Sürət

State olmasa, Terraform hər icra üçün bütün resursları API-dən soruşmalı olardı — bu isə əməliyyatları ciddi ləngidərdi.

Artımlı (incremental) dəyişiklik

State sayəsində Terraform hər şeyi yenidən qurmaq əvəzinə yalnız dəyişməli olan komponentləri yeniləyir. Bu, böyük infrastrukturlarda həm vaxta, həm də risk səviyyəsinə birbaşa təsir edir.

4 · Remote state

Remote state nədir

Remote state — state faylının paylaşılan uzaq bir yerdə saxlanmasıdır: S3 bucket, Azure Blob Storage, Google Cloud Storage və ya HashiCorp-un Terraform Cloud xidməti. Beləliklə komandanın bütün üzvləri eyni state faylı ilə işləyir və uyğunluq pozulmur.

XüsusiyyətNə verir
State lockingEyni anda yalnız bir nəfər state-i dəyişə bilir — paralel apply state-i korlaya bilmir
ŞifrələməState faylındakı həssas məlumatlar saxlanma zamanı şifrələnir
VersiyalamaS3 kimi anbarlar state-in köhnə versiyalarını saxlayır — səhv dəyişiklikdən geri qayıtmaq mümkün olur
Fəlakətdən bərpaState faylı yüksək əlçatanlıqlı və davamlı anbarda qalır, yerli maşın sıradan çıxsa itmir

Amazon S3 ilə remote state qurulması

State faylını S3 bucket-də saxlamaq üçün Terraform-u S3 backend-i ilə konfiqurasiya edirik:

terraform {
  backend "s3" {
    bucket  = "my-terraform-state"
    key     = "global/s3/terraform.tfstate"
    region  = "us-west-1"
    encrypt = true
  }
}
  • bucket — state faylının saxlanacağı S3 bucket-in adı.
  • key — bucket daxilində state faylının yolu. Fərqli layihələr üçün fərqli key seçin.
  • region — bucket-in yerləşdiyi AWS region-u.
  • encrypt — state faylının server tərəfli şifrələmə (SSE) ilə saxlanmasını təmin edir.
Bucket-də versioning-i aktivləşdirin. Belə olsa, korlanmış və ya səhvən silinmiş state-in əvvəlki versiyasını bərpa etmək mümkün olur — bu, ən ucuz sığortadır.

DynamoDB ilə state locking

İki nəfərin eyni vaxtda state-i dəyişməsinin qarşısını almaq üçün DynamoDB cədvəli ilə locking qurulur. Beləliklə eyni anda yalnız bir terraform apply icra oluna bilər və state korlanmır. 

terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "global/s3/terraform.tfstate"
    region         = "us-west-1"
    encrypt        = true
    dynamodb_table = "terraform-lock"   # lock cədvəli
  }
}

dynamodb_table arqumenti dəyişikliklər tətbiq olunarkən state-i kilidləmək üçün istifadə ediləcək cədvəli göstərir. Cədvəlin partition key-i LockID adlı string olmalıdır.

Əməliyyat yarımçıq kəsilsə (məsələn, terminal bağlansa) kilid asılı qala bilər. Bu halda terraform force-unlock <LOCK_ID> işlədilir — lakin əvvəlcə əmin olun ki, həqiqətən heç kim apply icra etmir, əks halda state-i korlaya bilərsiniz.

Terraform Cloud backend-i

Remote state üçün başqa bir seçim Terraform Cloud-dur — state saxlanması, locking və komanda əməkdaşlığı üçün hazır dəstəyi var:

  • State idarəsi: state faylları üçün təhlükəsiz uzaq backend.
  • State versiyalanması: versiyalar avtomatik saxlanılır, bərpa mümkündür.
  • Daxili locking: paralel dəyişikliklərin qarşısı alınır.
  • Əməkdaşlıq: GitHub kimi versiya nəzarəti sistemləri ilə inteqrasiya, komanda əsaslı iş axını.
terraform {
  backend "remote" {
    organization = "my-org"

    workspaces {
      name = "my-workspace"
    }
  }
}

5 · Backend-lər

Backend nədir

Terraform-da backend iki şeyi təyin edir: state faylının harada və necə saxlanması, həmçinin Terraform əməliyyatlarının (plan, apply, destroy) harada icra olunması. Susmaya görə local backend işləyir, lakin onu S3, Azure Blob Storage, Google Cloud Storage, Terraform Cloud və digər uzaq variantlarla əvəzləmək olar.

Backend nəyə imkan verir

  • State-i uzaqda saxlamaq: əməkdaşlıq və fəlakətdən bərpa üçün.
  • State locking: eyni vaxtda dəyişikliyin qarşısını almaq.
  • Şifrələmə: state daxilindəki həssas məlumatları qorumaq.
  • Uzaq icra: Terraform Cloud kimi backend-lər plan və apply-ı sizin noutbukda deyil, uzaq mühitdə icra edir.

Backend konfiqurasiyası: Azure Blob Storage

terraform {
  backend "azurerm" {
    storage_account_name = "myterraformstorage"
    container_name       = "tfstate"
    key                  = "terraform.tfstate"
  }
}
  • storage_account_name — state faylının saxlandığı Azure storage account-un adı.
  • container_name — həmin account daxilindəki container.
  • key — state faylının adı.
Backend blokunda dəyişən (var.*) işlətmək olmaz — bu blok Terraform-un ən erkən mərhələsində oxunur. Mühitə görə fərqli dəyərlər lazımdırsa, qismən konfiqurasiya yazıb qalanını əmr sətrindən ötürün: terraform init -backend-config=prod.hcl.

Backend-i tətbiq etmək və state-i köçürmək

Backend bloku əlavə edildikdən sonra terraform init işə salınmalıdır. Terraform mövcud yerli state-i yeni backend-ə köçürməyi təklif edir:

# backend blokunu yazdıqdan sonra
terraform init

# Terraform soruşacaq: mövcud state yeni backend-ə köçürülsün?
# "yes" cavabı verin — state S3-ə/Blob-a yüklənəcək

# backend parametrləri dəyişəndə yenidən konfiqurasiya:
terraform init -reconfigure

# state-in cari məzmununa baxmaq
terraform state list
terraform state show aws_instance.my_instance
State faylını heç vaxt əl ilə açıb redaktə etməyin. Resursu yenidən adlandırmaq üçün terraform state mv, state-dən çıxarmaq üçün terraform state rm, mövcud resursu state-ə əlavə etmək üçün isə terraform import istifadə olunur.

6 · Yekun

Yadda saxla

  • State Terraform-un yaddaşıdır: hansı resursun mövcud olduğunu, ID-lərini və atributlarını orada saxlayır; onsuz artımlı dəyişiklik mümkün deyil.
  • State həssasdır: parol və açarlar açıq şəkildə düşə bilər — git-ə salmayın, şifrələyin, girişi məhdudlaşdırın.
  • Komanda işi = remote state: S3, Azure Blob, GCS və ya Terraform Cloud paylaşılan həqiqət mənbəyi verir.
  • Locking mütləqdir: S3 üçün DynamoDB cədvəli, Terraform Cloud üçün daxili locking — paralel apply state-i korlamasın deyə.
  • Versiyalama bərpa deməkdir: bucket-də versioning aktiv olsun ki, səhv və ya korlanma halında geri qayıda biləsiniz.
