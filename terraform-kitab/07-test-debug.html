Test və Debug

DPE-07 · Data Platform & Engineering Bootcamp

Terraform kodu sadəcə mətn deyil — o, canlı serverləri, verilənlər bazalarını və şəbəkələri idarə edir. Ona görə də səhv bir sətir birbaşa infrastruktura dəyir. Bu fəsildə konfiqurasiyanı prod-a çıxarmazdan əvvəl yoxlamağın yollarını — validate, plan, sandbox mühitində sınaq və Terratest ilə avtomatlaşdırılmış test — və nəsə səhv gedəndə problemi tapmaq üçün debug üsullarını öyrənəcəyik.

1 · Terraform-da testin əhəmiyyəti

Niyə test edirik?

Terraform işlədiyi anda mücərrəd obyektlərlə deyil, faktiki bulud resursları ilə işləyir. Səhv yazılmış bir cidr_block şəbəkəni bağlaya bilər, unudulmuş bir lifecycle qaydası isə verilənlər bazasını silə bilər. Test bu səhvləri hələ kod mərhələsində — heç nə yaradılmamış — tutmaq üçündür.

Testin üç səviyyəsi

SəviyyəNəyi yoxlayırTipik alət
Unit testAyrıca komponent — məsələn, bir modulun öz daxilində düzgün işləməsiterraform validate, tflint
Integration testFərqli hissələrin bir-biri ilə düzgün əlaqəsi (VPC + EC2 + Security Group)Terratest, terraform plan
Acceptance testBütöv infrastrukturun ayağa qalxması və gözlənilən kimi işləməsiTerratest, InSpec
Bu üç səviyyə bir-birini əvəz etmir, tamamlayır. validate ucuz və sürətlidir — hər commit-də işləyə bilər. Terratest isə əsl resurs yaradır, ona görə həm bahalı, həm də yavaşdır — adətən gündə bir dəfə və ya merge-dən əvvəl işlədilir.

2 · terraform validate ilə unit test

Sintaksis və daxili uyğunluq yoxlaması

terraform validate konfiqurasiya fayllarının sintaksisinin düzgün olduğunu və daxilən bir-biri ilə uyğun gəldiyini yoxlayır. Bulud provider-inə heç bir sorğu göndərmir, resurs yaratmır və ya silmir.

terraform validate

Konfiqurasiya düzgündürsə, nəticə belə olur:

Success! The configuration is valid.

Problem varsa, Terraform səhvin harada olduğunu göstərən mesaj qaytarır — çatışmayan arqument, tanınmayan resurs tipi, yanlış tip verilmiş dəyişən və s.

Nəyi tutur, nəyi tutmur

  • Tutur: yazı səhvləri, bağlanmamış mötərizələr, mövcud olmayan dəyişənə istinad, səhv atribut adı.
  • Tutmur: AWS-də olmayan AMI ID, artıq tutulmuş S3 bucket adı, icazə çatışmazlığı — bunlar yalnız plan və ya apply zamanı üzə çıxır.
validate işlətməzdən əvvəl terraform init icra edilməlidir — provider sxemləri olmadan Terraform atributların düzgünlüyünü yoxlaya bilməz. Formatlaşdırma üçün isə ayrıca terraform fmt -check -recursive əmri var; ikisini birlikdə CI-da işlətmək yaxşı vərdişdir.

3 · terraform plan — dəyişiklikləri əvvəlcədən görmək

Tətbiq etmədən öncə baxış

terraform plan testin ən vacib addımıdır. O, mövcud state ilə arzu olunan vəziyyəti müqayisə edir və Terraform-un nə edəcəyini — hansı resursu yaradacağını, dəyişəcəyini və ya siləcəyini — əvvəlcədən göstərir.

terraform plan

Nümunə nəticə:

+ aws_instance.my_instance
      ami:           "ami-0c55b159cbfafe1f0"
      instance_type: "t2.micro"
      ...

Plan: 1 to add, 0 to change, 0 to destroy.

Simvolların mənası

SimvolMənasıDiqqət səviyyəsi
+Yeni resurs yaradılacaqAdi
~Mövcud resurs dəyişdiriləcək (yerində)Orta — hansı atribut dəyişir, oxu
-Resurs silinəcəkYüksək
-/+Resurs silinib yenidən yaradılacaqÇox yüksək — data itkisi ola bilər
Plan nəticəsində -/+ (replace) görsəniz, dayanın və səbəbini araşdırın. Verilənlər bazası və ya disk üçün bu, məlumatın silinməsi deməkdir. Terraform hansı atributun dəyişməni məcbur etdiyini forces replacement qeydi ilə göstərir.
Planı fayla yazıb sonra tam eyni planı tətbiq etmək olar — CI/CD-də bu, plan ilə apply arasında heç nəyin dəyişmədiyinə zəmanət verir: 
terraform plan -out=tfplan
terraform apply tfplan

4 · Sandbox mühitində apply ilə test

Kodun faktiki davranışını yoxlamaq

plan yalnız Terraform-un niyyətini göstərir. Resursun həqiqətən ayağa qalxıb-qalxmadığını, tətbiqin bağlantı qura bildiyini isə ancaq apply göstərir. Ona görə də dəyişiklikləri əvvəlcə ayrıca sandbox, dev və ya staging mühitində tətbiq edirik.

terraform apply

Nümunə nəticə:

aws_instance.my_instance: Creating...
aws_instance.my_instance: Creation complete after 30s [id=i-0abcd1234]

Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

Sandbox-da hər şey gözlənildiyi kimi işləyirsə, eyni kodu prod mühitinə çıxarmaq olar. Mühitlərin ayrılması üçün workspace-lərdən və ya ayrı state fayllarından istifadə edin — 5-ci fəsildə baxdığımız kimi.

Sandbox mühiti prod-un kiçildilmiş surəti olmalıdır: eyni region, eyni provider versiyası, oxşar şəbəkə quruluşu. Fərqli quruluşda keçən test prod-da keçəcəyinə zəmanət vermir.
Test bitəndən sonra terraform destroy ilə sandbox resurslarını silin. Unudulmuş test resursları aylıq bulud xərcinin sakit artım mənbəyidir.

5 · Terratest ilə avtomatlaşdırılmış test

Terratest nədir?

Terratest — Go dilində yazılmış, Terraform kodu üçün avtomat test yazmağa imkan verən kitabxanadır. O, infrastrukturu qurur, yoxlamaları icra edir, sonra hər şeyi özü silir. Integration və acceptance testləri üçün ən çox işlədilən vasitədir.

Terratest ilə nə etmək olar:

  • Go dilində Terraform kodunu yoxlayan test yazmaq.
  • İnfrastrukturu qurub üzərində faktiki yoxlamalar aparmaq — EC2 instansına ping atmaq, load balancer-in cavab verdiyini təsdiqləmək, portun açıq olduğunu yoxlamaq.
  • Test bitən kimi infrastrukturu avtomatik dağıtmaq.

Nümunə: EC2 instansının yoxlanması

package test

import (
  "testing"
  "github.com/gruntwork-io/terratest/modules/aws"
  "github.com/gruntwork-io/terratest/modules/terraform"
)

func TestTerraformEC2Instance(t *testing.T) {
  terraformOptions := &terraform.Options{
    // Terraform kodunun yolu
    TerraformDir: "../examples/terraform-aws-ec2-instance",
  }

  // Test bitəndə resursları sil (defer — funksiyanın sonunda işləyir)
  defer terraform.Destroy(t, terraformOptions)

  // `terraform init` və `terraform apply` icra et
  terraform.InitAndApply(t, terraformOptions)

  // Yeni yaradılmış instansın ID-sini output-dan götür
  instanceID := terraform.Output(t, terraformOptions, "instance_id")

  // EC2 instansının işlədiyini təsdiqlə
  aws.AssertInstanceIsRunning(t, instanceID, "us-west-1")
}

Bu testdə Terraform əvvəlcə EC2 instansını qurur, sonra onun həqiqətən running vəziyyətində olduğu təsdiqlənir. Test bitən kimi terraform destroy avtomatik işə düşür.

defer terraform.Destroy(...) sətrini apply-dan əvvəl yazmaq vacibdir. Go-da defer funksiyanın sonunda icra olunur — belə yazsanız, test ortada uğursuz olsa belə resurslar yenə silinəcək.

Quraşdırma və işə salma

1. Go quraşdırın:

brew install go                 # macOS
sudo apt-get install golang-go  # Ubuntu

2. Layihəni hazırlayın və Terratest-i əlavə edin:

go mod init my_terraform_tests
go get github.com/gruntwork-io/terratest/modules/terraform

3. Testləri işə salın:

go test -v -timeout 30m
Terratest testləri əsl bulud resursları yaradır, ona görə Go-nun standart 10 dəqiqəlik limiti tez-tez çatmır. -timeout 30m kimi açıq limit vermək demək olar ki, həmişə lazımdır.

6 · Debug — problemi tapmaq

a. Debug loglarını aktivləşdirmək

Terraform TF_LOG mühit dəyişəni vasitəsilə ətraflı log yazır. DEBUG səviyyəsi hər addımı, o cümlədən provider-ə göndərilən API sorğularını göstərir.

export TF_LOG=DEBUG
terraform apply

Log səviyyələri: TRACE (ən ətraflı), DEBUG, INFO, WARN, ERROR. Logu ekran əvəzinə fayla yönləndirmək daha rahatdır:

export TF_LOG=DEBUG
export TF_LOG_PATH=./terraform-debug.log
terraform apply
Debug logunda provider-ə göndərilən sorğuların məzmunu görünür — orada parol, token və digər həssas dəyərlər ola bilər. Log faylını heç vaxt repository-yə commit etməyin və başqası ilə paylaşmadan əvvəl təmizləyin.

b. State-ə baxmaq

Terraform gözlənilməz davranırsa, ilk baxılacaq yer state faylıdır. O, Terraform-un infrastruktur haqqında "bildiyi" hər şeyi saxlayır.

terraform show                    # state-in tam məzmunu
terraform state list              # idarə olunan resursların siyahısı
terraform state show aws_instance.my_instance   # bir resursun detalları

Resurs state-də yoxdursa, Terraform onu yenidən yaratmağa çalışacaq. Əksinə, silinmiş resurs hələ də state-də qalıbsa, plan gözlənilməz nəticə verəcək.

c. Asılılıqları debug etmək

Terraform resurslar arasındakı asılılıqları özü müəyyən edir və düzgün sıra ilə işə salır. Sıra ilə bağlı şübhəniz varsa, asılılıq qrafını görüntüləyin:

terraform graph | dot -Tsvg > graph.svg

Bu əmr resurslar arasındakı əlaqələrin qrafik təsvirini yaradır — hansı resursun hansından asılı olduğunu vizual görmək sıra problemlərini tapmağı asanlaşdırır.

dot əmri Graphviz paketinin bir hissəsidir: brew install graphviz və ya sudo apt-get install graphviz.

7 · Tez-tez rast gəlinən xətalar

Səhv və həlli

1. Resurs artıq mövcuddur

Terraform yaratmağa çalışdığı resursun artıq buludda olduğunu bildirirsə, demək resurs faktiki mövcuddur, amma state-də yoxdur. Həll — onu state-ə import etmək:

terraform import <resurs_ünvanı> <ID>
terraform import aws_instance.my_instance i-0abcd1234

2. Timeout xətaları

Bəzi resurslar (RDS, EKS klasteri, NAT Gateway) yaranmaq üçün uzun vaxt tələb edir və Terraform-un standart gözləmə müddəti çatmaya bilər. Resurs daxilində timeouts bloku ilə limiti artırın:

resource "aws_instance" "my_instance" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  # Yaratma əməliyyatı üçün 10 dəqiqəlik limit
  timeouts {
    create = "10m"
    update = "10m"
    delete = "15m"
  }
}

Xülasə cədvəli

SimptomEhtimal olunan səbəbİlk addım

AI köməkçisindən istifadə edərkən xəta mesajını olduğu kimi verin — kəsilmiş mətn əvəzinə tam log parçası. Bununla yanaşı, əlaqəli resurs blokunu da göstərin: səbəb çox vaxt xətanın özündə deyil, ona istinad edən konfiqurasiyadadır. Loqu paylaşmadan öncə token və parolları təmizləyin.

8 · Yadda saxla

  • Üç səviyyə: unit (validate), integration (plan, Terratest), acceptance (faktiki mühitdə yoxlama). Ucuzdan bahaya doğru irəliləyin.
  • Plan oxumaq bacarıqdır: + yaradır, ~ dəyişir, - silir, -/+ silib yenidən yaradır. Sonuncunu görəndə dayanıb səbəbi araşdırın.
  • Sandbox mütləqdir: heç bir dəyişiklik dev və ya staging mühitindən keçmədən prod-a getməməlidir.
  • Terratest resurs yaradır: defer terraform.Destroy(...) sətrini apply-dan əvvəl yazın ki, test uğursuz olsa belə təmizlik işləsin.
  • Debug ardıcıllığı: əvvəlcə terraform show ilə state-ə bax, sonra TF_LOG=DEBUG ilə logu oxu, asılılıq şübhəsi varsa terraform graph işlət.
