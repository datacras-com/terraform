Uyğunluq (Compliance) və Audit

DPE-07 · Data Platform & Engineering Bootcamp

Infrastruktur yalnız işləməklə kifayətlənmir — o həm də təhlükəsizlik standartlarına, qanunvericiliyə və şirkətdaxili qaydalara cavab verməlidir. Bu fəsildə uyğunluq qaydalarını kod şəklində yazmağı (Policy as Code), Sentinel və OPA ilə yoxlamaları CI/CD-yə qoşmağı, həssas məlumatı düzgün idarə etməyi və audit üçün log toplamağı öyrənirik.

1 · IaC-də uyğunluq nə deməkdir?

Üç fərqli təbəqə

Infrastructure as Code-da uyğunluq (compliance) yerləşdirdiyin infrastrukturun müəyyən təhlükəsizlik və tənzimləyici tələblərə cavab verməsi deməkdir. Praktikada üç təbəqəyə bölünür:

NövNəyi tələb edirTerraform-da necə görünür
Təhlükəsizlik uyğunluğuŞəbəkə bölgüsü, şifrələmə, giriş nəzarətiŞifrələnməmiş bucket-i qadağan edən policy
Tənzimləyici uyğunluqGDPR, HIPAA, SOC 2, PCI DSSLog saxlama müddəti, data yerləşmə regionu
Əməliyyat uyğunluğuDaxili qaydalar: resource idarəetməsi, xərc nəzarətiMəcburi tag-lar, icazə verilən instance ölçüləri

Terraform bu qaydaları kod şəklində tətbiq etmək üçün mexanizmlər verir — yəni uyğunluq yoxlaması sənədə yazılmış tövsiyə deyil, pipeline-ı dayandıran avtomatik nəzarətə çevrilir.

2 · Əsas uyğunluq problemləri

a. Konfiqurasiya sürüşməsi (drift)

Drift infrastrukturun faktiki vəziyyəti Terraform kodunda təsvir olunan arzuolunan vəziyyətdən ayrıldıqda yaranır. Adətən səbəb sadədir: kimsə konsoldan əl ilə dəyişiklik edir. Nəticədə kod “şifrələmə açıqdır” deyir, gerçəklikdə isə kimsə onu söndürüb — bu artıq uyğunluq pozuntusudur.

b. Giriş nəzarəti və secret idarəetməsi

Həssas resource-lara (baza, S3 bucket) girişin məhdudlaşdırılması və secret-lərin (API açarı, kredensial) təhlükəsiz saxlanması demək olar ki, bütün standartların əsas tələbidir.

c. Tənzimləyici hesabatlıq

Bir çox tənzimləmə təşkilatdan uyğunluğu sübut edən hesabat tələb edir. Infrastruktur dəyişikliklərini əl ilə izləyib hesabat hazırlamaq praktiki olaraq mümkün deyil — avtomatlaşdırma məcburiyyətdir.

Drift-ə qarşı sadə vərdiş: CI-da gündəlik cədvəl üzrə terraform plan -detailed-exitcode işə sal. Çıxış kodu 2 olarsa, deməli infrastrukturda kodla üst-üstə düşməyən nəsə var — komandaya bildiriş göndər.

3 · Policy as Code (PaC)

Anlayış

Policy as Code — uyğunluq qaydalarının eynilə infrastruktur kimi kod şəklində yazılması metodologiyasıdır. Bu yanaşma ilə qaydalar bütün infrastruktura avtomatik tətbiq olunur, versiyalanır və baxışdan keçir. Terraform bir neçə PaC aləti ilə inteqrasiya olunur.

a. Sentinel

Sentinel — HashiCorp-un Terraform ilə işləmək üçün hazırladığı Policy as Code çərçivəsidir. Yazdığın policy-lər dəyişiklik tətbiq olunmazdan əvvəl plan üzərində qiymətləndirilir.

Nümunə: AWS instance ölçüsünü məhdudlaşdıran Sentinel policy

import "tfplan/v2" as tfplan

# yalnız t2.micro və t2.small ölçülərinə icazə verilir
main = rule {
  all tfplan.resource_changes as _, rc {
    rc.change.after.instance_type is "t2.micro" or
    rc.change.after.instance_type is "t2.small"
  }
}

Bu nümunədə:

  • Policy yalnız t2.micro və t2.small tiplərinə icazə verir.
  • Daha böyük instance yerləşdirmək cəhdi olarsa, dəyişiklik bloklanır.

Sentinel ilə geniş dairədə tələblər tətbiq etmək olar: resource tiplərinin məhdudlaşdırılmasından tutmuş tag standartlarına və məcburi şifrələməyə qədər.

b. Open Policy Agent (OPA)

OPA — açıq mənbəli, ümumi təyinatlı policy mühərrikidir. Sentinel-dən fərqli olaraq yalnız Terraform ilə məhdudlaşmır: Kubernetes, API gateway və digər sistemlərdə eyni dil (Rego) ilə işləyir.

Nümunə: S3 bucket-lər üçün şifrələməni məcburi edən OPA policy

package terraform.s3

# şifrələməsi olmayan hər S3 bucket rədd edilir
deny[msg] {
  input.resource_type == "aws_s3_bucket"
  input.config.server_side_encryption_configuration == null
  msg = "S3 bucket-də şifrələmə aktiv olmalıdır."
}

Bu policy server-side şifrələməsi olmayan istənilən S3 bucket-i rədd edir və beləliklə təhlükəsizlik standartına riayəti təmin edir.

Seçim məsləhəti: Terraform Cloud/Enterprise işlədirsənsə, Sentinel daha az konfiqurasiya tələb edir. Öz CI/CD-nizdə qalırsınızsa və ya artıq Kubernetes-də Gatekeeper işlədirsinizsə, OPA ilə tək policy bazasında qalmaq daha səmərəlidir.

4 · Uyğunluq yoxlamalarının CI/CD-də avtomatlaşdırılması

GitHub Actions + OPA

Uyğunluq yoxlamalarını pipeline-a qoşmaqla infrastruktur dəyişikliklərinin tətbiqdən əvvəl qaydalarla üzləşdirilməsini təmin edirsən.

name: Terraform Compliance Check

on:
  pull_request:
    branches: [main]

jobs:
  terraform:
    runs-on: ubuntu-latest
    steps:
      - name: "Repo-nu yüklə"
        uses: actions/checkout@v2

      - name: "Terraform quraşdır"
        uses: hashicorp/setup-terraform@v1

      # plan-ı JSON-a çevir ki, OPA onu oxuya bilsin
      - name: "Plan hazırla"
        run: |
          terraform init
          terraform plan -out=tfplan
          terraform show -json tfplan > terraform-plan.json

      - name: "OPA policy yoxlaması"
        run: opa eval --data policy.rego --input terraform-plan.json --format pretty

Bu nümunədə:

  • Pipeline Terraform plan çıxışını OPA policy-ləri ilə qiymətləndirir.
  • Qayda pozularsa (məsələn, şifrələməsiz S3 bucket), pipeline uğursuz olur və dəyişiklik tətbiq edilmir.
Tez-tez buraxılan səhv: policy yoxlaması apply-dan sonra qoyulur və ya nəticəsi pipeline-ı dayandırmır (“warning” rejimi). Belə qurğu heç nə qorumur — yoxlama apply-dan əvvəl olmalı və uğursuzluq job-u dayandırmalıdır.

5 · Həssas məlumat və secret-lərin idarəsi

AWS Secrets Manager nümunəsi

API açarları, baza kredensialları və giriş token-ləri uyğunluğun ən çox yoxlanan nöqtəsidir. Terraform bir sıra secret idarəetmə alətləri ilə inteqrasiya olunur ki, həssas məlumat təhlükəsiz saxlanılsın və icra anında oxunsun.

data "aws_secretsmanager_secret" "db_password" {
  name = "my-database-password"
}

resource "aws_db_instance" "my_db" {
  allocated_storage = 20
  engine            = "mysql"
  instance_class    = "db.t2.micro"
  # parol konfiqurasiyada saxlanmır, icra anında gətirilir
  password = data.aws_secretsmanager_secret.db_password.secret_string
}

Beləliklə parol Terraform konfiqurasiyasında qalmır — o, hər icrada secret store-dan təhlükəsiz oxunur.

Əlavə qat: secret-i tam çıxarmaq mümkün olduqda daha yaxşısını et — parolu ümumiyyətlə Terraform-a vermə. AWS RDS-də manage_master_user_password = true ilə parolu birbaşa RDS Secrets Manager-ə həvalə edə bilərsən; onda parol nə kodda, nə də state-də görünür.

6 · Uyğunluq üçün loglama və audit

a. AWS CloudTrail

Tənzimləyici tələbləri qarşılamaq üçün təşkilatlar infrastruktur dəyişikliklərinin və həssas resource-lara girişin ətraflı log-unu saxlamalıdır. CloudTrail Terraform-un etdiyi bütün API sorğularını qeydə alır: kim tətbiq edib, hansı resource dəyişib.

resource "aws_cloudtrail" "my_trail" {
  name                          = "my-trail"
  s3_bucket_name                = aws_s3_bucket.my_bucket.id
  include_global_service_events = true   # IAM kimi qlobal xidmətlər də daxil
  is_multi_region_trail         = true   # bütün region-ları əhatə edir
  enable_logging                = true
}

Bu konfiqurasiya bütün Terraform fəaliyyətinin loglanmasını təmin edir və SOC 2, PCI DSS kimi standartların tələb etdiyi audit izini yaradır.

b. Azure Monitor

Azure tərəfində eyni rolu Azure Monitor diaqnostika parametrləri oynayır:

resource "azurerm_monitor_diagnostic_setting" "example" {
  name               = "example-setting"
  target_resource_id = azurerm_storage_account.example.id

  log {
    category = "Administrative"   # yaratma, silmə kimi inzibati əməliyyatlar
    enabled  = true

    retention_policy {
      enabled = true
      days    = 365            # log-lar 1 il saxlanır
    }
  }
}

Burada bütün inzibati əməliyyatlar (resource yaratma, silmə) loglanır və 365 gün saxlanır.

Audit log-un öz təhlükəsizliyi: log saxlanan bucket-ə silmə icazəsi olan hər kəs izləri yox edə bilər. CloudTrail bucket-ində object lock və ya ən azı MFA delete tələb et, log bucket-ini isə ayrı account-da saxla.

7 · Uyğunluq üçün ən yaxşı praktikalar

a. Fasiləsiz uyğunluq

Uyğunluq yoxlamaları infrastruktur həyat dövrünün hər mərhələsinə qoşulmalıdır. CI/CD-də və mövcud infrastrukturun müntəzəm skan edilməsində avtomatik yoxlamalar işlədikcə qaydaya uyğun olmayan resource-un mühitə düşmə riski azalır.

b. Policy as Code-u komandalar arasında standartlaşdır

Sentinel və ya OPA policy-lərini ayrı repo-da saxla, bütün komandalar oradan istifadə etsin. Qaydalar da kod kimi baxışdan keçməli və tələblər dəyişdikcə yenilənməlidir.

c. Müntəzəm audit və monitorinq

CloudTrail, Azure Monitor və ya Google Cloud Logging ilə mütəmadi audit qur. Müntəzəm yoxlama həm standartlara riayəti təsdiqləyir, həm də icazəsiz dəyişikliyi erkən üzə çıxarır.

Copilot ilə iş: Rego sintaksisi ilk baxışda yad gəlir. Copilot-dan “bu Terraform plan JSON strukturuna əsasən bütün aws_s3_bucket resource-larında versiyalamanın açıq olmasını tələb edən deny qaydası yaz” tipli konkret göstərişlə başla, sonra qaydanı opa test ilə həm müsbət, həm mənfi nümunə üzərində yoxla — model çox vaxt sahə adlarını (resource_changes, change.after) qarışdırır.

8 · Yadda saxla

  • Uyğunluq üç təbəqədən ibarətdir: təhlükəsizlik, tənzimləyici tələblər və daxili əməliyyat qaydaları — hər üçü kodla tətbiq oluna bilər.
  • Policy as Code qaydanı sənəddən pipeline-a köçürür: Sentinel Terraform Cloud üçün, OPA/Rego isə çoxplatformalı mühitlər üçün daha uyğundur.
  • Policy yoxlaması apply-dan əvvəl işləməli və pozuntu halında pipeline-ı dayandırmalıdır.
  • Secret-ləri Secrets Manager / Key Vault-dan oxu; mümkün olan yerdə parolu ümumiyyətlə Terraform-dan kənarda saxla.
  • CloudTrail və Azure Monitor audit izini yaradır — log saxlama müddətini standartın tələb etdiyi qədər təyin et və log-ların özünü silinmədən qoru.
