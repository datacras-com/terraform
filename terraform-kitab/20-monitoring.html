Monitorinq və Loqlama

DPE-07 · Data Platform & Engineering Bootcamp

İnfrastrukturu qurmaq işin yarısıdır — onun sağlam işlədiyini bilmək ikinci yarısıdır. Bu fəsildə Terraform ilə AWS CloudWatch və Azure Monitor-u konfiqurasiya edəcəyik: metric izləyəcəyik, hədd aşılanda alarm qurduracağıq və loqları mərkəzləşdirəcəyik. Bu, kitabın son fəslidir — sonda bundan sonra nə etmək lazım olduğuna dair qısa yol xəritəsi var.

1 · Monitorinq və loqlama niyə vacibdir

Problemi istifadəçi sənə deməzdən əvvəl bilmək

Monitorinqin məqsədi sadədir: nasazlıq istifadəçiyə çatmamış aşkarlansın. Bunun dörd əsas faydası var:

  • Performans izləmə — tətbiq və servislərin göstəricilərini izləmək onların SLA-lara cavab verdiyini yoxlamağa imkan verir.
  • Xəta aşkarlama — loqlar nasazlığın səbəbini tapmaq üçün əsas mənbədir. Loq yoxdursa, təxmin etməkdən başqa yol qalmır.
  • Təhlükəsizlik nəzarəti — giriş cəhdləri, siyasət dəyişiklikləri kimi hadisələri qeyd etmək pozuntuları vaxtında görməyə kömək edir.
  • Avtomatik xəbərdarlıq — əvvəlcədən təyin olunmuş hədd aşılanda və ya anomaliya görünəndə komandaya dərhal bildiriş getsin.
Monitorinqi «sonra əlavə edərik» siyahısına salmaq ən bahalı qərarlardan biridir. Terraform-da monitorinq resource-larını izlədikləri resource-la eyni modulda saxla — belədə yeni servis yaradan hər kəs onunla birgə alarm da alır.

2 · Terraform ilə monitorinqin üç hissəsi

a. İnfrastruktur monitorinqi

Terraform AWS CloudWatch, Azure Monitor və Google Cloud Monitoring kimi vasitələri konfiqurasiya edə bilər. CPU istifadəsi, yaddaş, şəbəkə trafiki kimi metric-lər avtomatik yığılır və təhlil olunur.

b. Loqlama

Loqlar infrastrukturda baş verən hadisələrin ətraflı qeydidir. Terraform ilə AWS CloudWatch Logs, Azure Log Analytics və Google Cloud Logging qurulur — loqlar toplanır, saxlanılır və təhlil edilir.

c. Alarmlar

Əvvəlcədən müəyyən edilmiş həddlərə əsaslanan alarm-lar problem böyüməmiş reaksiya verməyə imkan verir. Terraform bütün platformalarda bildiriş mexanizmini konfiqurasiya edə bilir.

3 · Nümunə — AWS CloudWatch ilə metric və alarm

a. CPU alarmı

EC2 instance-ın CPU istifadəsini izləyək və hədd aşılanda xəbərdarlıq göndərək.

resource "aws_cloudwatch_metric_alarm" "high_cpu_alarm" {
  alarm_name          = "HighCPUAlarm"
  comparison_operator = "GreaterThanThreshold"
  # 2 ardıcıl dövr hədd aşılsa alarm işə düşsün
  evaluation_periods  = 2
  metric_name         = "CPUUtilization"
  namespace           = "AWS/EC2"
  # Hər dövr 300 saniyə = 5 dəqiqə
  period              = 300
  statistic           = "Average"
  threshold           = 80
  alarm_actions       = [aws_sns_topic.alert_topic.arn]

  # Hansı instance izlənilir
  dimensions = {
    InstanceId = aws_instance.my_instance.id
  }
}

Bu nümunədə:

  • CloudWatch EC2 instance-ın CPUUtilization metric-ini izləyir.
  • Orta CPU istifadəsi iki ardıcıl 5 dəqiqəlik dövr ərzində 80%-i keçsə, alarm işə düşür.
  • alarm_actions alarm işə düşəndə nə baş verəcəyini deyir — burada SNS topic-ə mesaj göndərilir.
evaluation_periods = 2 təsadüfi seçilməyib. Bir dövrlə alarm qursan, qısamüddətli sıçrayışlar da xəbərdarlıq yaradacaq və komanda tezliklə bildirişlərə fikir verməyi dayandıracaq. Bu, «alert fatigue» adlanır və monitorinqin ən çox rast gəlinən uğursuzluq səbəbidir.

b. SNS ilə bildiriş qurmaq

Alarm işə düşəndə kimsə xəbər tutmalıdır. AWS-də bunun üçün Simple Notification Service (SNS) istifadə olunur.

resource "aws_sns_topic" "alert_topic" {
  name = "cpu-alerts-topic"
}

resource "aws_sns_topic_subscription" "email_subscription" {
  topic_arn = aws_sns_topic.alert_topic.arn
  protocol  = "email"
  # Bildiriş göndəriləcək ünvanı öz ünvanınla əvəz et
  endpoint  = "admin@example.com"
}

Bu konfiqurasiyada SNS topic yaradılır və ona e-poçt abunəliyi əlavə olunur. CPU alarmı işə düşəndə göstərilən ünvana bildiriş gedir.

E-poçt abunəliyi təsdiq tələb edir. Terraform apply uğurla bitsə də, ünvan sahibi məktubdakı linkə klikləyənə qədər abunəlik pending confirmation vəziyyətində qalır və bildiriş gəlmir. Alarm qurduqdan sonra onu qəsdən işə salıb bildirişin gəldiyini yoxla.
E-poçt tək kanal olaraq zəifdir — gecə saat 3-də kimsə poçta baxmır. Prod üçün SNS-i Slack, PagerDuty və ya Opsgenie ilə birləşdir; SNS bunları HTTPS endpoint və ya Lambda vasitəsilə dəstəkləyir.

4 · Nümunə — Azure Monitor ilə metric və alert

a. Virtual maşın üçün CPU alert-i

Azure Monitor Azure infrastrukturunun performansını izləmək üçün əhatəli həlldir. Virtual maşının CPU istifadəsinə görə alert quraq.

resource "azurerm_monitor_metric_alert" "cpu_alert" {
  name                = "HighCPUAlert"
  resource_group_name = azurerm_resource_group.example.name
  # Hansı resurs izlənilir
  scopes              = [azurerm_linux_virtual_machine.example.id]
  description         = "CPU istifadəsi 80%-i keçəndə xəbərdarlıq"

  criteria {
    metric_name      = "Percentage CPU"
    aggregation      = "Average"
    operator         = "GreaterThan"
    threshold        = 80
    dimensions       = []
    time_grain       = "PT1M"
    metric_namespace = "microsoft.compute/virtualmachines"
  }

  action {
    action_group_id = azurerm_monitor_action_group.example.id
  }
}

Bu nümunədə:

  • Azure Monitor virtual maşının CPU istifadəsini izləyir.
  • Müəyyən vaxt aralığında orta CPU 80%-i keçsə, alert işə düşür.
  • time_grain = "PT1M" ISO 8601 formatındadır və «1 dəqiqə» deməkdir.

b. Action Group — bildirişin çatdırılması

Azure-da alert-in kimə və necə çatacağını action group müəyyən edir. Bir action group-u bir neçə alert-ə qoşmaq olar.

resource "azurerm_monitor_action_group" "example" {
  name                = "my-action-group"
  resource_group_name = azurerm_resource_group.example.name
  # SMS və push bildirişlərində görünən qısa ad (maks. 12 simvol)
  short_name          = "alertgrp"

  email_receiver {
    name          = "emailalerts"
    email_address = "admin@example.com"
  }
}

Burada action group göstərilən ünvana e-poçt göndərir — CPU alert-i hər dəfə işə düşəndə.

Action group-u ayrıca resource kimi saxlamağın üstünlüyü: bildiriş ünvanı dəyişəndə onlarla alert-i deyil, bir resource-u redaktə edirsən. Bunu modul çıxışı (output) kimi ver, bütün komandalar eyni qrupdan istifadə etsin.

5 · Loqlama infrastrukturu

AWS CloudWatch Logs

CloudWatch Logs EC2, Lambda, RDS kimi AWS resource-larının sistem və tətbiq loqlarını toplayır. Terraform ilə log group-u əvvəlcədən yaratmaq saxlanma müddətinə nəzarət etməyə imkan verir.

resource "aws_cloudwatch_log_group" "my_log_group" {
  name = "/aws/lambda/my_lambda_logs"
  # Loqlar 7 gün saxlanılır, sonra silinir
  retention_in_days = 7
}

resource "aws_lambda_function" "my_lambda" {
  function_name = "MyLambdaFunction"
  handler       = "lambda_function.lambda_handler"
  runtime       = "python3.8"
  filename      = "lambda_function.zip"

  environment {
    variables = {
      LOG_GROUP_NAME = aws_cloudwatch_log_group.my_log_group.name
    }
  }
}

Bu nümunədə:

  • Lambda function-un loqlarını toplamaq üçün CloudWatch Logs qurulur.
  • Loqlar 7 gün saxlanılıb silinir — bu, saxlama xərcini nəzarətdə saxlayır.
Log group-u özün yaratmasan, Lambda ilk işə düşəndə onu avtomatik yaradır və saxlanma müddəti «Never expire» olur. Yəni loqlar əbədi qalır və hər ay hesab artır. Bu, Terraform ilə idarə olunmayan resource-un necə səssizcə pul yediyinə klassik nümunədir.

6 · Monitorinq və loqlama qaydaları

a. Monitorinqi avtomatlaşdır

Monitorinq və loqlamanı Terraform ilə qur. Belədə bütün kritik resurslar istisnasız izlənilir və loqlar hər mühitdə eyni cür toplanır. Əl ilə konsoldan qurulan alarm həmişə unudulan resource-lar buraxır.

b. Kritik hadisələr üçün alarm qoy

CPU, yaddaş, şəbəkə trafiki kimi əsas metric-lər üçün alarm mütləq olsun. Bildirişi çatdırmaq üçün AWS SNS, Azure Monitor Action Group və ya Google Cloud Alerts istifadə et.

Yaxşı meyar: hər alarm bir hərəkət tələb etməlidir. Əgər alarm gələndə komandanın edəcəyi bir iş yoxdursa, o alarm deyil — səs-küydür. Onu ya sil, ya da dashboard-a köçür.

c. Loqları mərkəzləşdir

Loqları CloudWatch Logs, Azure Log Analytics və ya Google Cloud Logging kimi platformalarda bir yerə topla. Mərkəzləşdirilmiş loqlama nasazlığı araşdırmağı və sistem performansını təhlil etməyi xeyli asanlaşdırır — on serverə ayrı-ayrılıqda SSH ilə girib fayl oxumaq həll deyil.

d. Metric-i xərcə bağla

Monitorinq özü də pul tutur: xüsusi metric-lər, yüksək tezlikli toplama və uzun saxlanma müddəti hesabı artırır. 16-cı fəsildəki büdcə alarmlarını monitorinq xərcinə də tətbiq et.

7 · Kitab bitdi — bundan sonra nə etməli

Nəyi öyrəndik

Bu kitab boyunca Terraform-un əsaslarından — provider, resource, dəyişən və state-dən — başlayıb modul, CI/CD, multicloud, təhlükəsizlik, xərc idarəçiliyi, Kubernetes və serverless-ə qədər gəldik. Son fəsildə isə qurduğumuzun sağlam işlədiyini necə biləcəyimizi öyrəndik.

Üç əsas nəticə:

  • Infrastructure as Code (IaC) — Terraform infrastrukturu bir neçə cloud provider-də bəyanedici (declarative) və təkrarlanan şəkildə təsvir etməyə imkan verir.
  • Avtomatlaşdırma — provisioning, ölçüləndirmə və idarəetmə avtomatlaşdıqca əl işi və insan səhvi azalır.
  • Yaxşı təcrübələr — modul, remote state və versiya nəzarəti infrastrukturu genişlənən, davamlı və təhlükəsiz saxlayır.

İndi nə etməli

  1. Kiçik bir gerçək layihə seç. Öyrənməyin ən sürətli yolu — mövcud əl ilə qurulmuş bir mühiti Terraform-a köçürmək. terraform import ilə başla.
  2. State-i ilk gündən remote backend-ə qoy. Lokal terraform.tfstate ilə işləmək vərdişi sonra bahalı düzəlir.
  3. Öz modul kitabxananı qur. Şirkətində təkrarlanan üç-dörd nümunəni (VPC, RDS, Lambda, EKS node group) modul kimi yaz və versiyala.
  4. CI-a qoş. fmt, validate, plan hər merge request-də avtomatik işləsin; apply isə yalnız təsdiqlə.
  5. Policy və təhlükəsizlik yoxlamaları əlavə et. tfsec, checkov və ya OPA/Sentinel pipeline-a qoşulanda səhv konfiqurasiya prod-a çatmır.
  6. Sənədləşdir. terraform-docs ilə modul sənədini avtomatik yarat — komandaya qoşulan yeni adam üçün ən dəyərli şeydir.
Terraform sürətlə dəyişir. Provider CHANGELOG-larını izlə, versiyaları required_providers-də sabitlə və yeniləməni planlı şəkildə et — bir gün «hər şey işləyirdi, indi plan 40 dəyişiklik göstərir» vəziyyətinə düşməmək üçün.

8 · Yadda saxla

  • Monitorinq resource-u izlədiyi resource ilə eyni modulda yaşasın — belədə heç bir servis alarmsız qalmır.
  • Alarm həddi + evaluation_periods birlikdə düşünülür. Tək dövrlük hədd yalançı xəbərdarlıq yaradır, komanda isə bildirişlərə baxmağı dayandırır.
  • Bildiriş kanalını yoxla. SNS e-poçt abunəliyi təsdiqlənməyibsə, alarm işə düşür, amma heç kimə çatmır.
  • Log group-u özün yarat və retention_in_days qoy — əks halda loqlar əbədi saxlanılır və hesab durmadan artır.
  • Loqları mərkəzləşdir, alarmı hərəkətə bağla. Cavab tələb etməyən bildiriş monitorinq deyil, səs-küydür.
