DR/HA — Praktik Nümunələr

DPE-07 · Data Platform & Engineering Bootcamp

Bu fəsildə fəlakətdən bərpa (DR) və yüksək əlçatanlıq (HA) anlayışlarını konkret Terraform kodu üzərində qururuq: iki region-a yayılmış yerləşdirmə, Route 53 ilə DNS failover, RDS və S3 üçün avtomatik ehtiyat nüsxə, Multi-AZ failover və nəhayət hər şeyi bağlayan monitorinq qatı.

1 · DR və HA — nə üçün lazımdır?

İki fərqli məqsəd

DR və HA infrastrukturun dayanıqlı olmasını, nasazlıq və kəsilmələr zamanı işləməyə davam etməsini təmin edir. Hər ikisi dayanma müddətini, məlumat itkisini və xidmət pozulmasını minimuma endirməyə yönəlib, lakin fərqli suallara cavab verir:

DR (Disaster Recovery)HA (High Availability)
SualıFəlakətdən sonra necə bərpa edəcəyik?Nasazlıq zamanı xidmət necə davam edəcək?
SsenariData mərkəzinin itməsi, təbii fəlakət, region kəsilməsiBir instance, bir AZ və ya bir komponentin sıradan çıxması
AlətEhtiyat nüsxə, replikasiya, ikinci regionArtıqlıq (redundancy), failover, load balancer
Ölçü göstəricisiRTO / RPO (bərpa müddəti və məlumat itkisi)Uptime faizi (99.9%, 99.99%)

Terraform bu strategiyaları kod şəklində təsvir etməyə imkan verir — nəticədə dayanıqlı infrastruktur ardıcıl və təkrarlana bilən şəkildə yerləşdirilir.

RTO və RPO nədir? RTO (Recovery Time Objective) — xidmətin bərpasına icazə verilən maksimum vaxt. RPO (Recovery Point Objective) — itirilməsinə dözülə bilən maksimum məlumat həcmi (vaxt ilə). 7 günlük gündəlik backup RPO-nu 24 saata bərabər edir; bu sənin biznesin üçün kifayətdirmi — DR dizaynı məhz bu sualla başlayır.

2 · Əsas anlayışlar

a. Çoxregionlu yerləşdirmə

DR və HA-nın əsas strategiyalarından biri infrastrukturu bir neçə region-a yaymaqdır. Bir region sıradan çıxarsa, trafik eyni infrastrukturun yerləşdirildiyi digər region-a yönləndirilir.

b. Replikasiya və failover

Məlumat bütövlüyünü və xidmətin davamlılığını təmin etmək üçün baza, storage və tətbiq kimi resource-lar region-lar arasında replikasiya olunmalıdır. Failover mexanizmi əsas sistem sıradan çıxdıqda avtomatik olaraq ehtiyat sistemə keçidi təmin edir.

c. Ehtiyat nüsxə və bərpa

Baza və storage kimi kritik resource-ların ehtiyat nüsxəsinin avtomatlaşdırılması fəlakət anında məlumatın sürətlə və dəqiq bərpasına imkan verir. Terraform backup cədvəllərini və saxlama qaydalarını idarə edə bilir.

3 · Terraform ilə çoxregionlu yerləşdirmə

AWS üzərində iki region

Aşağıdakı nümunədə tətbiqi iki AWS region-una (US-East və US-West) yerləşdiririk: hər region-da bir EC2 instance, RDS baza və DNS failover üçün Route 53.

Addım 1 — hər region üçün provider təyin et

provider "aws" {
  region = "us-east-1"
  alias  = "us_east"
}

provider "aws" {
  region = "us-west-2"
  alias  = "us_west"
}

Burada iki AWS provider-i alias ilə təyin edilir; bundan sonra hər resource hansı region-da yaranacağını provider arqumenti ilə göstərir.

Addım 2 — hər region-da EC2 instance yerləşdir

# US-East region-unda EC2 instance
resource "aws_instance" "web_us_east" {
  provider      = aws.us_east
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    Name = "WebServer-East"
  }
}

# US-West region-unda EC2 instance
resource "aws_instance" "web_us_west" {
  provider      = aws.us_west
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    Name = "WebServer-West"
  }
}
  • Hər iki region-da eyni tətbiqi işlədən EC2 instance yaradılır.
  • Beləliklə region səviyyəsində əlçatanlıq təmin olunur.
AMI ID region-a bağlıdır: nümunədə hər iki instance eyni ami-0c55b159cbfafe1f0 dəyərini işlədir — praktikada bu işləməz, çünki AMI ID-lər region-lar arasında fərqlidir. Düzgün yol: hər region üçün aws_ami data source ilə ən son image-i axtarmaq və ya region → AMI xəritəsini dəyişən kimi saxlamaq.

Addım 3 — Route 53 ilə DNS failover

resource "aws_route53_zone" "example" {
  name = "example.com"
}

# əsas (primary) qeyd — US-East
resource "aws_route53_record" "primary" {
  zone_id = aws_route53_zone.example.zone_id
  name    = "www.example.com"
  type    = "A"

  alias {
    name                   = aws_instance.web_us_east.public_ip
    zone_id                = aws_instance.web_us_east.id
    evaluate_target_health = true
  }

  failover_routing_policy {
    type = "PRIMARY"
  }
}

# ehtiyat (secondary) qeyd — US-West
resource "aws_route53_record" "secondary" {
  zone_id = aws_route53_zone.example.zone_id
  name    = "www.example.com"
  type    = "A"

  alias {
    name                   = aws_instance.web_us_west.public_ip
    zone_id                = aws_instance.web_us_west.id
    evaluate_target_health = true
  }

  failover_routing_policy {
    type = "SECONDARY"
  }
}

Bu konfiqurasiyada:

  • Route 53 DNS səviyyəsində failover marşrutlaşdırması qurur.
  • US-East-dəki əsas instance sağlamlıq yoxlamasından keçmədikdə trafik avtomatik olaraq US-West-dəki ehtiyat instance-a yönləndirilir.
DNS failover-in həqiqi sürəti: keçid ani deyil — sağlamlıq yoxlamasının aşkarlama vaxtı üstəgəl qeydin TTL-i qədər gecikir. DR ssenarisində TTL-i 60 saniyə kimi aşağı dəyərdə saxla, əks halda 5 dəqiqəlik TTL failover-i praktikada 5 dəqiqəlik kəsilməyə çevirir.

4 · Ehtiyat nüsxələrin avtomatlaşdırılması

a. RDS avtomatik backup

Kritik məlumatın ehtiyat nüsxəsinin avtomatlaşdırılması məlumat itkisindən və infrastruktur nasazlığından bərpanı mümkün edir. Aşağıda RDS bazası üçün gündəlik backup qurulur:

resource "aws_db_instance" "mydb" {
  allocated_storage = 20
  engine            = "mysql"
  instance_class    = "db.t2.micro"
  name              = "mydb"
  username          = "admin"
  password          = "password"

  backup_retention_period = 7             # nüsxələr 7 gün saxlanır
  backup_window           = "01:00-03:00" # backup üçün vaxt aralığı
}
  • RDS instance-ı 7 gün saxlanan avtomatik backup ilə yaradılır.
  • Nüsxələr göstərilən vaxt aralığında gündəlik alınır.
Nümunədəki parola diqqət: password = "password" yalnız izahat üçündür. Prod mühitdə parolu heç vaxt koda yazma — 13-cü fəsildə göstərildiyi kimi Secrets Manager-dən oxu və ya manage_master_user_password ilə idarəni RDS-ə həvalə et.

b. S3 üçün ehtiyat nüsxə və arxivləşdirmə

Baza ilə yanaşı S3-də saxlanan fayllar da qorunmalıdır. Bunun üçün lifecycle policy-lərdən istifadə edirik:

resource "aws_s3_bucket" "my_bucket" {
  bucket = "my-backup-bucket"

  lifecycle_rule {
    enabled = true

    transition {
      days          = 30
      storage_class = "GLACIER"  # 30 gündən sonra uzunmüddətli arxivə keçir
    }

    expiration {
      days = 365  # 365 gündən sonra silinir
    }
  }
}
  • Bucket-dəki məlumat 30 gündən sonra avtomatik olaraq Glacier-ə köçürülür.
  • 365 gündən sonra obyektlər silinir — saxlama xərci nəzarətdə qalır.
Versiya qeydi: AWS provider-in yeni versiyalarında lifecycle_rule bloku bucket resource-undan çıxarılıb və ayrıca aws_s3_bucket_lifecycle_configuration resource-una köçürülüb. Məntiq eynidir, yalnız struktur ayrılıb — işlətdiyin provider versiyasının sənədini yoxla.

5 · Avtomatik failover və replikasiya

RDS Multi-AZ

Avtomatik failover əsas infrastruktur sıradan çıxdıqda trafikin fasiləsiz şəkildə ehtiyat infrastruktura yönəldilməsini təmin edir. AWS RDS, Azure SQL və Google Cloud SQL bazalar üçün avtomatik failover dəstəkləyir.

AWS RDS-in Multi-AZ rejimi məlumatı avtomatik olaraq başqa availability zone-a replikasiya edir və aparat ya şəbəkə nasazlığında failover təmin edir:

resource "aws_db_instance" "mydb" {
  allocated_storage = 20
  engine            = "mysql"
  instance_class    = "db.t2.micro"

  multi_az = true  # Multi-AZ failover aktiv edilir

  name     = "mydb"
  username = "admin"
  password = "password"
}
  • Multi-AZ seçimi ilə RDS bazanı başqa availability zone-a avtomatik replikasiya edir.
  • Kəsilmə baş verdikdə AWS avtomatik olaraq digər zone-dakı standby instance-a keçir.

Diqqət yetir: Multi-AZ HA mexanizmidir, DR deyil. O, bütöv region kəsiləndə və ya cədvəl səhvən silinəndə səni xilas etmir — bunun üçün cross-region replika və backup lazımdır. İkisini bir-birinin əvəzi kimi görmək DR planının ən çox yayılan boşluğudur.

6 · Monitorinq və xəbərdarlıqlar

CloudWatch ilə EC2 izləməsi

Nasazlığı vaxtında görmədən nə HA, nə də DR işləyir. Terraform CloudWatch, Azure Monitor və Google Cloud Monitoring kimi alətləri konfiqurasiya edə bilir:

resource "aws_cloudwatch_metric_alarm" "cpu_alarm" {
  alarm_name          = "high-cpu-usage"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 2
  metric_name         = "CPUUtilization"
  namespace           = "AWS/EC2"
  period              = 60
  statistic           = "Average"
  threshold           = 80

  # xəbərdarlıq SNS topic vasitəsilə komandaya çatır
  alarm_actions = [aws_sns_topic.my_sns_topic.arn]

  dimensions = {
    InstanceId = aws_instance.web_us_east.id
  }
}
  • CPU istifadəsi 80%-i keçdikdə alarm işə düşür.
  • Bildiriş SNS topic vasitəsilə administratorlara göndərilir.
Copilot ilə iş: çoxregionlu qurğuda eyni alarm dəstini hər region üçün təkrarlamaq lazım gəlir. Copilot-a bu bloku for_each ilə region xəritəsi üzərində gəzən modula çevirməyi tapşır — nəticəni yoxlayarkən provider arqumentinin düzgün ötürüldüyünə xüsusi diqqət yetir, model bu detalı tez-tez atlayır.

7 · DR/HA üçün ən yaxşı praktikalar

a. Çoxregionlu və çoxzonalı qurğu işlət

Kritik tətbiqləri bir neçə region və ya availability zone-da yerləşdir — dayanıqlılıq artır, dayanma riski azalır.

b. Failover və backup-ı avtomatlaşdır

Failover mexanizmlərini avtomatlaşdır və müntəzəm sına ki, lazım olan anda həqiqətən işlədiyinə əmin olasan. Eyni qayda backup və saxlama müddətlərinə də aiddir.

c. DR planını izlə və sına

Mütəmadi DR məşqləri keçir: bərpa prosedurunun addımlarını əsl kəsilmə anında deyil, əvvəlcədən yoxla. Monitorinq və xəbərdarlıq sisteminin nasazlıq zamanı vaxtında bildiriş göndərdiyinə əmin ol.

Sınanmamış DR planı — plan deyil. Backup-ın alındığını göstərən yaşıl işarə heç nə sübut etmir; sübut yalnız uğurla bərpa edilmiş bazadır. Rüblük bir dəfə backup-dan sınaq mühiti qaldır və bərpa müddətini ölç — bu, sənin faktiki RTO göstəricindir.

8 · Yadda saxla

  • HA lokal nasazlığa (instance, AZ) qarşı işləyir, DR isə region itkisi və məlumat itkisi ssenarilərinə hazırlıqdır — biri digərini əvəz etmir.
  • Çoxregionlu qurğuda alias-lı provider-lər işlədilir; AMI kimi region-a bağlı dəyərləri sabit yazma, data source ilə tap.
  • Route 53 failover DNS səviyyəsində keçid verir — sürəti sağlamlıq yoxlaması və TTL müəyyən edir.
  • RDS-də backup_retention_period və multi_az, S3-də lifecycle qaydaları bir neçə sətirlə ciddi dayanıqlılıq qazandırır.
  • DR planını müntəzəm sına və faktiki RTO/RPO göstəricilərini ölç — sınanmamış bərpa proseduru gözlənilməz an üçün yararsızdır.
