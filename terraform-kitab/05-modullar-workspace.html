Modullar və Workspace-lər

DPE-07 · Data Platform & Engineering Bootcamp

Konfiqurasiya böyüdükcə eyni kodu təkrar-təkrar yazmaq dözülməz olur. Modul — bir neçə resursu tək, təkrar işlədilə bilən vahid halında paketləməyin yoludur. Workspace isə eyni konfiqurasiya ilə bir neçə mühiti (dev, staging, prod) idarə etməyə imkan verir: hər workspace-in öz state faylı olur. Bu fəsildə modul yazmağı, çağırmağı, uzaq modullardan istifadə etməyi və workspace-lərin güclü/zəif tərəflərini öyrənəcəyik.

1 · Modul nədir

Modul — resursların qabı

Terraform-da modul birlikdə işlədilən bir neçə resursun qabıdır (container). Modul infrastruktur kodunu elə paketləyir ki, onu layihələr və mühitlər arasında asanlıqla təkrar işlətmək, saxlamaq və paylaşmaq mümkün olsun.

Terraform-da hər konfiqurasiya artıq bir moduldur. İşlədiyiniz qovluqdakı konfiqurasiya root modul adlanır və başqa modulları məhz oradan çağırırsınız.

2 · Modulun yazılması

Modulun tərkib hissələri

  • main.tf — modulun idarə etdiyi resurslar.
  • variables.tf — modulun qəbul etdiyi giriş dəyişənləri.
  • outputs.tf — modulun çağıran konfiqurasiyaya qaytardığı dəyərlər.

Addım 1 — qovluq quruluşu

/modules
  /ec2
    main.tf
    variables.tf
    outputs.tf

Addım 2 — main.tf (resurslar)

resource "aws_instance" "my_instance" {
  ami           = var.ami
  instance_type = var.instance_type

  tags = {
    Name = var.instance_name
  }
}

Burada EC2 instance dəyişənlər vasitəsilə ötürülən AMI, instance tipi və ad ilə yaradılır — modulun içində sabit dəyər yoxdur.

Addım 3 — variables.tf (girişlər)

variable "ami" {
  description = "EC2 instance üçün istifadə olunacaq AMI"
}

variable "instance_type" {
  description = "İstifadə olunacaq instance tipi"
  default     = "t2.micro"
}

variable "instance_name" {
  description = "EC2 instance-a veriləcək ad"
  default     = "example-instance"
}

Üç dəyişən təyin edildi: ami, instance_type, instance_name. Onları modulu çağıran konfiqurasiya ötürür.

Addım 4 — outputs.tf (çıxışlar)

output "instance_id" {
  value = aws_instance.my_instance.id
}

output "instance_public_ip" {
  value = aws_instance.my_instance.public_ip
}

Output-lar modulun yaratdığı EC2 instance-ın ID-sini və public IP-sini çölə açır — çağıran konfiqurasiya bu dəyərlərdən istifadə edə bilər.

Modulun içində provider bloku təyin etməyin — provider konfiqurasiyası root moduldan gəlməlidir. Əks halda modulu fərqli region və ya account üçün təkrar işlətmək çətinləşir.

3 · Modulun çağırılması

Root moduldan istifadə

Modul hazır olduqdan sonra onu iş qovluğundakı əsas konfiqurasiyadan çağırırıq:

module "my_ec2" {
  source        = "./modules/ec2"
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
  instance_name = "my-terraform-instance"
}
  • source — modulun yeri. Burada yerli yol göstərilib: ./modules/ec2.
  • ami, instance_type, instance_name — modulun tələb etdiyi giriş dəyişənləri.

terraform apply icra ediləndə Terraform bu modulu işlədib göstərilən AMI, tip və adla EC2 instance yaradacaq. Modulun output-una isə belə müraciət olunur: module.my_ec2.instance_public_ip.

Yeni modul əlavə edəndə və ya source dəyişəndə mütləq terraform init işə salın — Terraform modulu yükləməlidir. Əks halda "module not installed" xətası alacaqsınız.

Uzaq (remote) modullar

Yerli modullardan başqa Terraform GitHub kimi versiya nəzarəti sistemlərində və ya Terraform Registry-də yerləşən uzaq modulları da işlədə bilir. Bu, modulları komandalar və layihələr arasında paylaşmağı asanlaşdırır. 

module "vpc" {
  source  = "github.com/terraform-aws-modules/terraform-aws-vpc"
  version = "2.0.0"

  cidr = "10.0.0.0/16"
  azs  = ["us-west-1a", "us-west-1b"]
}
  • source modulu saxlayan repozitoriyaya işarə edir.
  • version hansı versiyanın işlədiləcəyini təyin edir.
  • Modul cidr, azs kimi girişləri qəbul edərək VPC konfiqurasiyasını qurur.
Uzaq modulda versiyanı həmişə sabitləyin. Versiya göstərilməsə, modulun müəllifi dəyişiklik edən kimi sizin plan gözlənilmədən başqa nəticə verə bilər.

Modul üçün yaxşı təcrübələr

  1. Təkrar işlədilən hissələri modula çevirin: VPC, EC2, verilənlər bazası kimi bloklar üçün ayrı modullar yaradın.
  2. Versiyalayın: versiya nəzarətindən və ya Registry-dən gələn modullarda həmişə versiya göstərin ki, uyğunsuz dəyişiklik sizi vurmasın.
  3. Layihəni bölün: şəbəkə üçün bir modul, hesablama resursları üçün başqa, monitorinq üçün üçüncü — belə struktur saxlamağı asanlaşdırır.
  4. Sənədləşdirin: hər modulun giriş, çıxış və məqsədini aydın yazın ki, komanda üzvləri onu düzgün işlətsin.
Modulu çox "ağıllı" etməyin. Yaxşı modul dar bir işi yaxşı görür və az sayda aydın giriş qəbul edir; onlarla şərtlə dolu nəhəng modul saxlanılması ən çətin koda çevrilir.

4 · Workspace-lər

Workspace nədir

Terraform workspace-ləri eyni konfiqurasiya ilə bir neçə mühiti — dev, staging, prod — idarə etməyə imkan verir. Hər workspace-in öz ayrıca state faylı olur, buna görə bir workspace-dəki dəyişiklik digərindəki resurslara toxunmur.

Susmaya görə Terraform default adlı tək workspace-də işləyir, lakin əlavə workspace-lər yaratmaq olar.

Workspace nə vaxt faydalıdır

  • Konfiqurasiya kodunu təkrarlamadan ayrı mühitlər saxlamaq istəyəndə.
  • Test və ya QA üçün infrastrukturun izolyasiya olunmuş nüsxəsini qurmaq lazım gələndə.

Workspace-lərin yaradılması və idarəsi

Addım 1 — yeni workspace

terraform workspace new dev

dev adlı yeni workspace yaranır və Terraform onun üçün avtomatik ayrıca state faylı hazırlayır.

Addım 2 — mövcud workspace-ə keçmək

terraform workspace select dev

Bu əmr Terraform-u dev workspace-inə keçirir. Burada yaradılan və ya dəyişdirilən resurslar digər workspace-lərdən təcrid olunur.

Addım 3 — workspace siyahısı

terraform workspace list

# nəticə:
* default
  dev
  prod

* işarəsi hazırda aktiv olan workspace-i göstərir. Cari workspace-i terraform workspace show ilə də görmək olar.

Workspace-lərin adları state-in yolunda əks olunur. Məsələn, S3 backend-də dev workspace-inin state faylı env:/dev/<key> yolunda saxlanılır — default isə birbaşa <key> yolunda qalır.

Konfiqurasiyada workspace-dən istifadə

Aktiv workspace-in adına konfiqurasiya daxilində terraform.workspace dəyişəni ilə müraciət olunur. Bu, resurs adlarını və teq-ləri mühitə görə fərqləndirmək üçün əlverişlidir. 

resource "aws_instance" "my_instance" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    # ad workspace adı ilə tamamlanır
    Name = "my-instance-${terraform.workspace}"
  }
}

Nəticədə instance-ın adı workspace adı ilə bitəcək: my-instance-dev, my-instance-prod və s.

Eyni üsulla ölçüləri də mühitə görə seçmək olar, məsələn map ilə: local.instance_size[terraform.workspace] — belə yanaşma if zəncirlərindən daha oxunaqlıdır.

Bir neçə mühitin idarəsi

Workspace-lər kodu təkrarlamadan dev, staging və prod mühitlərini saxlamaq üçün əlverişlidir. Nümunə iş axını:

# 1) hər mühit üçün workspace yaradırıq
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod

# 2) hər mühitə resursları yerləşdiririk
terraform workspace select dev
terraform apply        # dev mühitinə tətbiq

terraform workspace select staging
terraform apply        # staging mühitinə tətbiq

Beləliklə hər mühit üçün ayrıca konfiqurasiya yazmağa ehtiyac qalmır, state isə tam təcrid olunmuş qalır.

Ən çox rast gəlinən səhv: yanlış workspace-də apply etmək. Prod-a toxunmadan əvvəl həmişə terraform workspace show ilə harada olduğunuzu yoxlayın, plan çıxışını isə diqqətlə oxuyun.

Workspace-lərin məhdudiyyətləri

  • Yalnız state-i ayırır: workspace konfiqurasiyanı deyil, sadəcə state-i təcrid edir. Dev və prod üçün fərqli AMI ID-si lazımdırsa, bu məntiqi dəyişənlərlə həll etməlisiniz.
  • Hər hal üçün uyğun deyil: mühitlər arasında çoxlu fərq olan iri layihələrdə workspace-lər konfiqurasiyanı mürəkkəbləşdirir. Belə hallarda hər mühit üçün ayrı Terraform layihəsi (ayrı qovluq və backend key) daha düzgündür.

5 · Yekun

Yadda saxla

  • Hər konfiqurasiya moduldur: iş qovluğunuz root moduldur, digər modulları oradan çağırırsınız.
  • Modul üç fayldan ibarətdir: main.tf (resurslar), variables.tf (girişlər), outputs.tf (çıxışlar) — sabit dəyərləri modulun içinə yazmayın.
  • Uzaq modulda versiyanı sabitləyin: version göstərilməsə, kənar dəyişiklik sizin plan-ı gözlənilmədən dəyişə bilər.
  • Workspace state-i ayırır, konfiqurasiyanı yox: mühitlər arası fərqləri dəyişənlərlə idarə edin, terraform.workspace ilə adlandırın.
  • Prod ciddi ayrılıq tələb edir: mühitlər bir-birindən çox fərqlənəndə və ya giriş hüquqları ayrılmalıdırsa, workspace əvəzinə ayrı layihə və ayrı backend seçin.
