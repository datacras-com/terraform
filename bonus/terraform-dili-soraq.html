1 · Fayl xəritəsi — hansı fayl nə üçündür?

Yadda saxla: fayl adları şərtidir — Terraform qovluqdakı bütün .tf faylları birləşdirib oxuyur. Bölgü insan üçün səliqədir:

FaylKim yaradırNə üçündür
main.tfSənResurslar və modul çağırışları — işin əsas hissəsi
variables.tfSənDəyişənlərin bəyanı (adı, tipi, təsviri) — dəyərlər yox!
terraform.tfvarsSənDəyişənlərin dəyərləri — bu mühit üçün konkret rəqəmlər/adlar
outputs.tfSənÇıxış dəyərləri — "işin sonunda nəyi göstər/qaytar"
provider.tfSənProvider konfiqurasiyası (region və s.) + versiya kilidi
.terraform/Terraform (init)Endirilmiş provider-lər və modullar — git-ə getmir
.terraform.lock.hclTerraform (init)Provider versiyalarının dəqiq kilidi — git-ə gedir
terraform.tfstateTerraform (apply)Yaddaş: kod ↔ real dünya xəritəsi — əl ilə redaktə etmə, git-ə qoyma!

2 · variable — dəyişənin anatomiyası

Dəyişən = kodun parametrləşdirilməsi: dəyəri koddan çıxarırsan ki, eyni kod fərqli dəyərlərlə işləsin (Fəsil 2-dəki "bir kod — fərqli nəticələr").

variable "dev_cidr_block" {
  description = "CIDR for the development VPC"  # insan üçün izah
  type        = string                              # hansı tip qəbul edilir
  default     = "10.0.0.0/16"                     # dəyər verilməsə, bu işləyir
}

Sahələr:

  • description — həmişə yaz: 6 ay sonra özünə hədiyyə
  • type — yazılmasa "any" olur; həmişə yaz
  • default — istəyə bağlıdır: yoxdursa, dəyər verilməsi məcburidir

Bonus sahələr:

  • sensitive = true — dəyər plan çıxışında gizlədilir (parollar üçün)
  • validation { } — dəyərə şərt qoyur (məsələn: port > 1024)
⚠️ Modul dərsindən qayda: modul dəyişənlərinə default qoymuruq — dəyəri çağıran verməlidir. Kök dəyişənlərdə isə default məqbuldur.

3 · Dəyər vermə yolları və PRİORİTET

Eyni dəyişənə bir neçə yerdən dəyər gələ bilər — güclü olan qalib gəlir (aşağıdan yuxarı güclənir):

# 1 (ən zəif) — variables.tf-də default:
default = "10.0.0.0/16"

# 2 — mühit dəyişəni (TF_VAR_ prefiksi ilə):
$ export TF_VAR_dev_cidr_block="10.1.0.0/16"

# 3 — terraform.tfvars faylı:
dev_cidr_block = "10.2.0.0/16"

# 4 (ən güclü) — CLI bayrağı:
$ terraform apply -var="dev_cidr_block=10.3.0.0/16"

Bu nümunədə VPC 10.3.0.0/16 ilə yaranacaq — CLI hamısını üstələyir. CLI olmasa → tfvars (10.2) → o da olmasa env var (10.1) → o da olmasa default (10.0).

✅ Praktik qayda: gündəlik dəyərlər tfvars-da yaşayır (fayldır, görünür, git-ə düşə bilər — secrets yoxdursa); müvəqqəti sınaq üçün -var; secrets üçün env var (TF_VAR_...) — fayla düşmür.

4 · output — işin nəticəsini göstər / qaytar

Output iki işə yarayır:

  1. İnsan üçün: apply bitəndə vacib dəyərləri ekrana çıxarır — VPC ID, server IP-si… konsola girib axtarmağa ehtiyac qalmır
  2. Kod üçün: modulun "return" dəyəri — kənar kod modulun içinə yalnız output-la çata bilir (Fəsil 4.5)
output "vpc_id" {
  description = "The ID of the production VPC"
  value       = aws_vpc.prd.id
}
$ terraform apply
Outputs:
vpc_id = "vpc-0be9c8f38606c4096"

$ terraform output              # istənilən vaxt yenidən bax
$ terraform output -json        # skriptlər üçün JSON formatında
$ terraform output vpc_id       # tək dəyər
✅ Modul output-una müraciət: module.vpc.vpc_id — "vpc modulunun vpc_id output-u".

5 · locals — təkrarlanan ifadələr üçün

Eyni ifadəni 5 yerdə yazırsansa — bir dəfə locals-da yaz, hər yerdə local. ilə istifadə et:

locals {
  common_tags = {
    ManagedBy = "terraform"
    Course    = "dpe-07"
  }
  name_prefix = "prd"
}

resource "aws_vpc" "prd" {
  cidr_block = "10.0.0.0/16"
  tags       = local.common_tags        # bir mənbə, hər yerdə eyni
}

variable ilə fərqi nədir? Variable — kənardan gələn dəyərdir (istifadəçi/tfvars verir); local — daxili hesablanan qısaltmadır, kənardan dəyişdirilə bilmir. Sual belə qoyulur: "bu dəyəri çağıran dəyişməlidir?" Bəli → variable; xeyr, sadəcə təkrarı azaldıram → local.

6 · Tip sistemi — string-dən map-a

TipNümunə dəyərNə vaxt lazımdır
string"eu-north-1"Mətn: adlar, region, CIDR
number3Rəqəm: say, port, ölçü
booltrue / falseAç/bağla: enable_dns_hostnames
list(string)["10.0.1.0/24", "10.0.2.0/24"]Sıralı siyahı — index ilə: var.cidrs[0]
map(string){ dev = "10.1.0.0/16", prd = "10.0.0.0/16" }Açar-dəyər — açarla: var.cidrs["dev"]
object({...}){ name = "web", port = 80 }Qarışıq tipli strukturlar (irəli mövzu)
⚠️ Klassik başlanğıc xətası (özün gördün!): string dəyəri dırnaqsız yazmaq — region = us-east-1 ✗. String həmişə dırnaqda: region = "eu-north-1" ✓. Rəqəm və bool isə dırnaqsızdır: count = 3, enabled = true.

7 · İstinadlar — "bu dəyəri haradan götürüm?"

Terraform kodunda hər istinadın öz prefiksi var — prefiks mənbəyi deyir:

YazılışMənası
var.dev_cidr_blockDəyişəndən (variables.tf-də bəyan edilib)
local.common_tagsLocal dəyərdən
aws_vpc.prd.idResursdan: tip.ad.atribut — "prd adlı VPC-nin ID-si"
module.vpc.vpc_idModulun output-undan
data.aws_ami.ubuntu.idData source-dan (tapılmış mövcud resursdan)
"${var.env}-vpc"İnterpolyasiya — string içində dəyər: nəticə "dev-vpc"
✅ Resursa istinad həm də asılılıq yaradır (implicit dependency): vpc_id = aws_vpc.prd.id yazdınsa, Terraform bilir ki, əvvəl VPC yaranmalıdır.

8 · data vs resource — yaratmaq yoxsa tapmaq?

resource "aws_vpc" "prd" {
  cidr_block = "10.0.0.0/16"
}

resource = YARADIR ✚
Bu resursun həyatı Terraform-un əlindədir: yaradır, dəyişir, silir.

data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
}

data = TAPIR 🔍
Mövcud olanı axtarıb oxuyur — yaratmır, silmir, yalnız məlumat götürür.

✅ "Server Təməlləri" sənədindən düstur: cloud = çox resource · on-prem = əvvəl data ilə təməli tap (datastore, network, template), sonra resource ilə VM yarat.

9 · count və for_each — bir bloku çoxaltmaq (tanışlıq)

Fəsil 4-də üç subnet üçün üç blok yazdıq. Əslində bir blok yazıb çoxaltmaq olar:

# count — say ilə
resource "aws_subnet" "pub" {
  count      = 3
  vpc_id     = aws_vpc.prd.id
  cidr_block = "10.0.${count.index}.0/24"
}
# yaradır: pub[0], pub[1], pub[2]
# for_each — açarlarla (tövsiyə olunan)
resource "aws_subnet" "pub" {
  for_each   = { a = "10.0.0.0/24", b = "10.0.1.0/24" }
  vpc_id     = aws_vpc.prd.id
  cidr_block = each.value
}
# yaradır: pub["a"], pub["b"]

Fərq bir cümlədə: count nömrə ilə işləyir — siyahının ortasından element silinəndə qalanların nömrəsi sürüşür və Terraform onları yenidən yaratmaq istəyir; for_each açarla işləyir — hər element öz açarında sabit qalır. Ona görə praktikada for_each üstündür.

🤖 Bu mövzu kursun yekun mini-layihəsində qarşına çıxacaq (data-lake bucket-ləri for_each ilə) — burada tanışlıq kifayətdir.

10 · Əmrlər — cib vərəqəsi

ƏmrNə edir
terraform initProvider/modul endirir, qovluğu hazırlayır — yeni provider və ya modul = yenidən init
terraform fmtKodu avtomatik formatlayır (boşluqlar, düzləndirmə)
terraform validateSintaksis + istinadları yoxlayır — hallüsinasiya tutucu
terraform planÖnizləmə: + yaradılacaq · ~ dəyişəcək · - silinəcək. Heç nəyi dəyişmir
terraform applyDəyişiklikləri həqiqətən tətbiq edir (təsdiq istəyir)
terraform destroyState-dəki hər şeyi silir — dərs sonu ritualı 🧹
terraform state listState-dəki resursların siyahısı — "Terraform nəyi tanıyır?"
terraform outputOutput dəyərlərini göstərir
terraform consoleİnteraktiv sınaq meydanı: ifadələri (var.x, funksiyalar) canlı yoxla
✅ Kursun ritmi: fmt → validate → plan → (oxu!) → apply — hər dəfə, həmişə, Copilot yazanda xüsusilə.

11 · .gitignore — git-ə nə GETMİR?

# Terraform layihəsinin standart .gitignore-u:
.terraform/          # endirilmiş provider-lər — ağırdır, init yenidən endirir

*.tfstate.*          # state backup-ları — eyni səbəb
*.tfvars             # içində secrets varsa; yoxdursa saxlamaq olar
crash.log
  • Git-ə gedir: bütün .tf fayllar + .terraform.lock.hcl (versiya kilidi komanda üçün vacibdir)
  • Git-ə getmir: state (həssas!), .terraform/ qovluğu, secrets olan tfvars
