1 · Əsaslar

🟢Terraform nədir?
HashiCorp-un açıq mənbəli Infrastructure as Code alətidir. İnfrastrukturun (VM-lər, şəbəkələr, storage…) istənilən vəziyyətini deklarativ dildə (HCL) təsvir edirsən, Terraform isə həmin vəziyyətə çatmaq üçün resursları yaradır, dəyişir və silir. Konfiqurasiya faylları versiya nəzarətində saxlanılır — dəyişikliklər izlənilə bilən və təkrarlana biləndir.
🟢Infrastructure as Code (IaC) nədir?
İnfrastrukturu əl prosesləri ilə deyil, kodla idarə etmək praktikasıdır. Kod istənilən vəziyyəti təyin edir; bu, versiya nəzarəti, komanda əməkdaşlığı və bütün infrastruktur həyat dövrünün avtomatlaşdırılmasını mümkün edir. "Konsolda klik" dövrünün əksidir: hər dəyişikliyin tarixçəsi, müəllifi və geri qaytarılma yolu olur.
🟢Terraform-un Ansible/Chef/Puppet kimi alətlərdən fərqi nədir?
Onlar konfiqurasiya idarəetməsi alətləridir — mövcud serverlərin içini qururlar (paketlər, fayllar, servislər). Terraform isə infrastrukturun özünü yaradır və idarə edir (provisioning) və platformadan asılı deyil (cloud-aqnostik). Rəqib deyil, tamamlayıcıdırlar: əvvəl Terraform serveri yaradır, sonra Ansible içini qurur.
🟢Terraform necə quraşdırılır?
Rəsmi saytdan OS-ə uyğun binary endirilir və PATH-a əlavə olunur; paket menecerləri daha rahatdır: macOS-da brew install hashicorp/tap/terraform, Ubuntu-da HashiCorp apt repo-su, Windows-da winget install Hashicorp.Terraform. Yoxlama: terraform version.
🟢HCL nədir və əsas sintaksis elementləri hansılardır?
HashiCorp Configuration Language — Terraform konfiqurasiyalarının yazıldığı dil. Əsas elementlər: bloklar ({ } ilə: resource, variable, provider…), arqumentlər (blok daxilində açar = dəyər cütləri), ifadələr və interpolyasiya (${var.env}-vpc — string içində dəyər). İnsan üçün oxunaqlı olması əsas dizayn məqsədidir.
🟡Immutable infrastructure nədir və Terraform onu necə dəstəkləyir?
İşləyən komponentləri dəyişdirmək əvəzinə yenisi ilə əvəzləmək praktikasıdır. Terraform deklarativ olduğu üçün buna təbii uyğundur: konfiqurasiya dəyişəndə plan çıxarır və lazım gələndə resursu silib yenidən yaradır (-/+ replace). Nəticə: ardıcıllıq, təkrarlanabilirlik və asan geri qayıtma.

2 · İş axını (init → plan → apply → destroy)

🟢terraform init nə edir?
İş qovluğunu hazırlayır: konfiqurasiyada göstərilən provider-ləri və modulları endirir, backend-i qurur. Layihə ilə işin ilk addımıdır; qayda: yeni provider VƏ YA yeni modul əlavə olundu = yenidən init.
🟢terraform plan nə üçündür?
İcra planının önizləməsi: konfiqurasiyanı (istənilən vəziyyət) mövcud state ilə müqayisə edib nəyin yaradılacağını (+), dəyişəcəyini (~) və silinəcəyini (-) göstərir. Heç nəyi dəyişmir — "dry run"dır. Apply-dan əvvəl xətaları və gözlənilməz dəyişiklikləri tutmaq üçün mütləq oxunmalıdır.
🟢terraform apply necə işləyir?
Plandakı dəyişiklikləri icra edir: təsdiq istəyir (yes), platformanın API-lərini çağırıb resursları yaradır/dəyişir/silir və nəticəyə uyğun state faylını yeniləyir. Plan ilə fərqi bir cümlədə: plan = önizləmə (heç nə dəyişmir), apply = icra (real dəyişiklik).
🟢terraform destroy nə edir və nəyə diqqət etməli?
State-də olan bütün idarə olunan resursları silir. Geri dönməz əməliyyatdır — icradan əvvəl siyahını oxumaq və təsdiqi şüurlu vermək lazımdır. Vacib nüans: yalnız state-dəki resurslara toxunur; əl ilə (Terraform-dan kənar) yaradılmış resurslara dəymir.

3 · Resurs, Provider, Data Source

🟢Terraform-da resource nədir?
İdarə etmək istədiyin infrastruktur komponentidir: VM, şəbəkə, DB, DNS qeydi… Konfiqurasiyada resource "tip" "ad" { } bloku ilə bəyan olunur; hər resurs tipi konkret provider-ə aiddir. Terraform bu blok əsasında real resursu yaradır, yeniləyir və silir.
🟢Provider nədir və Terraform-un imkanlarını necə genişləndirir?
Terraform core ilə konkret platforma (AWS, Azure, vSphere…) arasında plugin-körpüdür: API kommunikasiyasını və autentifikasiyanı öz üzərinə götürür, həmin platformanın resource tiplərini və data source-larını təyin edir. Bir konfiqurasiyada bir neçə provider işlədilə bilər — multi-cloud və hibrid ssenarilərin təməli budur.
🔴Provider alias nədir və nə vaxt lazımdır?
Eyni provider-in bir neçə fərqli konfiqurasiyasını bir layihədə istifadə etməyə imkan verir. Klassik ssenari: resursları iki fərqli AWS regionunda yaratmaq: 
provider "aws" { region = "eu-north-1" }
provider "aws" { region = "eu-west-1"  alias = "ireland" }

resource "aws_s3_bucket" "backup" {
  provider = aws.ireland   # bu bucket İrlandiyada yaranacaq
  ...
}
🟢Data source nədir və resource-dan fərqi nədir?
Data source mövcud məlumatı oxuyur — yaratmır, dəyişmir, silmir. Nümunələr: ən son Ubuntu AMI-sini tapmaq, mövcud VPC-nin ID-sini almaq, regionun AZ siyahısını oxumaq. Resource isə resursu yaradır və həyatını idarə edir. Düstur: resource = yaradır ✚, data = tapır 🔍.
🟡Output ilə data source-un fərqi nədir?
Output — öz konfiqurasiyanın nəticəsini kənara verir (apply-dan sonra göstərilir, modullar arasında ötürülür). Data source — kənar/mövcud məlumatı içəri gətirir. İstiqamətləri əksdir: output = ixrac, data = idxal.
🟡Resurslar arasında asılılıqlar necə idarə olunur?
Əsasən avtomatik: bir resurs digərinə istinad edəndə (vpc_id = aws_vpc.prd.id) Terraform implicit dependency qurur və yaradılış sırasını özü müəyyən edir. İstinadla ifadə olunmayan "gizli" asılılıqlar üçün depends_on meta-arqumenti var — amma tövsiyə implicit-ə üstünlük verməkdir: kod daha oxunaqlı qalır.

4 · Dəyişənlər, tfvars, Outputs, Locals

🟢Variable nədir və necə təyin olunur?
Konfiqurasiyaya kənardan dəyər ötürməyə imkan verən parametrdir — kodun təkrar istifadəsinin açarı. variable bloku ilə bəyan olunur: ad, type, description, istəyə görə default. Default yoxdursa, dəyərin verilməsi məcburidir. Kodda var.ad ilə istinad olunur.
🟢terraform.tfvars faylı nə üçündür?
Terraform-un avtomatik yüklədiyi dəyər faylıdır: dəyişənlərə dəyərləri variables.tf-dəki default-lara toxunmadan burada verirsən. Məntiq ayrılığı yaradır: bəyan (variables.tf) ↔ dəyərlər (tfvars). Prioritet zənciri: default < TF_VAR_ env dəyişəni < tfvars < CLI -var (ən güclü).
🟢Dəyişənlərə kodda necə istinad olunur? İnterpolyasiya nədir?
Birbaşa: instance_type = var.instance_type. String içində dəyər lazım olanda interpolyasiya işlədilir — ${} sintaksisi: 
tags = { Name = "web-${var.environment}" }   # nəticə: "web-dev"
🟢Output nə üçündür?
İki vəzifəsi var: (1) apply-dan sonra seçilmiş dəyərləri (VPC ID, server IP…) insana göstərmək — terraform output ilə istənilən vaxt baxılır; (2) modulun "return" dəyəri olmaq — kənar kod modulun içinə yalnız output vasitəsilə çatır: module.vpc.vpc_id.
🟡Locals nədir və oxunaqlılığı necə artırır?
Təkrarlanan/mürəkkəb ifadələrə ad verən daxili dəyərlərdir: bir dəfə hesabla, hər yerdə local.ad ilə istifadə et. Faydası: təkrarın azalması, mürəkkəb ifadələrin sadələşməsi, dəyişikliyin bir nöqtədən idarəsi. Variable ilə fərqi: variable kənardan gəlir, local daxildə hesablanır və kənardan dəyişdirilə bilmir.
🟡Terraform-da şərti məntiq (if-else) necə qurulur?
Klassik if-else yoxdur — üç mexanizmlə əvəzlənir: (1) üçlü operator: count = var.create_instance ? 1 : 0 — resursu şərtlə yarat/yaratma; (2) for_each üzərində filter: for_each = { for k, v in var.items : k => v if v.enabled }; (3) locals-da şərti ifadələr.
🔴Dynamic block nədir və dəyişənlərlə necə işləyir?
Resurs daxilindəki təkrarlanan iç-blokları (məsələn, security group-un çoxlu ingress qaydası) dinamik yaratmaq üçündür: 
dynamic "ingress" {
  for_each = var.rules
  content {
    from_port = ingress.value.port
    to_port   = ingress.value.port
    protocol  = "tcp"
  }
}
var.rules map/list dəyişənidir — hər elementi üçün bir ingress bloku yaranır.

5 · State, Backend-lər, Locking

🟢State faylının məqsədi nədir?
terraform.tfstate — Terraform-un yaddaşıdır: idarə olunan resursları, konfiqurasiyalarını və aralarındakı əlaqələri saxlayır. Kod (istənilən vəziyyət) ilə real infrastruktur arasında xəritə rolunu oynayır — plan/apply nəyin əlavə/dəyişdirilməli/silinməli olduğunu məhz state ilə müqayisədən çıxarır. "Source of truth"dur: əl ilə redaktə edilmir, git-ə qoyulmur.
🟡Remote backend nədir və niyə vacibdir?
State faylını lokal qovluqda deyil, mərkəzi/paylaşılan yerdə (Amazon S3, Azure Storage, HashiCorp Consul, Terraform Cloud) saxlamaqdır. Faydaları: əməkdaşlıq (hamı eyni state ilə işləyir), locking (paralel dəyişikliyin qarşısı), ardıcıllıq (vahid mənbə), təhlükəsizlik (laptop itsə state itmir).
🔴Backend tipləri hansılardır?
Local — state öz maşınında (default; komanda işinə uyğun deyil) · Remote — S3, Azure Storage, Consul kimi paylaşılan saxlama · Enhanced remote — saxlamadan əlavə uzaqdan icra da verən Terraform Cloud/Enterprise.
🟡State locking nədir və komanda mühitində niyə kritikdir?
Eyni state üzərində paralel əməliyyatların qarşısını alan mexanizmdir. Proses: əməliyyatdan əvvəl kilid alınır → iş görülür → kilid buraxılır. Bu olmasa, iki nəfər eyni anda apply etsə, state korlana və resurslar ziddiyyətə düşə bilər. Remote backend-lər (S3+DynamoDB, Terraform Cloud) locking-i daxilən dəstəkləyir.
🟡Infrastructure drift nədir və Terraform onu necə idarə edir?
Drift — real infrastrukturun koddan kənara sürüşməsidir (kimsə konsoldan əl ilə dəyişiklik edəndə). Terraform növbəti plan-da state/real müqayisəsi ilə fərqi aşkarlayır və apply ilə infrastrukturu kodda yazılan vəziyyətə qaytarır. Qızıl qayda: Terraform ilə qurulana əl ilə toxunma — hər dəyişiklik koddan keçsin.
🔴terraform import nədir və nə vaxt istifadə olunur?
Terraform-dan kənarda yaradılmış mövcud resursu Terraform idarəsinə gətirir — resursu state-ə bağlayır: 
terraform import aws_instance.example i-0123456789abcdef0
Diqqət ediləsi: əvvəlcə resursa uyğun konfiqurasiya bloku yazılmalıdır (import kod yaratmır, yalnız state-ə salır), resursun düzgün ID-si verilməli və importdan sonra plan ilə kod↔real uyğunluğu yoxlanmalıdır.
🔴Kənarda silinmiş resursu Terraform necə görür?
Növbəti plan/apply-da refresh zamanı resursun yoxluğunu aşkarlayır və iki yol var: konfiqurasiyada hələ varsa — yenidən yaratmağı təklif edir ("1 to add"); resurs artıq lazım deyilsə — kodu silirsən və state sinxronlaşır. Əks ssenari (state itib, resurs durur) üçün terraform import işlədilir.
🔴Komandada state idarəsinin çətinlikləri və ən yaxşı praktikaları hansılardır?
Çətinliklər: paralel dəyişikliklər, dəyişikliklərin görünürlüyü, ardıcıllıq. Praktikalar: paylaşılan remote backend + state locking · state fayllarına incə tənzimlənmiş giriş nəzarəti · audit loqları · müntəzəm backup · CI/CD-də ayrıca workspace/state-lər.

6 · Modullar

🟢Modul ilə resursun fərqi nədir?
Resource — tək tikinti daşıdır (bir VM, bir şəbəkə). Modul — resursları qablaşdıran təkrar istifadə edilə bilən paketdir: input (variables) → resurslar → output. Resurslar binanın kərpicidirsə, modullar hazır otaq layihələridir — bir dəfə yaz, fərqli parametrlərlə dönə-dönə çağır.
🟢Modullar kod təkrarını və saxlanılmanı necə yaxşılaşdırır?
Təkrar istifadə (bir VPC modulu → dev/staging/prd üçün üç çağırış) · abstraksiya (istifadəçi daxili detalları bilmir, yalnız input/output görür) · ardıcıllıq (bütün mühitlər eyni qəlibdən çıxır) · saxlanılma (düzəliş bir yerdə edilir, hamı faydalanır).
🟡Modullar arasında asılılıqlar necə qurulur?
Əsas yol: bir modulun output-unu digərinin input-una ötürmək — vpc_id = module.network.vpc_id. Terraform bu istinaddan icra sırasını özü çıxarır. Böyük sistemlərdə ayrı state-lər arasında terraform_remote_state data source-u da işlədilir (irəli mövzu).
🔴Modul versiyalaması necə aparılır?
Modul ayrıca repo/qovluqda saxlanılır və semantic versioning (v1.2.3) ilə tag-lənir; çağıran tərəf versiyanı pin edir (version = "~> 1.2"). Əlavə praktikalar: release notes/changelog, Terraform Registry və ya şirkətdaxili module registry, aydın sənədləşdirilmiş input/output müqaviləsi.

7 · count, for_each, lifecycle

🟢count ilə for_each-in fərqi nədir?
İkisi də bir blokdan çox nüsxə yaradan meta-arqumentlərdir. count — rəqəmlə işləyir (count = 3 → nüsxələr [0],[1],[2]); siyahının ortasından element silinəndə qalanların indeksi sürüşür və Terraform onları yenidən yaratmaq istəyir. for_each — map/set üzərində açarla işləyir (nüsxələr ["a"],["b"]); hər element öz açarında sabitdir, ona görə praktikada üstün tutulur.
🟡count/for_each modullarla da işləyir?
Bəli — modul çağırışını da çoxaltmaq olar: 
module "vpc" {
  source   = "./modules/vpc"
  for_each = { dev = "10.1.0.0/16", prd = "10.0.0.0/16" }

  vpc_cidr_block = each.value
  vpc_name       = "${each.key}-vpc"
}
Nəticə: iki müstəqil VPC — module.vpc["dev"] və module.vpc["prd"].
🔴Lifecycle bloku nədir və hansı parametrləri var?
Resursun həyat dövrü davranışını tənzimləyir: create_before_destroy — replace zamanı əvvəl yenisini yarat, sonra köhnəni sil (sıfır-kəsinti) · prevent_destroy — kritik resursun (prod DB!) təsadüfi silinməsinə sığorta · ignore_changes — seçilmiş atributlardakı kənar dəyişiklikləri görməzdən gəl.
🔴Null resource nədir və nə vaxt lazımdır?
Real platformada qarşılığı olmayan "boş" resursdur — hədəf infrastrukturda heç nə yaratmır. İstifadə yerləri: resurslar arasında süni asılılıq körpüsü qurmaq, triggers ilə dəyişikliyə reaksiya verib skript işlətmək, lokal provisioner-ləri resurssuz icra etmək. Müasir alternativi çox halda terraform_data resursudur.
🔴Resource targeting (-target) nədir?
terraform apply -target=aws_vpc.prd — əməliyyatı konkret resursla məhdudlaşdırır. İstifadəsi: təcili nöqtəvi düzəliş, riskin azaldılması, icra vaxtına qənaət. Xəbərdarlıq: gündəlik alət deyil — state-i qismən yeniləyir, asılılıqlar kənarda qala bilər; müntəzəm istifadəsi anti-pattern sayılır.

8 · Mühitlər, Workspaces, Komanda işi

🟡Terraform workspaces nədir?
Eyni konfiqurasiya dəstinin bir neçə müstəqil nüsxəsini idarə etməyə imkan verir — hər workspace-in öz state faylı olur. Tipik istifadə: dev/staging/prd mühitləri. Əmrlər: terraform workspace new dev, terraform workspace select prd; kodda terraform.workspace ilə cari ada müraciət olunur.
🔴Mühitləri (dev/staging/prd) idarə etməyin yolları və müqayisəsi?
İki əsas yanaşma: (1) workspaces — bir kod bazası, ayrı state-lər; sadə, təkrarsız, kiçik komandalar üçün rahat; (2) ayrı qovluqlar/backend key-lər — hər mühitin öz konfiqurasiyası; daha şəffaf, mühitlər arasında fərqlər böyüyəndə və icazələr ayrılanda üstündür. Böyük təşkilatlarda adətən ikinci yanaşma + modullar kombinasiyası işlədilir.
🟡Terraform Git ilə necə istifadə olunur?
Konfiqurasiya adi kod kimi idarə olunur: repo + müntəzəm commit/push · dəyişikliklər branch + pull request ilə (kod baxışı!) · buraxılışlar tag-lənir · CI-da minimum fmt -check və validate, sonra plan/apply pipeline-ı. Git-ə girməyənlər: state faylları, .terraform/, secrets olan tfvars.
🔴Terraform kodunun təşkili üzrə ən yaxşı praktikalar hansılardır?
  • Modular struktur — təkrar istifadə edilə bilən modullar
  • Mühit ayrımı — workspaces və ya qovluq strukturu ilə
  • Dəyişənlərlə parametrləşdirmə, adlandırma konvensiyaları
  • Remote backend + state locking
  • Versiya nəzarəti + kod baxışı (PR) prosesi
  • Provider/modul versiyalarının pin edilməsi, lock faylının commit olunması
  • Şərhlər və README ilə sənədləşdirmə
🔴CI/CD pipeline-da Terraform-un çətinlikləri və praktikaları?
Çətinliklər: state ardıcıllığı, paralel işə salınmalar, icazələrin idarəsi. Praktikalar: remote backend + locking · mühit başına ayrıca state/workspace · pipeline axını: fmt → validate → plan (artefakt kimi saxla) → əl təsdiqi → apply · pipeline konfiqurasiyasının özünü də kod kimi saxlamaq · uğursuzluqda bildiriş + geri qayıtma strategiyası (tag-lənmiş son işlək vəziyyət, state backup-ları).

9 · Secrets və Həssas Məlumat

🟡Terraform-da həssas məlumat (parol, API açarı) necə idarə olunur?
Əsas qayda: konfiqurasiya faylına açıq mətnlə yazma. Yollar: dəyişəndə sensitive = true (plan çıxışında gizlədilir) · dəyəri env dəyişəni ilə vermək (TF_VAR_db_password) · xüsusi secret alətləri ilə inteqrasiya — HashiCorp Vault, AWS Secrets Manager, cloud parameter store-ları. Unutma: dəyər yenə state-ə düşə bilər — ona görə state-in özü qorunmalı və git-dən kənar saxlanmalıdır.
🔴Secret rotation (məsələn, DB parolunun dövri dəyişməsi) Terraform ilə necə həll olunur?
Terraform rotasiyanı özü etmir — kənar alətlərlə qurulur: Vault/Secrets Manager-in avtomatik rotation funksiyaları (Terraform yalnız secret-ə istinad edir), CI/CD pipeline-ında planlı yeniləmə addımı, və ya rolling qaydada tətbiq (kəsintini azaltmaq üçün). Yanaşma: "secret-in sahibi secret meneceri olsun, Terraform yalnız ünvanını bilsin".

10 · Provisioners (qısa tanışlıq)

🔴Provisioner nədir? remote-exec nə edir?
Provisioner — resurs yaradılandan sonra skript/əmr icra edən mexanizmdir: local-exec — skripti öz maşınında işlədir; remote-exec — yaradılan uzaq maşında işlədir (SSH ilə qoşulub paket qurmaq, bootstrap etmək). Rolu: ilkin konfiqurasiya/bootstrapping. Vacib qeyd: HashiCorp provisioner-ləri son çarə sayır — konfiqurasiya idarəsi üçün düzgün alətlər Ansible/cloud-init/Packer-dir.

11 · Ekosistem: Cloud, Enterprise, Multi-cloud

🔴Terraform Cloud nədir?
HashiCorp-un idarə olunan xidmətidir — Terraform iş axınlarına əlavə imkanlar verir: uzaqdan icra (plan/apply idarə olunan mühitdə) · remote state saxlama + locking · komanda əməkdaşlığı · Sentinel ilə policy-as-code (qaydaların məcburi tətbiqi) · şəxsi modul registry-si. Kiçik komandalar üçün pulsuz səviyyəsi var.
🔴Terraform Enterprise nədir və açıq mənbədən nə ilə fərqlənir?
Böyük təşkilatlar üçün kommersiya təklifidir (öz infrastrukturunda qurulan Terraform Cloud). Açıq mənbə üzərinə əlavə etdiyi: geniş əməkdaşlıq və icazə idarəsi (RBAC/SSO) · mərkəzi state + audit loqları · VCS inteqrasiyalı avtomatik iş axınları · policy enforcement · şəxsi modul registry. Açıq mənbə fərdi/kiçik komandaya bəs edir; Enterprise idarəetmə (governance) tələbləri olan miqyas üçündür.
🟡Terraform ilə multi-cloud necə idarə olunur?
Bir konfiqurasiyada bir neçə provider bloku təyin edilir (aws + azurerm + google…), resurslar öz provider-inin tipləri ilə yazılır, ümumi məntiq dəyişənlər/modullarla parametrləşdirilir. Terraform-un dəyəri: bir dil, bir iş axını (init→plan→apply) bütün platformalarda — hər cloud üçün ayrıca alət öyrənmək lazım gəlmir.
🔴Terraform-un CI/CD alətləri (Jenkins, GitLab CI…) ilə birləşdirilməsinin faydaları?
Avtomatlaşdırma (əl apply-larının aradan qalxması) · versiya nəzarətli, izlənilə bilən deployment-lər · mühitlər arasında ardıcıllıq · plan-ın PR-da görünməsi (dəyişikliyin baxışı) · audit izi · miqyaslanma. Tipik axın: PR → CI-da fmt/validate/plan → baxış+təsdiq → merge → apply.
🔴Uğursuz deployment zamanı geri qayıtma (rollback) strategiyaları hansılardır?
Terraform-da klassik "rollback düyməsi" yoxdur — strategiya qabaqcadan qurulur: işlək vəziyyətlər VCS tag-ları ilə işarələnir (geri qayıtmaq = köhnə tag-ı apply etmək) · state fayllarının müntəzəm backup-ı · pipeline-da erkən xəbərdarlıq (plan mərhələsində tutmaq) · kritik resurslarda prevent_destroy + create_before_destroy. Fəlsəfə: irəliyə doğru düzəliş (roll forward) çox vaxt geri qayıtmadan asandır.
